# 3.1 HTML FUNDAMENTALS

## 3.1.1 Document Structure and Parsing
🟢 Beginner · **Must-know** · Prerequisites: Phase 2.1

**Definition:** The skeleton every HTML page needs, and how the browser turns markup into the DOM.

**Why interviewers ask:** It checks whether you know what the browser does with your markup, which underpins performance, SEO, and bug-hunting.

**Minimal correct document**
```html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Page title (unique per page)</title>
  <meta name="description" content="150-160 char summary for search results">
  <link rel="stylesheet" href="/styles.css">
  <script src="/app.js" defer></script>
</head>
<body>
  <header>…</header>
  <main id="main">…</main>
  <footer>…</footer>
</body>
</html>
```

**Key concepts**
- **`<!DOCTYPE html>`** triggers **standards mode**. Without it the browser uses **quirks mode**, which emulates old buggy behavior (e.g., a different box model).
- **`lang`** on `<html>` helps screen readers pick pronunciation, helps translation tools, and aids SEO.
- **`charset` must be within the first 1024 bytes** and match the HTTP header (UTF-8).
- **Viewport meta:** without it, mobile browsers render at about 980px and scale down, so your media queries won't behave. Don't set `user-scalable=no`, because it breaks zoom accessibility.
- **Parsing pipeline:** bytes → characters → tokens → nodes → **DOM**. CSS becomes the **CSSOM**. DOM + CSSOM → **render tree** → layout → paint → composite.
- **The parser is forgiving.** It auto-closes tags, relocates misplaced elements, and never throws. Invalid HTML therefore fails silently in odd ways. Validate with the W3C validator.
- **Render-blocking and parser-blocking:** CSS blocks rendering. A classic `<script>` blocks the parser (it must run first because it might call `document.write` or read styles).
- **Lifecycle events:** `DOMContentLoaded` fires when HTML is parsed and deferred scripts have run (no waiting for images). `load` fires after all resources (images, styles) finish.
- **Head order matters for performance:** charset, viewport, `<title>`, preconnects, critical CSS, then scripts.
- **Block vs inline elements:** block (`div`, `p`, `section`) start on a new line and take full width. Inline (`span`, `a`, `strong`) flow in text, and width and height don't apply. Inline-block mixes both.

**Questions**
1. What does the doctype do? What is quirks mode?
2. Why is the viewport meta tag needed?
3. `DOMContentLoaded` vs `load`?
4. What happens when the parser meets a `<script>` without `defer` or `async`?
5. What's the difference between the DOM and the HTML source? *(The DOM is the parsed, corrected, live object tree. JS changes it, and "view source" shows the original text.)*
6. What does the browser do with invalid HTML like an unclosed `<div>`?
7. Block vs inline vs inline-block?

**Model answer, Q4:** "The parser stops building the DOM, downloads the script, executes it, then resumes. That's why scripts at the top without `defer` delay first render. `defer` downloads in parallel and runs after parsing, in order. `async` runs as soon as downloaded, in any order, which suits independent scripts like analytics."

**Mistakes:** forgetting the viewport meta, multiple `<h1>`-style structure chaos, scripts in `<head>` with no `defer`, missing `lang`.

**Mini task:** Write a page, remove the doctype, and observe the difference in rendering (e.g., table cell sizing and `box-sizing`). Then `console.log` the timing of `DOMContentLoaded` vs `load` with a large image.

## 3.1.2 Semantic HTML
🟢 Beginner · **Must-know**

**Definition:** Choosing elements for their *meaning* (a nav is a `<nav>`, not a `<div class="nav">`), so browsers, assistive tech, and search engines understand the page.

**Why interviewers ask:** It's a proxy for accessibility awareness and craftsmanship. "Div soup" is a red flag.

**Key concepts**

| Element | Purpose |
|---|---|
| `<header>` | Intro or navigational aids, for the page or a section |
| `<nav>` | Major navigation links (label multiple navs with `aria-label`) |
| `<main>` | Primary content, **one per page** (skip-link target) |
| `<article>` | Self-contained, independently distributable (post, card, comment) |
| `<section>` | Thematic grouping, **should have a heading** |
| `<aside>` | Tangentially related content (sidebar, callout) |
| `<footer>` | Footer for page or section |
| `<figure>`/`<figcaption>` | Media with a caption |
| `<time datetime="">` | Machine-readable dates |
| `<address>` | Contact info for the nearest article/body |
| `<mark>`, `<abbr>`, `<code>`, `<kbd>`, `<blockquote>`, `<cite>` | Inline semantics |

- **Landmarks:** `header`, `nav`, `main`, `aside`, `footer`, and `section`/`form` with a name map to ARIA landmarks. Screen reader users jump between them.
- **Heading hierarchy:** one logical outline (`h1` → `h2` → `h3`), no skipping levels for styling. Style with CSS, not heading level.
- **Buttons vs links:** `<a href>` **navigates**, `<button>` **performs an action**. A `<div onclick>` has no keyboard focus, no Enter/Space activation, and no role. You'd have to re-implement all of that (the first rule of ARIA is to use native elements first).
- **Lists** (`ul/ol/dl`) for list content, **tables** for tabular data only (with `<caption>`, `<th scope>`), and never for layout.
- **`<div>` and `<span>`** are fine when no semantic element fits.
- **Benefits:** accessibility for free, SEO, readable code, default behaviors (focus, keyboard, form submit), and reader modes.

```html
<!-- ❌ -->
<div class="button" onclick="save()">Save</div>
<!-- ✅ -->
<button type="button" onclick="save()">Save</button>
```

**Questions**
1. Why use semantic HTML? Give concrete benefits.
2. `<section>` vs `<article>` vs `<div>`?
3. Why is `<div onclick>` a bad button? What do you lose?
4. How should headings be structured?
5. When is a `<table>` appropriate?
6. `<b>` vs `<strong>`, `<i>` vs `<em>`? *(strong/em carry meaning and emphasis for screen readers. b/i are presentational.)*
7. How do you make multiple `<nav>` elements distinguishable? *(`aria-label="Primary"`, `aria-label="Footer"`)*

**Model answer, Q3:** "A `div` has no role, so screen readers don't announce a button. It isn't focusable via Tab, doesn't activate with Enter or Space, has no disabled state, and doesn't submit forms. A native `<button>` gives all of that for free. To fix a div you'd need `role="button"`, `tabindex="0"`, key handlers, and focus styles, which is just reimplementing `<button>` badly."

**Mini task:** Take a div-soup page (copy any), refactor with semantic landmarks, run Lighthouse accessibility before and after, and navigate with VoiceOver, NVDA, or the browser's accessibility tree.

## 3.1.3 Script Loading and Resource Hints
🟡 Intermediate · **Must-know**

```
<script>              ── HTML parsing ▮▮▮ pause ▮ fetch ▮ execute ▮ resume ▮▮▮
<script async>        ── parsing ▮▮▮▮▮▮ (fetch in parallel) ▮ pause + execute when ready ▮▮▮
<script defer>        ── parsing ▮▮▮▮▮▮▮▮▮▮ (fetch in parallel) ▮ execute after parse, in order
<script type="module">── like defer by default; strict mode; own scope; import/export
```

| | Blocks parsing | Order preserved | Runs when | Use for |
|---|---|---|---|---|
| plain | Yes | Yes | Immediately | Rarely (tiny inline critical code) |
| `async` | Only during execution | No | ASAP after download | Independent scripts (analytics) |
| `defer` | No | Yes | After parsing, before `DOMContentLoaded` | App code that needs the DOM |
| `module` | No | Yes (deferred) | After parsing | Modern apps; `async` also allowed on modules |

**Resource hints**
- `<link rel="preload" href="font.woff2" as="font" crossorigin>`: fetch this *current-page* resource early at high priority (fonts need `crossorigin` even same-origin).
- `<link rel="preconnect" href="https://api.example.com">`: do DNS, TCP, and TLS early.
- `<link rel="dns-prefetch">`: DNS only, a cheaper fallback.
- `<link rel="prefetch" href="/next-page.js">`: low-priority fetch for a *likely future* navigation.
- `<link rel="modulepreload">`: preload ES modules.
- `fetchpriority="high"` on the LCP image, `loading="lazy"` for below-the-fold images, `<link rel="stylesheet" media="print">` tricks for non-critical CSS.
- **Overusing preload** hurts, because it competes with other critical resources.

**Questions**
1. `async` vs `defer`? When would each be wrong? *(async for scripts that depend on DOM or on each other can break. defer is the default choice.)*
2. Why can a `<script>` in `<head>` hurt performance?
3. `preload` vs `prefetch` vs `preconnect`?
4. Why must font preloads include `crossorigin`?
5. How are ES modules loaded differently from classic scripts?

**Mini task:** Load three scripts with dependencies using the three modes and log the execution order. Make a table of what you observed.

## 3.1.4 Forms and Validation
🟡 Intermediate · **Must-know**

**Definition:** Collecting user input with native controls and validating it in the browser (UX) and on the server (security).

**Why interviewers ask:** Forms are the main way users send data. Questions expose your knowledge of native validation, accessibility, UX, and the client/server trust boundary.

**Key concepts**
- **Labels:** every control needs a programmatic label, via `<label for="id">` or by wrapping. Placeholders are *not* labels (they disappear and have poor contrast). A label also increases the click target.
- **Input types** give mobile keyboards and built-in validation: `email`, `tel`, `url`, `number`, `date`, `password`, `search`, `range`, `file`, `checkbox`, `radio`. Plus `inputmode="numeric"` for numeric keypads without `number`'s quirks (use it for OTP and card numbers, not `type=number`).
- **Constraint attributes:** `required`, `minlength`, `maxlength`, `min`, `max`, `step`, `pattern`, `type`.
- **Constraint Validation API:** `input.validity` (`valueMissing`, `typeMismatch`, `patternMismatch`, `tooShort`, `rangeUnderflow`, `customError`…), `checkValidity()`, `reportValidity()`, `setCustomValidity(msg)` (an empty string clears it), `:valid`/`:invalid`, and `:user-invalid` (only after user interaction, a newer and better UX hook).
- **`novalidate`** on the form disables built-in bubbles so you can render custom messages while still using the API.
- **`autocomplete` tokens** (`email`, `current-password`, `new-password`, `one-time-code`, `given-name`, `street-address`) enable autofill and password managers (also a WCAG requirement).
- **Submit behavior:** a `<button>` inside a form defaults to `type="submit"`, so always set `type="button"` for non-submit buttons. Enter submits when a form has a submit button.
- **`FormData`** collects values: `new FormData(form)`, then `Object.fromEntries(fd)`. Unchecked checkboxes aren't included. Multiple values per name need `getAll`.
- **File uploads:** `<input type="file" accept="image/*" multiple>` and `enctype="multipart/form-data"`. Validate type and size on the *server* (the `accept` attribute is only a hint).
- **Accessible errors:** associate with `aria-describedby`, set `aria-invalid="true"`, announce with `role="alert"` or `aria-live="polite"`, move focus to the first invalid field on submit, state the error in text (not by color alone), and don't clear user input.
- **Client vs server validation:** client validation is for UX. **Server validation is mandatory** because the client can be bypassed with curl or DevTools. Validate type, length, range, format, and authorization on the server, and return a field-level error structure (`422` with `{errors: {email: "..."}}`).
- **Fieldset/legend** group related controls (radio groups).
- **CSRF** (Phase 7) applies to cookie-authenticated form posts.

```html
<form id="signup" novalidate>
  <div>
    <label for="email">Email</label>
    <input id="email" name="email" type="email" required
           autocomplete="email" aria-describedby="email-err">
    <p id="email-err" class="error" hidden></p>
  </div>

  <div>
    <label for="pw">Password (min 12 chars)</label>
    <input id="pw" name="password" type="password" required minlength="12"
           autocomplete="new-password" aria-describedby="pw-err">
    <p id="pw-err" class="error" hidden></p>
  </div>

  <button type="submit">Create account</button>
</form>
```
```js
const form = document.querySelector('#signup');

form.addEventListener('submit', (e) => {
  let firstInvalid = null;
  for (const input of form.elements) {
    if (!(input instanceof HTMLInputElement)) continue;
    const err = document.getElementById(`${input.id}-err`);
    const ok = input.checkValidity();
    input.setAttribute('aria-invalid', String(!ok));
    err.hidden = ok;
    err.textContent = ok ? '' : input.validationMessage;
    if (!ok && !firstInvalid) firstInvalid = input;
  }
  if (firstInvalid) { e.preventDefault(); firstInvalid.focus(); }
});

// custom rule example
pw.addEventListener('input', () => {
  pw.setCustomValidity(/\d/.test(pw.value) ? '' : 'Include at least one number');
});
```

**Questions**
1. Why is client-side validation not enough?
2. How do you make form errors accessible?
3. `<input type="number">` problems? *(scroll wheel changes value, allows `e`, leading zeros lost, bad for IDs/phones/OTP, so use `text` + `inputmode`/`pattern`.)*
4. What's the Constraint Validation API?
5. What's the default `type` of a `<button>` in a form, and why does it matter?
6. Controlled vs uncontrolled inputs (React, covered in Phase 4)?
7. How would you validate an email? *(`type=email` for basic shape, then send a confirmation email. A regex can't prove the address exists or is deliverable.)*
8. How do you prevent double submission? *(disable the button while pending, use idempotency keys server-side)*
9. How do file uploads work in HTML? What are the security concerns? *(multipart, MIME sniffing, size limits, malware, path traversal, storing outside the web root, Phase 7)*
10. How do you preserve user data on validation failure?

**Mistakes:** placeholder as label; relying only on client validation; `type="submit"` by accident on plain buttons (page reload); error text only in red; blocking paste in password fields; regex-validating emails to death.

**Mini task:** Build a registration form with custom error rendering, `aria-describedby`, focus-first-error, async username-availability check (debounced), and a server stub that returns `422` with per-field errors that you display.

## 3.1.5 Accessibility Standards (HTML-level)
🟡 Intermediate · **Must-know** (deep dive: Phase 3 Part 3)

**Definition:** Building so people with disabilities (visual, motor, hearing, cognitive) can perceive, operate, and understand your UI.

**Why interviewers ask:** It's legally relevant (ADA, EAA, Section 508), widens your audience, and signals senior-level care.

**Key concepts**
- **WCAG** principles, **POUR:** Perceivable, Operable, Understandable, Robust. Levels A, AA (the usual legal target), and AAA. Current version is 2.2.
- **Text alternatives:** meaningful `alt` for informative images, `alt=""` for decorative ones (so screen readers skip them), and an `aria-label` or visually hidden text for icon-only buttons. Never omit `alt` entirely.
- **Contrast (AA):** 4.5:1 for normal text, 3:1 for large text (18pt+ or 14pt bold+) and UI components.
- **Keyboard:** everything operable via Tab, Shift+Tab, Enter, Space, arrows, and Esc. **Visible focus indicator** (never `outline: none` without a replacement), and use `:focus-visible`. Logical tab order follows DOM order, and avoid positive `tabindex`. A **skip link** to `#main`. Don't trap focus (except in modals, deliberately).
- **Target size:** WCAG 2.2 sets a 24×24 CSS px minimum (AA), with about 44×44 as a good mobile target.
- **ARIA:** it only changes what assistive tech *hears*, not behavior.
  - **Rule 1:** use native HTML first.
  - Roles (`role="dialog"`), states (`aria-expanded`, `aria-checked`, `aria-selected`), properties (`aria-label`, `aria-labelledby`, `aria-describedby`), and live regions (`aria-live`, `role="status"`, `role="alert"`).
  - **Bad ARIA is worse than no ARIA.** Incorrect roles mislead users.
- **Don't convey info by color alone**; respect `prefers-reduced-motion`; support zoom to 200% and reflow at 320px width; use relative units.
- **Forms:** labels, grouped controls, and error association (3.1.4).
- **Dynamic content:** announce changes (toasts, route changes in SPAs) with live regions, and manage focus on route change and modal open and close.
- **Testing:** keyboard-only pass, screen reader (VoiceOver, NVDA), axe DevTools, Lighthouse, the browser accessibility tree panel, and zoom and high-contrast testing. Automated tools catch only about 30-40% of issues.

```html
<a class="skip" href="#main">Skip to content</a>
<button aria-label="Close dialog"><svg aria-hidden="true">…</svg></button>
<button aria-expanded="false" aria-controls="menu">Menu</button>
<div id="status" role="status" aria-live="polite"></div>
```
```css
.sr-only { position:absolute; width:1px; height:1px; margin:-1px; padding:0;
           overflow:hidden; clip-path:inset(50%); white-space:nowrap; border:0; }
:focus-visible { outline: 3px solid #1a73e8; outline-offset: 2px; }
```

**Questions**
1. What are the first steps to make a page accessible?
2. What's ARIA and when should you not use it?
3. `alt=""` vs missing `alt` vs descriptive alt?
4. How do you test accessibility?
5. How do you make a custom dropdown or modal accessible? *(roles, focus management, keyboard handling, Esc, `aria-expanded`, return focus. Better: use native `<dialog>` and `<select>`.)*
6. `display:none` vs `visibility:hidden` vs `aria-hidden` vs `.sr-only` for screen readers? *(none and hidden remove from the accessibility tree. `aria-hidden` removes it from AT but not visually. `.sr-only` is visual-only hidden but announced.)*
7. How would you announce an async result (e.g., "Saved") to screen readers?
8. What contrast ratio does WCAG AA require?

**Mini task:** Unplug your mouse and complete a purchase flow on a real site. Write down every barrier. Then fix a small demo app until axe reports zero issues *and* it works by keyboard alone.

## 3.1.6 SEO, Meta Tags, and Open Graph
🟡 Intermediate · **Good-to-know** (**Must** for content and e-commerce roles)

**Key concepts**
- **Crawl → render → index → rank.** Googlebot does execute JavaScript but in a deferred rendering queue. For critical content prefer **SSR/SSG** (Phase 4). Make sure content isn't behind client-only fetches or blocked by `robots.txt`.
- **Essentials**
  - Unique `<title>` (about 50-60 chars) and `<meta name="description">` (about 150-160 chars) per page
  - One clear `<h1>`, a logical heading outline, semantic HTML, descriptive link text (not "click here"), and `alt` text
  - Clean, human-readable URLs, and **canonical** tags: `<link rel="canonical" href="…">` to resolve duplicate content
  - `robots.txt` (crawl rules, not security) and `<meta name="robots" content="noindex">` (index rules), plus `sitemap.xml`
  - Proper status codes: 301 for moves, a real 404 (avoid "soft 404"), and a 410 for permanently gone
  - `hreflang` for localized variants
  - **Core Web Vitals** (LCP, INP, CLS) are ranking signals, and mobile-first indexing applies
  - **Structured data (JSON-LD)** enables rich results (Product, Article, FAQ, BreadcrumbList)
- **Open Graph / Twitter cards** control link previews (not ranking):

```html
<meta property="og:title" content="Title">
<meta property="og:description" content="Summary">
<meta property="og:image" content="https://example.com/og.png">  <!-- ~1200×630, absolute URL -->
<meta property="og:url" content="https://example.com/page">
<meta property="og:type" content="article">
<meta name="twitter:card" content="summary_large_image">

<script type="application/ld+json">
{ "@context":"https://schema.org", "@type":"Product", "name":"Mug",
  "offers": { "@type":"Offer", "price":"12.00", "priceCurrency":"USD" } }
</script>
```
- **SPA SEO pitfalls:** the same `<title>` on every route, content loaded only after login or interaction, hash-based URLs, and missing server-side 404s.
- **Social crawlers don't run JS**, so OG tags must be in the server-rendered HTML.

**Questions**
1. How would you make a React SPA SEO-friendly? *(SSR/SSG with Next.js or similar, per-route metadata, canonical, sitemap, real links `<a href>`, structured data, performance.)*
2. `noindex` vs `robots.txt` disallow? *(A disallowed URL can still be indexed from links without content. To remove it from results, allow crawling and use `noindex`.)*
3. What's a canonical URL and why?
4. What are Open Graph tags? Why do they sometimes not update? *(scraper caches. Use the Sharing Debugger)*
5. What's structured data?
6. Why does link text matter?

**Mini task:** Audit a page with Lighthouse and view-source, then write the missing meta, canonical, OG, and JSON-LD. Validate with the Rich Results Test.

## 3.1.7 Responsive Images and Media
🟡 Intermediate · **Must-know** (for performance)

**Key concepts**
- **Resolution switching:** let the browser choose a file by viewport and DPR.
```html
<img src="photo-800.jpg"
     srcset="photo-400.jpg 400w, photo-800.jpg 800w, photo-1600.jpg 1600w"
     sizes="(min-width: 1024px) 33vw, 100vw"
     width="800" height="600" alt="Team at the 2024 offsite"
     loading="lazy" decoding="async">
```
  `w` descriptors say how wide each file is, and `sizes` says how wide the image will *display*. The browser combines these with DPR to pick one. (`x` descriptors suit fixed-size images.)
- **Art direction and formats with `<picture>`:**
```html
<picture>
  <source type="image/avif" srcset="hero.avif">
  <source type="image/webp" srcset="hero.webp">
  <source media="(max-width: 600px)" srcset="hero-crop.jpg">
  <img src="hero.jpg" width="1200" height="600" alt="…">
</picture>
```
- **Prevent CLS:** always set `width` and `height` (or CSS `aspect-ratio`), and the browser reserves space before the image loads.
- **Lazy-load below the fold; never lazy-load the LCP/hero image.** Give it `fetchpriority="high"`.
- **Formats:** AVIF (best compression) → WebP → JPEG/PNG fallback. SVG for icons and logos. Prefer video over GIF (`<video autoplay muted loop playsinline>`).
- **`object-fit: cover|contain`** controls cropping in a box.
- **Video/audio:** `<video controls preload="metadata" poster>` with `<track kind="captions">` for accessibility.
- **Image CDNs/frameworks** (`next/image`, Cloudinary, imgix) automate resizing and format negotiation.

**Questions**
1. `srcset` vs `sizes` vs `<picture>`: what does each do?
2. How do images cause layout shift? How do you prevent it?
3. Why shouldn't the hero image be lazy-loaded?
4. Which format would you choose and why?
5. How do you serve an appropriately cropped image on mobile? *(`<picture>` with `media` sources)*

**Mini task:** Take a 3MB hero image and get it under 150KB on mobile using AVIF/WebP, `srcset`, and proper dimensions. Compare LCP before and after in Lighthouse.

## 3.1.8 Native Interactive Elements: `<dialog>`, `<details>`, Popover
🟡 Intermediate · **Good-to-know**

- **`<dialog>`:** `dialog.showModal()` opens it in the top layer, with a `::backdrop`, **focus trapping**, inert background, and **Esc to close**, all built in. `dialog.show()` opens non-modally. `dialog.close(returnValue)`, and `<form method="dialog">` closes it on submit. Focus is restored to the previously focused element in modern browsers.
```html
<button id="open">Delete…</button>
<dialog id="confirm" aria-labelledby="t">
  <form method="dialog">
    <h2 id="t">Delete item?</h2>
    <button value="cancel">Cancel</button>
    <button value="ok">Delete</button>
  </form>
</dialog>
<script>
  open.onclick = () => confirm.showModal();
  confirm.addEventListener('close', () => console.log(confirm.returnValue));
</script>
```
- **`<details>`/`<summary>`:** an accessible, JS-free disclosure. With a shared `name` attribute, several details form an exclusive accordion. It's searchable and keyboard-operable.
- **Popover API:** `<button popovertarget="tip">` + `<div id="tip" popover>` gives light-dismiss, top-layer rendering, and Esc handling. It's good for menus and tooltips (anchor positioning is arriving in CSS).
- **`inert` attribute:** makes a subtree non-interactive and non-focusable (handy for modals you build yourself).
- **Why it matters:** these replace hundreds of lines of JS and ARIA, with better accessibility by default.

**Questions**
1. What do you get for free from `<dialog>.showModal()`?
2. How would you build an accessible modal from scratch (if you couldn't use `<dialog>`)? *(role=dialog + aria-modal, labelled, focus moves in, trapped inside, Esc closes, backdrop click closes, focus returns, background inert/scroll lock)*
3. `<details>` vs a custom accordion?

**Mini task:** Build a confirm modal, an FAQ accordion, and a dropdown menu using only native elements.

## 3.1.9 SVG
🟡 Intermediate · **Good-to-know**

- **Definition:** XML-based vector graphics, resolution-independent and scriptable.
- **Usage options**

| Method | CSS-stylable internals | Cached | Notes |
|---|---|---|---|
| `<img src="x.svg">` | No | Yes | Simple, no scripting |
| Inline `<svg>` | Yes (`currentColor`, CSS vars) | No (part of HTML) | Best for icons you theme and animate |
| CSS `background-image` | No | Yes | Decorative |
| `<use href="#id">` sprite | Partial (via CSS vars) | Yes | Reuse many icons |

- **`viewBox="0 0 24 24"`** defines the internal coordinate system, and the SVG scales to fit its CSS size. `preserveAspectRatio` controls fit.
- **Theming:** `fill="currentColor"` makes icons inherit text color.
- **Accessibility:** decorative → `aria-hidden="true"`. Meaningful → `<title>` + `role="img"` + `aria-labelledby`.
- **Performance:** optimize with SVGO, avoid huge path data, and avoid thousands of nodes (use Canvas then).
- **SVG vs Canvas vs DOM:** SVG has a retained scene graph (each shape is a DOM node, so it's easy to attach events and accessible, but slow with many thousands of elements). Canvas is immediate mode (fast for many objects, but you manage hit-testing and accessibility).
- **Security:** inline untrusted SVG can contain scripts, so sanitize user-uploaded SVGs (DOMPurify) or serve via `<img>`.

**Questions:** inline SVG vs `<img>`? How do you recolor an icon with CSS? What's `viewBox`? SVG vs Canvas for 10k points? *(Canvas, or WebGL.)* Security risk of user-uploaded SVG? *(XSS through `<script>` or event handlers.)*

## 3.1.10 Canvas API
🟡 Intermediate · **Good-to-know** (appears in games, charts, image editing, drawing apps)

**Definition:** A bitmap drawing surface controlled by JavaScript (`2D` context, plus `WebGL`/`WebGPU` for GPU graphics).

**Key concepts**
- **Immediate mode:** once drawn, pixels are just pixels. There are no objects. To "move" something you clear and redraw the scene each frame.
- **Setup and HiDPI fix:** the canvas has a *bitmap size* (`width`/`height` attributes) separate from its *CSS size*. If you don't scale for `devicePixelRatio`, drawings look blurry on retina screens.
- **Animation loop:** use `requestAnimationFrame` (synced to display refresh and paused in background tabs), and make motion **time-based** (delta time), not frame-based.
- **API surface:** paths (`beginPath`, `moveTo`, `lineTo`, `arc`, `fill`, `stroke`), shapes (`fillRect`, `clearRect`), text, images (`drawImage`), transforms (`translate`, `rotate`, `scale`), state (`save()`/`restore()`), compositing, and `getImageData`/`putImageData` for pixel manipulation.
- **Hit-testing and events:** the canvas is one element, so you compute hits yourself (distance, bounding boxes, or an offscreen color-picking trick).
- **Accessibility:** the canvas is opaque to assistive tech, so provide fallback content inside the tag, ARIA labels, or a parallel DOM and data table.
- **Performance:** batch draw calls, avoid per-frame allocations, cache static layers on an offscreen canvas, and use `OffscreenCanvas` in a Web Worker, WebGL for heavy scenes, and integer coordinates for crisp lines.

```js
const canvas = document.querySelector('canvas');
const ctx = canvas.getContext('2d');
const dpr = window.devicePixelRatio || 1;
const { width, height } = canvas.getBoundingClientRect();
canvas.width = width * dpr;  canvas.height = height * dpr;
ctx.scale(dpr, dpr);                       // draw in CSS pixels

let x = 0, last = performance.now();
function frame(now) {
  const dt = (now - last) / 1000; last = now;   // seconds since last frame
  x = (x + 120 * dt) % width;                   // 120 px/second regardless of FPS
  ctx.clearRect(0, 0, width, height);
  ctx.fillStyle = '#1a73e8';
  ctx.beginPath(); ctx.arc(x, height / 2, 20, 0, Math.PI * 2); ctx.fill();
  requestAnimationFrame(frame);
}
requestAnimationFrame(frame);
```

## 3.1.11 Web Components and Shadow DOM
🔴 Advanced · **Good-to-know** (increasingly asked for design-system roles)

**Definition:** A set of browser-native standards for creating reusable, encapsulated custom elements that work in any framework.

**Three pillars**
1. **Custom Elements:** `customElements.define('user-card', UserCard)`. The name must contain a hyphen.
2. **Shadow DOM:** an encapsulated DOM subtree with scoped styles, via `attachShadow({mode:'open'})`.
3. **HTML templates and slots:** `<template>` (inert markup to clone) and `<slot>` (placeholders for light-DOM children).

**Lifecycle callbacks**

| Callback | Fires when |
|---|---|
| `constructor` | Element created (don't read attributes or children here) |
| `connectedCallback` | Added to the DOM (set up listeners, fetch, render) |
| `disconnectedCallback` | Removed (clean up listeners, timers, observers) |
| `attributeChangedCallback(name, old, new)` | An attribute in `static observedAttributes` changes |
| `adoptedCallback` | Moved to another document |

**Encapsulation rules**
- Styles inside the shadow root don't leak out, and page styles don't leak in.
- **Inherited properties and CSS custom properties pierce** the boundary (the theming mechanism).
- Expose styling hooks with `::part(name)` and CSS variables. Style from inside with `:host`, `:host(.x)`, and `::slotted(span)`.
- **Events:** are retargeted at the boundary. Dispatch custom events with `{bubbles: true, composed: true}` to cross out of the shadow root.
- `mode: 'open'` allows `el.shadowRoot` access. `closed` hides it (rarely worthwhile).
- **Form participation** needs `static formAssociated = true` plus `ElementInternals`.
- **SSR:** historically hard, and **Declarative Shadow DOM** (`<template shadowrootmode="open">`) now allows server-rendered shadow roots. Libraries like **Lit** add reactive templates.
- **Trade-offs vs React components:** framework-agnostic, long-lived, and native, but no built-in reactivity or state primitives, a verbose API without Lit, accessibility across shadow boundaries needing care (`aria-labelledby` can't reference across roots), and SSR and React interop quirks (React 19 improved custom-element props and events).
- **Used by:** design systems intended for multiple frameworks (Shoelace/Web Awesome, Salesforce Lightning, GitHub elements) and micro-frontend widgets.

```js
class UserCard extends HTMLElement {
  static observedAttributes = ['name'];

  constructor() {
    super();
    this.attachShadow({ mode: 'open' });
    this.shadowRoot.innerHTML = `
      <style>
        :host { display: block; border: 1px solid var(--card-border, #ddd); padding: 1rem; }
        h3 { margin: 0; }
      </style>
      <slot name="avatar"></slot>
      <h3 part="title"></h3>
      <slot></slot>`;
    this.title = this.shadowRoot.querySelector('h3');
  }

  connectedCallback() { this.#render(); }
  attributeChangedCallback() { this.#render(); }

  #render() { this.title.textContent = this.getAttribute('name') ?? 'Anonymous'; } // textContent: no XSS
}
customElements.define('user-card', UserCard);
```
```html
<user-card name="Ada">
  <img slot="avatar" src="ada.png" alt="">
  <p>Mathematician</p>
</user-card>
```

## 3.2.1 The Cascade, Specificity, and Inheritance
🟡 Intermediate · **Must-know**

**Definition:** The algorithm that decides which declaration wins when several rules target the same property.

**Why interviewers ask:** Almost every "why isn't my style applying?" bug is cascade-related. Candidates who understand it debug fast.

**Cascade order (high to low priority)**
1. **Origin and importance:** transitions → `!important` user-agent → `!important` user → `!important` author → animations → normal author → normal user → normal user-agent
2. **Cascade layers** (`@layer`): for normal declarations, later layers win, and unlayered styles beat layered ones. The order *reverses* for `!important`.
3. **Specificity**
4. **Order of appearance:** the last rule wins ties

**Specificity** (compare as (IDs, classes/attributes/pseudo-classes, elements/pseudo-elements), left to right, not as a base-10 number):

| Selector | Specificity |
|---|---|
| `*`, combinators (`>`, `+`, `~`) | 0,0,0 |
| `p`, `::before` | 0,0,1 |
| `.card`, `[type=text]`, `:hover` | 0,1,0 |
| `#nav` | 1,0,0 |
| `nav ul li a.active` | 0,1,4 |
| inline `style=""` | beats all selectors (just not `!important`) |
| `:is(a, .b)` | the highest specificity among its arguments |
| `:where(...)` | **always 0**, great for resets and defaults |
| `:not(.x)` | the specificity of its argument |

- **Inheritance:** some properties inherit by default (`color`, `font-*`, `line-height`, `visibility`, `cursor`), and many don't (`margin`, `padding`, `border`, `background`, `width`). Control it with `inherit`, `initial`, `unset`, `revert`.
- **Strategies:** keep specificity low and flat (single classes), avoid IDs in CSS, avoid `!important` (except utilities and overriding third-party), use `@layer` to order resets → base → components → utilities, and use `:where()` for default styles.
- **Debugging:** DevTools → Elements → Styles panel (struck-through rules lost), and the Computed tab shows the winner and traces it.

```css
@layer reset, base, components, utilities;
@layer components { .btn { padding: .5rem 1rem; } }
@layer utilities  { .p-0 { padding: 0; } }   /* wins even with lower specificity, as it's a later layer */
```

**Questions**
1. How does CSS decide between conflicting rules?
2. Specificity of `#a .b p` vs `.x .y .z .w`? *(1,1,1 beats 0,4,0, since an ID beats any number of classes.)*
3. What does `!important` do, and why avoid it?
4. Which properties inherit?
5. What are `@layer` and `:where()` for?
6. `initial` vs `inherit` vs `unset` vs `revert`?
7. Why might your style not apply? *(Overridden by a more specific rule, typo, wrong selector, not a valid value, an inherited vs non-inherited property confusion, the rule loads earlier, a layer order issue, a shadow DOM boundary.)*

**Model answer, Q1:** "First by origin and importance, so `!important` flips priorities. Then cascade layers, then specificity, comparing IDs, then classes/attributes/pseudo-classes, then elements. If still tied, the later declaration wins. I keep selectors flat and low-specificity and use layers to make ordering explicit."

## 3.2.2 Box Model, Display, Margin Collapsing, BFC, Units
🟢 → 🟡 · **Must-know**

**The box model:** every element is a box: **content → padding → border → margin**.
```
┌────────────── margin ──────────────┐
│ ┌──────────── border ────────────┐ │
│ │ ┌────────── padding ─────────┐ │ │
│ │ │          content           │ │ │
```
- **`box-sizing: content-box` (default):** `width` is *content only*, so the total = width + padding + border. **`border-box`:** `width` includes padding and border, which is far more predictable.
```css
*, *::before, *::after { box-sizing: border-box; }
```
- **Margin collapsing:** adjacent *vertical* margins of block elements combine into the larger one (not the sum). It happens between siblings, between a parent and its first or last child (if no border, padding, or clearfix separates them), and for empty blocks. It does **not** happen horizontally, in flex or grid containers, with floats, absolutely positioned elements, or in a new BFC.
- **Block formatting context (BFC):** an isolated layout region. Created by `overflow` other than visible, `display: flow-root` (the clean way), floats, absolute/fixed positioning, flex/grid items, and `contain: layout`. A BFC contains its floats (the clearfix replacement) and prevents margin collapse with children.
- **`display` values:** `block`, `inline`, `inline-block`, `flex`, `grid`, `none`, `contents`, `flow-root`, `table`.
- **Hiding techniques**

| Technique | Layout space | Accessibility tree | Events |
|---|---|---|---|
| `display: none` | Removed | Removed | No |
| `visibility: hidden` | Kept | Removed | No |
| `opacity: 0` | Kept | **Kept** | **Yes** (still clickable) |
| `hidden` attribute | Removed (UA `display:none`) | Removed | No |
| `.sr-only` | ~None | Kept | Focusable |

- **Units**

| Unit | Relative to | Use |
|---|---|---|
| `px` | CSS pixel | Borders, shadows, hairlines |
| `rem` | Root font-size (user preference) | Font sizes, spacing (respects user zoom settings) |
| `em` | The element's own font size (and for `font-size`, the parent's) | Component-relative padding (compounds when nested) |
| `%` | Parent's relevant dimension | Fluid widths |
| `vw`/`vh` | Viewport width/height | Full-bleed sections |
| `dvh`/`svh`/`lvh` | Dynamic/small/large viewport height | Mobile browsers with a collapsing URL bar (`100vh` overflows) |
| `ch` | Width of "0" | Readable line length (`max-width: 65ch`) |
| `fr` | Fraction of free space (grid) | Grid tracks |
| `lh`, `cqw` | Line height, container width | Modern spacing, container-based sizing |

- **Width/height details:** `width: auto` for block = fill container. `min-width`/`max-width` override. Percent heights need a parent with an explicit height. `aspect-ratio: 16/9` keeps proportions. `overflow: auto|hidden|scroll|clip`.
- **Inline elements** ignore vertical `margin` and `width`/`height`. Images are inline by default, causing a small baseline gap beneath them (`display:block` or `vertical-align: middle` fixes it).
- **`outline` vs `border`:** the outline doesn't take layout space and can overlap.
- **Text overflow**
```css
.truncate { white-space: nowrap; overflow: hidden; text-overflow: ellipsis; }
.clamp-3 { display: -webkit-box; -webkit-line-clamp: 3; -webkit-box-orient: vertical; overflow: hidden; }
```

## 3.2.3 Positioning and Stacking Context
🟡 Intermediate → 🔴 · **Must-know**

**`position` values**

| Value | Behavior |
|---|---|
| `static` (default) | Normal flow, and `top/left/z-index` ignored |
| `relative` | Normal flow, offset visually, and becomes the **containing block** for absolute children |
| `absolute` | Removed from flow, positioned relative to the nearest **positioned ancestor** (else the initial containing block) |
| `fixed` | Relative to the viewport (unless an ancestor has `transform`/`filter`/`perspective`, which makes *that* the containing block) |
| `sticky` | Hybrid: acts relative until a scroll threshold, then sticks within its **scroll container and parent** |

- **Sticky gotchas:** needs a threshold (`top: 0`). It fails if any ancestor has `overflow: hidden|auto|scroll` (that ancestor becomes the scroll container). The sticky element can't leave its parent's bounds. Also check for `height` constraints on the parent.
- **Stacking context:** an isolated 3D layering scope. `z-index` only compares siblings *within the same stacking context*. A child with `z-index: 9999` can't escape a parent whose context sits below another.
  - **Created by:** the root element; `position` absolute/relative with `z-index` ≠ auto; fixed/sticky; `opacity < 1`; `transform`, `filter`, `perspective`, `clip-path`, `mask`; `isolation: isolate`; `will-change` on those properties; flex/grid children with `z-index` ≠ auto; `contain: layout|paint`; and top-layer elements.
  - **Paint order inside a context (low → high):** the context's background → negative z-index children → in-flow blocks → floats → inline content → `z-index: 0/auto` positioned → positive z-index.
- **Practical fix for z-index wars:** create intentional contexts with `isolation: isolate` on components, use a small z-index scale via CSS variables (`--z-dropdown: 100; --z-modal: 1000`), and render modals and tooltips in the **top layer** (`<dialog>`, popover) or a React **portal** attached to `body`.
- **Floats (legacy):** originally for text wrap. Layout is done with flex/grid now. `clear` and `flow-root` contain them.
- **`inset: 0`** is shorthand for `top/right/bottom/left: 0`, and `position: absolute; inset: 0` fills the positioned parent.

```css
.card { position: relative; }
.card .badge { position: absolute; top: .5rem; right: .5rem; }      /* corner badge */
.overlay { position: fixed; inset: 0; background: rgb(0 0 0 / .5); } /* full-screen scrim */
.header { position: sticky; top: 0; z-index: var(--z-header); }
```

**Questions**
1. `relative` vs `absolute` vs `fixed` vs `sticky`?
2. My `position: sticky` isn't sticking. Why? *(ancestor overflow, no `top`, parent too short)*
3. Why doesn't `z-index: 9999` put my dropdown above another element? *(a lower stacking context, no positioning, or an ancestor with transform/opacity)*
4. What creates a stacking context?
5. How do you ensure a modal always overlays everything? *(top layer via `<dialog>`, or a portal to `body` at the end of the DOM)*
6. Why does `position: fixed` sometimes behave like absolute? *(an ancestor with `transform`, `filter`, or `perspective`)*
7. How do you make an absolutely positioned child fill its parent? *(parent `relative`, child `inset: 0`)*

**Model answer, Q3:** "`z-index` only orders elements within the same stacking context. If my dropdown lives inside a parent that creates its own context (e.g., it has `transform` or `opacity < 1`) and that parent is below the other element's context, no z-index value inside can escape. I'd inspect the ancestors for context-creating properties, restructure the DOM, or render the dropdown in a portal or the top layer."

## 3.2.4 Flexbox
🟢 → 🟡 · **Must-know**

**Definition:** A one-dimensional layout model (a row *or* a column) for distributing space and aligning items.

**Terminology:** the container has a **main axis** (set by `flex-direction`) and a **cross axis** (perpendicular).

| Container property | Controls |
|---|---|
| `display: flex` | Enables flex |
| `flex-direction` | `row` / `column` (+ `-reverse`) |
| `flex-wrap` | `nowrap` (default) / `wrap` |
| `justify-content` | Distribution along the **main** axis (`flex-start`, `center`, `space-between`, `space-around`, `space-evenly`) |
| `align-items` | Alignment of items along the **cross** axis (`stretch` default, `center`, `flex-start`, `baseline`) |
| `align-content` | Distribution of *lines* on the cross axis (only with wrapping, multiple lines) |
| `gap` | Spacing between items (prefer over margins) |

| Item property | Controls |
|---|---|
| `flex-grow` | Share of leftover space (default 0) |
| `flex-shrink` | Share of overflow to give up (default 1) |
| `flex-basis` | Starting size before grow/shrink (default `auto`, which uses `width`/content) |
| `flex` shorthand | `flex: 1` = `1 1 0%`, `flex: auto` = `1 1 auto`, `flex: none` = `0 0 auto` |
| `align-self` | Per-item cross-axis override |
| `order` | Visual order (**does not change tab or screen-reader order**, so it's an accessibility pitfall) |
| `margin: auto` | Absorbs free space (`margin-left: auto` pushes an item to the far end) |

**Key concepts and gotchas**
- **`flex: 1` vs `flex: auto`:** `1` starts every item from a 0 basis, so items become *equal width*. `auto` starts from content size, so items grow *proportionally* from their content.
- **Items won't shrink below their content:** the automatic minimum size is `min-width: auto`. Long text, URLs, or `<pre>` overflow the container. **Fix: `min-width: 0`** on the flex item (and `overflow: hidden`/`text-overflow` for truncation).
- **`justify-content` vs `align-items`** swap axes when you change direction. The mnemonic is "justify = main, align = cross."
- **`align-items` vs `align-content`:** `align-items` positions items within each line. `align-content` distributes lines, and does nothing on single-line containers.
- **`flex-basis` vs `width`:** `flex-basis` wins on the main axis when not `auto`, and the main axis flips in columns, where it acts like height.
- **Flex items are blockified**, and margins don't collapse in flex.
- **Use flex for** navbars, toolbars, centering, button groups, card internals, and media objects. **Use grid for** two-dimensional page layouts.
- **Sticky footer:** `body { min-height: 100dvh; display:flex; flex-direction:column } main { flex:1 }`.

```css
.navbar { display: flex; align-items: center; gap: 1rem; }
.navbar .push-right { margin-left: auto; }           /* logo | links ........ avatar */

.cards { display: flex; flex-wrap: wrap; gap: 1rem; }
.cards > * { flex: 1 1 250px; }                      /* wrap at ~250px, grow to fill */

.row { display: flex; gap: .5rem; }
.row .text { min-width: 0; flex: 1; }                /* allows ellipsis to work inside flex */
.row .text p { overflow: hidden; text-overflow: ellipsis; white-space: nowrap; }
```

**Questions**
1. What's the difference between the main and cross axis? `justify-content` vs `align-items`?
2. What does `flex: 1` expand to? What's the difference from `flex: auto`?
3. Why is my flex child overflowing its container? *(`min-width: auto`, so set `min-width: 0`)*
4. `align-items` vs `align-content`?
5. `flex-basis` vs `width`?
6. How do you push one item to the right in a navbar? *(`margin-left: auto`)*
7. How would you build an equal-height card row, with the button pinned at the bottom of each card? *(cards are flex columns, the content `flex: 1`, or `margin-top: auto` on the button)*
8. Why can `order` be problematic? *(visual order ≠ DOM/tab order, which breaks accessibility and WCAG 2.4.3)*

## 3.2.5 CSS Grid
🟡 Intermediate · **Must-know**

**Definition:** A two-dimensional layout system for placing items in rows and columns.

**Key concepts**
- **Defining tracks:** `grid-template-columns`/`-rows`, with units `px`, `%`, `fr`, `auto`, `minmax(min, max)`, `repeat(n, size)`, `min-content`/`max-content`/`fit-content()`.
- **`fr` units** divide the *remaining* space after fixed and content-sized tracks. `1fr` actually means `minmax(auto, 1fr)`, so content can blow out a track (use `minmax(0, 1fr)` to prevent this).
- **Placement:** `grid-column: 1 / 3`, `grid-row: span 2`, `grid-area`, negative line numbers (`-1` = the last line), and named lines and areas.
- **`grid-template-areas`:** readable page layouts:
```css
.page {
  display: grid;
  grid-template-columns: 240px 1fr;
  grid-template-rows: auto 1fr auto;
  grid-template-areas:
    "header header"
    "sidebar main"
    "footer footer";
  min-height: 100dvh;
}
.page > header { grid-area: header; }
.page > aside  { grid-area: sidebar; }
.page > main   { grid-area: main; }
.page > footer { grid-area: footer; }
```
- **Explicit vs implicit grid:** items beyond your defined tracks create implicit tracks, sized by `grid-auto-rows`/`-columns` and ordered by `grid-auto-flow` (`row` | `column` | `dense`).
- **Alignment:** `justify-items`/`align-items` (inside cells), `justify-content`/`align-content` (the whole grid in its container), `place-items: center`, `place-content: center`, and `gap`.
- **Responsive without media queries (the RAM pattern):**
```css
.grid { display: grid; gap: 1rem;
        grid-template-columns: repeat(auto-fit, minmax(min(250px, 100%), 1fr)); }
```
  **`auto-fit` vs `auto-fill`:** both create as many columns as fit. With few items, `auto-fill` keeps the empty tracks (items stay at their minimum size), whereas `auto-fit` collapses the empty tracks so items stretch to fill the row.
- **Subgrid:** `grid-template-columns: subgrid` lets nested grids align to the parent's tracks (now supported in all major browsers). It's good for card layouts where titles, bodies, and footers must align across cards.
- **Masonry:** not fully standardized (native support is still in progress), so use JS libraries or CSS columns.
- **Grid items:** margins don't collapse, and `z-index` works without `position`. Items can overlap by sharing cells.
- **Grid vs Flexbox:** use Grid when you define the layout first and put content into it (page layouts, dashboards, galleries, forms). Use Flex when content size drives the layout in a single dimension. They nest together.

## 3.2.6 Centering and Common Layout Recipes

## 3.2.7 Responsive Design
🟡 Intermediate · **Must-know**

**Definition:** Designing layouts that adapt to any viewport, input method, and user preference.

**Key concepts**
- **Mobile-first:** write base styles for small screens, then layer enhancements with `min-width` queries. It yields simpler CSS and better mobile performance.
- **Viewport meta** (3.1.1) is required.
- **Media queries:** `@media (min-width: 48rem) { … }`. Use **content-driven breakpoints** (where the layout breaks), not device models. Using `rem`/`em` in breakpoints respects user zoom settings. Range syntax: `@media (width >= 48rem)`.
- **Feature queries:** `prefers-color-scheme`, `prefers-reduced-motion`, `prefers-contrast`, `hover: hover` and `pointer: coarse` (touch vs mouse), `orientation`, and `@supports (display: grid)`.
- **Fluid techniques** reduce the number of breakpoints:
```css
h1 { font-size: clamp(1.75rem, 1.2rem + 2.5vw, 3rem); }       /* fluid type with min/max */
.section { padding-block: clamp(2rem, 6vw, 6rem); }
.container { width: min(100% - 2rem, 70rem); margin-inline: auto; }
```
  Keep a `rem` component in fluid type so users' browser zoom still scales it (pure `vw` text fails zoom accessibility).
- **Container queries:** a component responds to *its container's* size, not the viewport. This is key for reusable components in design systems:
```css
.card-wrap { container-type: inline-size; container-name: card; }
.card { display: grid; gap: 1rem; }
@container card (min-width: 30rem) {
  .card { grid-template-columns: 8rem 1fr; }
}
```
  Supported in all modern browsers. Related: container query units (`cqw`, `cqi`), and style queries (newer).
- **Logical properties:** `margin-inline`, `padding-block`, `inset-inline-start`, `border-inline-end`, `text-align: start`, `inline-size`/`block-size`. They adapt automatically to writing mode and direction (**RTL** for Arabic and Hebrew), so you don't maintain separate left/right overrides.
- **Responsive images and media** (3.1.7) and **responsive tables** (wrap in an `overflow-x: auto` container, or restack on small screens).
- **Touch:** targets of 44px or more, no hover-only functionality (`@media (hover: hover)`), and `touch-action`.
- **Layout tools:** Grid (`auto-fit/minmax`), Flex wrap, `gap`, `aspect-ratio`, `min()`/`max()`/`clamp()`.
- **Testing:** DevTools device mode (not a real device substitute), real devices, resizing from 320px up to 2560px, zoom to 200%, landscape, and slow networks.
- **Mobile viewport units:** use `dvh`/`svh`, and account for safe areas (`env(safe-area-inset-bottom)`) on notched phones.
- **Avoid:** fixed pixel widths, horizontal scroll at 320px, hiding vast content with `display:none` on mobile (it still downloads), and `user-scalable=no`.

**Questions**
1. What is mobile-first and why use it?
2. Media queries vs container queries: when would you use each? *(Media: page-level layout and user preferences. Container: reusable components placed in varying contexts.)*
3. How do you choose breakpoints? *(Content-based, not by device)*
4. What does `clamp()` do? Fluid typography without media queries?
5. How do you support RTL languages? *(logical properties, `dir="rtl"`, mirrored icons)*
6. How would you make a data table responsive?
7. How do you handle hover on touch devices?
8. How do you reduce layout shift in a responsive layout?
9. Your design works at 375px and 1440px but breaks at 900px. Why? *(device-model breakpoints. Test the continuum and use fluid and intrinsic layout.)*

## 3.2.8 Modern CSS Features
🟡 → 🔴 · **Must-know** (signals currency)

**Custom properties (CSS variables)**
```css
:root { --brand: #1a73e8; --space: 1rem; }
.btn { background: var(--brand); padding: var(--space, .5rem); }  /* fallback value */
.btn.danger { --brand: #d93025; }                                  /* scoped override */
```
- They are **runtime, cascade-aware, and inherited**, unlike Sass variables, which compile away. JS can read and write them (`el.style.setProperty('--x', v)`, `getComputedStyle`), they work in media queries only indirectly (you can't use `var()` inside a media condition), and they're the basis of theming and design tokens.
- `@property` registers typed variables, enabling animation of custom properties (e.g., gradients).

**Selectors and logic**
- **`:has()`**, the "parent selector": `.card:has(img)`, `label:has(input:checked)`, `form:has(:invalid) button { opacity:.5 }`.
- **`:is()`/`:where()`**: grouping, with `:where` at zero specificity.
- **`:not()`, `:focus-visible`, `:focus-within`**, `:user-invalid`, `::marker`, `::selection`, `::placeholder`.
- **Native nesting:**
```css
.card { padding: 1rem;
  & h2 { margin: 0; }
  &:hover { box-shadow: 0 2px 8px rgb(0 0 0/.15); }
  @media (width >= 48rem) { padding: 2rem; } }
```

**Layout and sizing helpers:** `gap`, `aspect-ratio`, `inset`, `min()/max()/clamp()`, `object-fit`, `scroll-snap-type`, `position: sticky`, `contain`, and `content-visibility: auto` (skip rendering of offscreen sections to improve load performance), `text-wrap: balance|pretty` for nicer headings, and `scrollbar-gutter: stable`.

**Color and visuals:** `rgb(0 0 0 / .5)` space-separated syntax, `hsl()`, `color-mix(in srgb, red 40%, white)`, `oklch()` (perceptually uniform), `light-dark()`, `accent-color`, `filter`/`backdrop-filter`, `mix-blend-mode`, `clip-path`, and `@supports`.

**Newer, check support before using in production:** anchor positioning, scroll-driven animations, View Transitions API, `@starting-style` (animate from `display:none`, with `transition-behavior: allow-discrete`), and `field-sizing`. Use progressive enhancement via `@supports` and check **Baseline** status on MDN or caniuse.

## 3.2.9 Transitions, Animations, and Animation Performance
🟡 → 🔴 · **Must-know**

**Techniques**

| Tool | Use for |
|---|---|
| `transition` | State changes (hover, focus, class toggle) between two values |
| `@keyframes` + `animation` | Multi-step, looping, autonomous animation |
| Web Animations API (`el.animate()`) | JS-controlled playback (pause, reverse, finish promises) |
| `requestAnimationFrame` | Custom per-frame logic (canvas, physics, scroll-linked effects) |
| View Transitions API | Animated page or state transitions |
| Libraries | Framer Motion/Motion, GSAP, React Spring, Lottie for complex sequences |

```css
.btn { transition: transform .2s ease, background-color .2s ease; }
.btn:hover { transform: translateY(-2px); }

@keyframes spin { to { transform: rotate(360deg); } }
.spinner { animation: spin 1s linear infinite; }

@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after { animation-duration: .01ms !important; animation-iteration-count: 1 !important; transition-duration: .01ms !important; }
}
```

**Performance, the key interview topic**
- The pipeline: **JS → Style → Layout → Paint → Composite**. Animating a property triggers the work from its stage onward.
  - **Layout-triggering** (expensive): `width`, `height`, `top/left`, `margin`, `padding`, `font-size`
  - **Paint-triggering:** `color`, `background`, `box-shadow`, `border-radius`
  - **Composite-only (cheap, GPU-friendly):** **`transform`** and **`opacity`** (also `filter` in many cases)
- **Rule:** animate `transform` and `opacity`, not `top/left/width/height`. Move with `translate`, resize with `scale`.
- **`will-change: transform`:** a hint to promote a layer *before* animating. Use it sparingly and remove it afterward, since each layer costs memory.
- **FLIP technique** (First, Last, Invert, Play): to animate layout changes cheaply, measure before and after, apply an inverse `transform`, then transition it to none.
- **Avoid layout thrashing:** interleaving DOM reads (`offsetHeight`) and writes in a loop forces repeated synchronous layouts. Batch reads, then writes.
- **Timing:** about 100-300ms for UI feedback. Use easing (`ease-out` for entering, `ease-in` for leaving), and keep motion purposeful.
- **Accessibility:** respect `prefers-reduced-motion`, avoid flashing (more than 3 flashes per second), and provide pause controls for autoplay content longer than 5 seconds.
- **60fps budget:** about 16.7ms per frame (and about 8.3ms for 120Hz).
- **Debug:** DevTools Performance panel (frames and long tasks), Rendering panel → Paint flashing, Layer borders, and Layers.

**Questions**
1. Transition vs animation?
2. Which CSS properties are cheap to animate, and why? *(Composite-only: `transform` and `opacity`, which skip layout and paint and run on the compositor thread.)*
3. Why is animating `left` worse than `transform: translateX`?
4. What does `will-change` do, and what are the risks?

## 3.2.10 Preprocessors, CSS Modules, and Architecture
🟡 Intermediate · **Must-know**

**Preprocessors (Sass/SCSS, Less, Stylus)**
- **Features:** variables, nesting, mixins, functions, partials, loops/maps, and math. Sass modules use `@use`/`@forward` (the old `@import` is deprecated).
- **Compile-time:** output is plain CSS.
- **Native CSS now covers much of it:** custom properties (runtime), nesting, `color-mix`, `calc()`, and `@layer`.
- **Still useful for:** loops and generated utility classes, complex mixins and functions, legacy codebases (Bootstrap source), and team conventions. **PostCSS** (autoprefixer, nesting polyfills, Tailwind pipeline) is the other commonly used tool, and **Lightning CSS** is the fast modern alternative.
```scss
@use 'sass:map';
$breakpoints: (sm: 40rem, md: 48rem, lg: 64rem);
@mixin up($bp) { @media (min-width: map.get($breakpoints, $bp)) { @content; } }
.card { padding: 1rem; @include up(md) { padding: 2rem; } &__title { font-weight: 600; } }
```

**CSS Modules**
- Each `.module.css` file is **locally scoped**: class names are transformed (hashed) at build time, e.g. `.title` → `Card_title__x7Gh2`. No collisions, and dependencies are explicit via imports.
```css
/* Card.module.css */
.card { padding: 1rem; }
.title { font-weight: 600; }
.title.active { color: var(--brand); }
```
```jsx
import styles from './Card.module.css';
export const Card = ({ active }) =>
  <div className={styles.card}><h2 className={`${styles.title} ${active ? styles.active : ''}`}>…</h2></div>;
```
- **Pros:** zero runtime cost, real CSS (tooling works), predictable scoping, and it works with Server Components. **Cons:** dynamic styles need CSS variables or conditional classes, global concerns need `:global`, class naming (`composes`) can be awkward, and theming requires variables.

**Naming and architecture methodologies**

| Method | Idea |
|---|---|
| **BEM** | `.block__element--modifier` (`.card__title--large`), flat specificity and explicit naming, but verbose |
| **SMACSS / ITCSS** | Layered organization (settings → tools → generic → elements → objects → components → utilities), going from low to high specificity |
| **OOCSS** | Separate structure from skin, favoring reusable objects |
| **Utility-first** | Compose single-purpose classes (Tailwind) |
| **CUBE CSS** | Composition, Utility, Block, Exception |
| **CSS Modules / CSS-in-JS** | Tool-enforced scoping instead of naming conventions |

**Scaling CSS:** design tokens (variables for color, spacing, type, radii), a reset or normalize layer, `@layer`, component-colocated styles, consistent spacing scale, linting (Stylelint), a dead CSS check (coverage tab), and documented patterns (Storybook).

**Questions**

## 3.2.11 Tailwind CSS and CSS-in-JS: Trade-offs
🟡 Intermediate · **Must-know** ("which would you choose and why?")

**Tailwind (utility-first)**
```html
<button class="rounded-lg bg-blue-600 px-4 py-2 font-medium text-white hover:bg-blue-700
               focus-visible:outline-2 focus-visible:outline-offset-2 md:px-6">
  Save
</button>
```
- **How it works:** it scans your source files for class names at build time and generates only the CSS you use (a small production stylesheet). Variants (`hover:`, `md:`, `dark:`, `group-hover:`) compose. Recent versions (v4) moved configuration into CSS and use a faster engine, and the core mechanics are the same.
- **Pros:** fast iteration, no naming, design-system constraints (spacing and color scale), tiny output, colocated styles, and consistent look.
- **Cons:** noisy markup, a learning curve (memorizing classes), harder to read complex states, dynamic class names must be complete strings (`"bg-" + color` **won't** be detected), and you still need CSS knowledge. Extract components (not `@apply` everywhere) to avoid duplication.

**CSS-in-JS**
- **Runtime libraries (styled-components, Emotion):** styles are authored in JS, scoped, and dynamic via props. **Costs:** runtime style injection overhead, bundle size, and **friction with React Server Components and streaming SSR**, which is why many teams are moving away.
- **Zero-runtime / build-time (vanilla-extract, Panda CSS, Linaria, StyleX):** typed JS or TS authoring that is extracted to static CSS at build time, so there is no runtime cost.

| | CSS Modules | Tailwind | Runtime CSS-in-JS | Zero-runtime CSS-in-JS | BEM + Sass |
|---|---|---|---|---|---|
| Scoping | Build-hashed | Utilities (global but atomic) | Generated names | Generated names | Convention |
| Runtime cost | None | None | Yes | None | None |
| Dynamic styles | Variables/classes | Classes/variables | Easy (props) | Variables/recipes | Classes |
| RSC-friendly | Yes | Yes | Problematic | Yes | Yes |
| Learning curve | Low | Medium | Medium | Medium-high | Low-medium |
| Best for | Component apps wanting real CSS | Fast product teams | Legacy/dynamic theming apps | Typed design systems | Traditional sites |

**Choosing, a good interview answer:** "It depends on team and constraints. For a new React/Next app with a modern setup I'd pick Tailwind for speed and consistency, or CSS Modules if the team prefers authoring real CSS. For a design system consumed by many apps, I'd lean on CSS variables and tokens with zero-runtime styling. I'd avoid runtime CSS-in-JS in new Server Component codebases because of runtime cost and RSC friction. Whichever I pick, the fundamentals of the cascade, layout, and accessibility don't change."

**Questions**
1. Why might a team choose Tailwind? Concerns about it?
2. Why is runtime CSS-in-JS falling out of favor?
3. Why doesn't `` `bg-${color}-500` `` work in Tailwind? *(Static analysis needs complete class names, so use a lookup map or safelist.)*

## 3.2.12 Dark Mode and Theming
🟡 Intermediate · **Good-to-know**

- **Detect the OS preference:** `@media (prefers-color-scheme: dark)`. **Tell the browser** your supported schemes with `color-scheme: light dark` (this styles native controls, scrollbars, and defaults), and `<meta name="color-scheme" content="light dark">`.
- **Token approach (variables):**
```css
:root { color-scheme: light dark;
        --bg: #fff; --fg: #111; --surface: #f5f5f5; --brand: #1a73e8; }
@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) { --bg:#0f1115; --fg:#e8eaed; --surface:#1a1d23; --brand:#8ab4f8; } }
[data-theme="dark"]  { --bg:#0f1115; --fg:#e8eaed; --surface:#1a1d23; --brand:#8ab4f8; }
body { background: var(--bg); color: var(--fg); }
/* or: color: light-dark(#111, #e8eaed);  (modern browsers) */
```
- **User toggle:** three states (system, light, dark), saved in `localStorage` and applied as `data-theme` on `<html>`.
- **Avoid the flash of wrong theme (FOUC):** apply the stored theme in an **inline `<script>` in `<head>`** before first paint, because waiting for React hydration flashes light mode. (Next.js: `next-themes` handles it, with `suppressHydrationWarning` on `<html>`.)
- **Design details:** don't just invert colors. Use dark gray rather than pure black (`#000` on white text causes halation), reduce saturation, re-check contrast ratios, lower image brightness or provide dark variants, and elevate surfaces with lighter tones rather than shadows.
- **Images and SVG:** use `currentColor`, or `<picture>` with `media="(prefers-color-scheme: dark)"`.
- **Related preferences:** `prefers-contrast`, `forced-colors` (Windows High Contrast, so don't rely on backgrounds for meaning, and use `outline` over `box-shadow` for focus).

**Questions:** How do you implement dark mode with a user toggle and system default? Why does the page flash light on load and how do you fix it? What does `color-scheme` do? How do you structure tokens for multi-theme (brand A/B) support?

## 3.2.13 CSS Performance and Debugging
🟡 → 🔴 · **Good-to-know**

**Performance**
- **CSS is render-blocking:** the browser won't paint until the CSSOM is built. Keep critical CSS small (inline above-the-fold CSS), defer non-critical CSS, remove unused CSS, and minify.
- **Selector cost rarely matters** in modern browsers. Avoid micro-optimizing selectors, and focus on payload size, render-blocking, layout cost, and paint cost.
- **Layout cost:** large DOMs, expensive selectors with `:has()` on huge trees (rare), forced synchronous layout in JS, and `content-visibility: auto` for long pages.
- **Fonts:** `font-display: swap|optional`, preload key WOFF2, subset fonts, use variable fonts, and match fallback metrics (`size-adjust`) to reduce CLS.
- **Paint cost:** large blurs and shadows, `backdrop-filter`, and big `filter` effects are expensive.
- **`contain`** (`layout`, `paint`, `size`, `content`) isolates subtrees so changes inside don't invalidate the whole page.

**Debugging playbook**
1. Inspect the element → Styles panel for struck-out rules and the winning rule → Computed tab for the final value and where it comes from.
2. **Layout:** toggle Flex/Grid overlays, check the box model diagram, and look for unexpected `min-width: auto`, margin collapse, or a missing positioned parent.
3. **Overflow:** run `* { outline: 1px solid red }` to find what causes horizontal scroll (usually a fixed width or 100vw plus a scrollbar).
4. **Not applying:** is the selector matching (check the Elements tab)? Is the property valid (a yellow warning icon appears)? Is it inherited vs non-inherited? Is it overridden? Is there a typo?
5. **Mobile only:** device emulation, `dvh` vs `vh`, hover states, and safe areas.
6. **z-index problems:** find the stacking contexts (the Layers panel or inspect ancestors).
7. **Rendering panel:** paint flashing, layout-shift regions, and prefers-* emulation.

**Questions**
1. How do you reduce render-blocking CSS?
2. What's critical CSS?
3. How do you find the element causing horizontal scroll?
4. How do you avoid layout shift from web fonts?
5. A 40KB stylesheet vs 400KB: what do you do? *(split by route, purge unused with coverage, and the utility or atomic approach)*

# 3.3.1 Variables, Hoisting, and the TDZ
🟢 Beginner → 🟡 · **Must-know** · Prerequisites: 2.4.1

**Why interviewers ask:** It's the standard opener. Answers reveal whether you understand the creation phase of execution contexts.

| | `var` | `let` | `const` |
|---|---|---|---|
| Scope | Function (or global) | Block | Block |
| Hoisted? | Yes, initialized to `undefined` | Yes, but **uninitialized** (TDZ) | Yes, but uninitialized (TDZ) |
| Redeclare in same scope | Allowed | SyntaxError | SyntaxError |
| Reassign | Yes | Yes | No (binding is fixed, the object is still mutable) |
| Global object property (script scope) | Yes (`window.x`) | No | No |
| Per-iteration binding in `for` loops | No (one shared binding) | Yes | Yes (but can't increment it) |

**Hoisting, precisely:** declarations are processed during the *creation phase*, before any code runs.
- **`var`:** the binding is created and initialized to `undefined`, and the assignment stays where you wrote it.
- **Function declarations:** the binding is created and initialized to the *whole function*. They're the most hoisted, and they win over a `var` of the same name until reassigned.
- **`let`/`const`/`class`:** the binding exists in scope from the start of the block but is **uninitialized**. Touching it before the declaration line throws `ReferenceError`. That span is the **Temporal Dead Zone (TDZ)**. This proves they *are* hoisted. If they weren't, an outer variable of the same name would be read instead, and it isn't:
```js
let x = 'outer';
{
  console.log(x);   // ReferenceError (the inner x shadows it, but is in TDZ)
  let x = 'inner';
}
```
- **Function expressions and arrows** follow their variable's rules: `var f = () => {}` hoists `f` as `undefined`, so calling it early gives `TypeError: f is not a function`.
- **`typeof` isn't safe in the TDZ:** `typeof undeclared` is `'undefined'`, but `typeof tdzVar` throws.
- **Default parameters** have their own TDZ: `function f(a = b, b) {}` throws when called as `f()`.

**Best practice:** default to `const`, use `let` when you reassign, never use `var`. Turn on ESLint's `prefer-const` and `no-var`.

**Questions**
1. `var` vs `let` vs `const`?
2. What is hoisting? Are `let` and `const` hoisted? *(model below)*
3. What is the Temporal Dead Zone?
4. Is `const` immutable? How would you make an object truly immutable? *(`Object.freeze` is shallow, so use a recursive freeze or Immer)*
5. Why does `var` in a loop with `setTimeout` print the same value? *(see 3.3.3)*
6. What's the difference between `undefined` and "not defined"? *(`undefined` is a value, "not defined" is a ReferenceError for an undeclared identifier)*
7. What happens when a function declaration and a `var` share a name?

**Model answer, Q2:** "Hoisting means the engine registers declarations when it creates the execution context, before running code. `var` is hoisted and initialized to `undefined`. Function declarations are hoisted with their full body. `let`, `const`, and `class` are hoisted too, meaning the name is reserved in the block, but they stay uninitialized until the declaration executes. Accessing them early throws a ReferenceError, and the window between block start and declaration is the TDZ."

**Mistakes:** saying "let/const aren't hoisted"; thinking `const` makes objects immutable; relying on function hoisting for readability.

**Mini task:** write 6 snippets that each demonstrate a different hoisting outcome (`undefined`, ReferenceError, TypeError, working call, shadowing in TDZ, `typeof` in TDZ), and predict each before running.

# 3.3.2 Execution Context, Call Stack, and Scope Chain
🟡 Intermediate · **Must-know**

**Definition:** An *execution context* is the environment in which code is evaluated. The *call stack* tracks active contexts. The *scope chain* is how identifiers are resolved by walking outward through lexical environments.

**Key concepts**
- **Types:** global (created once, `this` = global object or `undefined` in modules), function (one per call), and eval (avoid).
- **Two phases per context:**
  1. **Creation:** build the environment (variable and function bindings, hoisting), determine `this`, and link the outer environment reference.
  2. **Execution:** run line by line and assign values.
- **Lexical environment** = an *environment record* (identifier → value map) + a reference to the *outer* environment. A function's outer reference is fixed **where the function is defined**, not where it's called. That is **lexical (static) scoping**.
- **Scope chain lookup:** resolve a name in the current environment, then its outer, and so on to global. If not found, a `ReferenceError` is thrown (or, in sloppy mode, an assignment creates an accidental global, one more reason to use strict mode and modules).
- **Scopes:** global, module, function, block (`let`/`const`/`class` inside `{}`), and catch-clause scope.
- **Shadowing:** an inner binding hides an outer one with the same name.
- **Call stack:** LIFO. `main()` → `a()` → `b()`. Each call pushes a frame and each return pops one. Exceeding the limit throws `RangeError: Maximum call stack size exceeded`. Async callbacks run later on an **empty** stack, which is why stack traces from async code can lose context.
- **Global object:** `globalThis` is the portable name (`window`, `self`, or `global`). Top-level `var` in a classic script becomes a property of it, but not in ES modules or Node CommonJS modules (which are function-wrapped).
- **Strict mode** (`'use strict'`, automatic in modules and classes): no accidental globals, `this` is `undefined` in plain function calls, duplicate parameter names are errors, and assigning to read-only properties throws.
- **Dynamic scoping contrast:** JS `this` behaves dynamically (depends on the call site), but variable lookup is lexical. Interviewers love this contrast.

```js
const a = 'global';
function outer() {
  const b = 'outer';
  function inner() {
    const c = 'inner';
    console.log(a, b, c);   // found via scope chain: inner → outer → global
  }
  return inner;
}
outer()();        // 'global outer inner'

function whereDefined() { return a; }
function caller() { const a = 'local'; return whereDefined(); }
caller();         // 'global': lexical scoping, not the caller's scope
```

**Questions**
1. What is an execution context? What are its phases?
2. What is the scope chain? Lexical vs dynamic scope?
3. What's the difference between scope and context? *(Scope = variable visibility and is lexical. Context = the value of `this`, determined at call time.)*
4. How does the call stack work? What is a stack overflow?
5. What is the global object? What's `globalThis`?
6. What does strict mode change?
7. What is shadowing? Is it a problem? *(Legal, but it can hide bugs. Linters can warn with `no-shadow`.)*
8. Why is the call stack empty when a `setTimeout` callback runs?

# 3.3.3 Closures
🟡 Intermediate · **Must-know** (almost guaranteed)

**Definition:** A closure is a function bundled with references to the lexical environment where it was created, so it keeps access to those variables even after the outer function has returned.

**Why interviewers ask:** Closures underpin callbacks, modules, memoization, React hooks, and event handlers. They also explain the most famous JS gotchas.

**Key concepts**
- Every function in JS forms a closure. It becomes *interesting* when the function outlives its creator.
- Closures capture **variables (bindings), not values**. A closure sees later changes to the variable.
- **Uses:** private state and encapsulation, function factories and partial application, memoization and caching, once/debounce/throttle, the module pattern (IIFE), event handlers and callbacks, and iterators/generators.
- **Memory:** captured variables stay alive as long as the closure is reachable. A closure capturing a large object keeps all of it alive, so null out references or restructure when that matters.
- **React tie-in:** a **stale closure** happens when an effect or callback captures old state or props. Fixes are correct dependency arrays, functional updates (`setN(n => n + 1)`), and refs for latest-value access (Phase 4).

```js
// Private state
function createCounter() {
  let count = 0;                                  // not accessible from outside
  return { inc: () => ++count, get: () => count };
}
const c = createCounter(); c.inc(); c.inc(); c.get();   // 2

// Function factory
const multiplier = factor => n => n * factor;
const double = multiplier(2);

// Classic loop bug
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i), 0);   // 3 3 3 (one shared i)
for (let i = 0; i < 3; i++) setTimeout(() => console.log(i), 0);   // 0 1 2 (new binding per iteration)
for (var j = 0; j < 3; j++) ((k) => setTimeout(() => console.log(k), 0))(j);  // 0 1 2 (IIFE copies the value)

// Stale closure (React-style)
function makeLogger() {
  let msg = 'a';
  const log = () => console.log(msg);
  msg = 'b';
  return log;
}
makeLogger()();   // 'b': captured the variable, not the value 'a'
```

**Questions**
1. What is a closure? Give a practical example. *(model below)*
2. Why does the `var` loop print 3 3 3? Three ways to fix? *(`let`, an IIFE, or passing the value via `bind` or a parameter)*
3. How do you create private variables in JS? *(closures, `#private` fields, `WeakMap`, and the underscore convention only as a hint)*
4. Can closures cause memory leaks? How? *(long-lived listeners or caches holding large captured scopes)*
5. What's a stale closure in React and how do you fix it?
6. Implement `once(fn)` and `memoize(fn)`. *(3.3.17)*
7. What's the module pattern? How did ES modules replace it?
8. Do closures capture by value or by reference? *(Bindings, i.e. by reference to the variable.)*

**Model answer, Q1:** "A closure is a function plus the lexical environment it was defined in, so it can read and write the outer function's variables after that function has returned. For example, `createCounter` returns `inc` and `get`. Both close over `count`. Nothing else can touch `count`, so it's private state with no class needed. It's how callbacks remember context, how memoize keeps its cache, and why React hooks can hold state between renders."

**Mistakes:** saying "a closure is a function inside a function" (incomplete); thinking closures copy values; creating closures in hot loops without considering memory.

# 3.3.4 `this` Binding
🟡 Intermediate · **Must-know**

**Definition:** `this` is determined by *how a function is called*, not where it's defined (except arrow functions, which capture it lexically).

**The five rules, in order of precedence**
1. **`new` binding:** `new Foo()` makes `this` the newly created object.
2. **Explicit binding:** `fn.call(obj)`, `fn.apply(obj, [args])`, `fn.bind(obj)` (a bound function can't be re-bound, except by `new`).
3. **Implicit binding:** `obj.method()` makes `this` the object left of the dot at call time.
4. **Default binding:** a plain `fn()` call gives `this` as the global object in sloppy mode, or `undefined` in strict mode, modules, and classes.
5. **Arrow functions:** no own `this`. They use the enclosing scope's `this` at *definition*, and `call`/`bind` can't change it.

**Details**
- **Losing `this`:** extracting a method (`const f = obj.method; f()`) or passing it as a callback (`setTimeout(obj.method)`, `arr.map(obj.method)`) drops implicit binding. Fix with `bind`, an arrow wrapper, or class-field arrows.
- **DOM event handlers:** a regular function gets `this === event.currentTarget`. Arrows don't.
- **`call` vs `apply` vs `bind`:** `call(ctx, a, b)` invokes now, `apply(ctx, [a, b])` invokes now with an array, and `bind(ctx, a)` returns a new function (supports partial application).
- **Arrows aren't suitable** as object methods needing `this`, as constructors (no `new`), as prototype methods, or when you need `arguments`.
- **Class fields with arrows** (`handle = () => {...}`) bind per instance, which is convenient for React class components but costs memory per instance and prevents prototype-level overriding.
- **`this` in nested functions:** a regular function nested inside a method has default binding, which is a classic bug. Use an arrow or `bind`.
- **In modules:** top-level `this` is `undefined`. In CommonJS it's `module.exports`.

```js
const user = {
  name: 'Ada',
  regular() { return this?.name; },
  arrow: () => this?.name,                 // `this` of the enclosing module scope, not user
  later() { return [1].map(() => this.name); },        // arrow keeps method's `this`
  laterBroken() { return [1].map(function () { return this?.name; }); } // default binding
};
user.regular();               // 'Ada'
const f = user.regular; f();  // undefined (strict: `this` is undefined, hence `?.`)
user.arrow();                 // undefined
user.later();                 // ['Ada']
user.laterBroken();           // [undefined]
user.regular.call({ name: 'Bob' });   // 'Bob'

function Person(n) { this.n = n; }
const bound = Person.bind({ n: 'ignored' });
new bound('Eve').n;           // 'Eve': `new` beats bind
```

**Questions**
1. How is `this` determined? List the rules and their precedence. *(model below)*
2. `call` vs `apply` vs `bind`?
3. Why do arrow functions not have their own `this`? When should you not use them?
4. What's the output of `const f = obj.method; f()`? Why?
5. How does `this` work in event handlers? In classes? In `setTimeout`?
6. How would you fix `this` being lost in a React class component's handler? *(bind in the constructor, class-field arrow, or arrow in JSX with performance caveats)*
7. What does `new` do step by step? *(Create an object with `Ctor.prototype` as its prototype, call the constructor with `this` bound to it, and return the object unless the constructor returns another object.)*
8. Can you `bind` an arrow function? *(You can call it, but `this` doesn't change.)*

**Model answer, Q1:** "`this` is set at call time. If the call uses `new`, it's the new object. Otherwise, if the function was created with `bind` or invoked via `call`/`apply`, it's the specified object. Otherwise, if it's called as `obj.fn()`, it's `obj`. Otherwise it's the global object in sloppy mode or `undefined` in strict mode. Arrow functions are the exception: they don't get their own `this`, they use the one from where they were defined, so none of the other rules apply to them."

**Mistakes:** assuming `this` is where the function was *written*; using arrows for object methods; forgetting that callbacks lose their receiver.

# 3.3.5 Prototypes, Inheritance, and Classes
🟡 → 🔴 · **Must-know**

**Definition:** Every object has an internal `[[Prototype]]` link to another object (or `null`). Property lookup walks this *prototype chain*. Inheritance in JS is delegation along this chain.

**Key concepts**
- **`obj.__proto__`** (legacy accessor) = `Object.getPrototypeOf(obj)`. **`Fn.prototype`** is a property on *functions*: the object that becomes the `[[Prototype]]` of instances created with `new Fn()`. Mixing these up is the classic mistake.
```
const d = new Dog();
d ──[[Prototype]]──▶ Dog.prototype ──▶ Animal.prototype ──▶ Object.prototype ──▶ null
```
- **Lookup:** read `d.speak` → own properties → each prototype upward → `undefined`. **Writes** create *own* properties (shadowing), except for setters and non-writable inherited properties.
- **`Object.create(proto)`** builds an object with that prototype. `Object.create(null)` gives a dictionary with no prototype (safe from key collisions such as `"toString"` and from prototype pollution).
- **Own vs inherited:** `Object.hasOwn(obj, 'k')` (modern, instead of `obj.hasOwnProperty`), `Object.keys` (own enumerable), `for...in` (own and inherited enumerable, so filter or avoid).
- **Constructor functions:**
```js
function Animal(name) { this.name = name; }
Animal.prototype.speak = function () { return `${this.name} makes a sound`; };

function Dog(name) { Animal.call(this, name); }                  // super constructor
Dog.prototype = Object.create(Animal.prototype);                  // link chain
Dog.prototype.constructor = Dog;                                  // repair constructor
Dog.prototype.speak = function () { return `${this.name} barks`; };
```
- **ES6 classes are syntactic sugar over this**, with differences: `class` declarations have TDZ, class bodies are strict, methods are non-enumerable, calling a class without `new` throws, and `extends` also links the *constructors* (`Dog.__proto__ === Animal`) so statics inherit.
```js
class Animal {
  #energy = 10;                          // private field (truly private)
  static count = 0;                      // static field
  constructor(name) { this.name = name; Animal.count++; }
  speak() { return `${this.name} makes a sound`; }
  get energy() { return this.#energy; }
  static create(n) { return new this(n); }
}
class Dog extends Animal {
  constructor(name) { super(name); }     // must call super before using `this`
  speak() { return `${super.speak()}, barks`; }
}
```
- **Methods live on the prototype (shared)**, while class-field arrow functions live on each instance (not shared).
- **`instanceof`** checks whether `Ctor.prototype` appears in the object's chain. `isPrototypeOf` is similar. Customize it with `Symbol.hasInstance`. It can fail across realms (iframes), so prefer `Array.isArray`.
- **Inheritance vs composition:** deep hierarchies are brittle ("gorilla/banana problem"). Prefer small factories, mixins, and composition: `const canFly = s => ({ fly: () => ... })`.
- **Performance:** engines optimize objects with stable "shapes" (hidden classes). Adding properties in different orders or deleting them can degrade inline caches. Initialize all fields in the constructor in the same order.
- **Prototype pollution (security):** `obj.__proto__.isAdmin = true` or a malicious merge of `{"__proto__": {...}}` can alter *all* objects. Defenses: validate keys, use `Object.create(null)` or `Map`, `Object.freeze(Object.prototype)` in hardened environments, and keep merge libraries patched (Phase 7).
- **Property enumeration order:** integer-like keys ascending, then string keys in insertion order, then symbols.
- **Mixins:** `const Serializable = Base => class extends Base { toJSON() {…} }`.

**Questions**
1. Explain the prototype chain. What's the difference between `__proto__` and `prototype`? *(model below)*
2. How does inheritance work without classes? Show with `Object.create`.
3. Are ES6 classes "real" classes? What differs from Java? *(Sugar over prototypes. No static typing and no true multiple inheritance. Private fields are the exception, being truly private.)*
4. What does `new` do? Implement it.
5. What does `super` do in constructors and methods?
6. How do you check if a property is own or inherited?
7. `Object.create(null)` use cases?
8. Class method vs arrow class field: trade-offs?
9. Composition vs inheritance: how do you choose?
10. What is prototype pollution and how do you prevent it?
11. What's `Object.setPrototypeOf` and why is it discouraged? *(It deoptimizes performance.)*
12. How can you extend built-ins like `Array` or `Error`? *(`class MyErr extends Error` works natively, set `name`, and use `Error.captureStackTrace` in V8)*

**Model answer, Q1:** "Every object has a hidden link to a prototype object, and property reads walk that chain until found or until `null`. `prototype` is a property on constructor *functions*. When you call `new Fn()`, the new object's `[[Prototype]]` is set to `Fn.prototype`. `__proto__` (or `Object.getPrototypeOf`) is how you read an object's actual link. So `dog.__proto__ === Dog.prototype`. Methods put on the prototype are shared by all instances, which is memory-efficient, and `class` is just nicer syntax for that."

**Mistakes:** confusing `prototype` and `__proto__`; putting mutable arrays or objects on the prototype (shared across instances); arrow functions as prototype methods; forgetting `super()` before `this`.

# 3.3.6 The Event Loop: Tasks and Microtasks
🔴 Advanced · **Must-know** (guaranteed at most companies)

**Definition:** The mechanism that lets single-threaded JavaScript handle asynchronous work by queuing callbacks and running them when the call stack is empty.

**The model**
```
          ┌───────────────┐   Web APIs / OS / libuv (timers, network, I/O, DOM events)
          │  Call Stack   │ ◀──────────────────────────────┐
          └──────┬────────┘                                │ completed work enqueues callbacks
                 │ empty?                                  │
     ┌───────────▼────────────┐   ┌─────────────────┐     │
     │ 1. Run ONE macrotask   │──▶│ 2. Drain ALL    │─────┘
     │   (script, timer, I/O, │   │   microtasks    │
     │    UI event, message)  │   │   (promises,    │
     └────────────────────────┘   │   queueMicrotask)│
                 ▲                └────────┬────────┘
                 │                         ▼
                 │          3. (Browser) maybe RENDER: rAF callbacks → style → layout → paint
                 └─────────────────────────┘ repeat
```

**Rules**
- **Macrotasks (tasks):** the initial script, `setTimeout`/`setInterval`, UI/DOM events, network callbacks, `MessageChannel`, and `setImmediate` (Node).
- **Microtasks:** Promise reactions (`.then/.catch/.finally`, and the continuation after `await`), `queueMicrotask`, and `MutationObserver`.
- After each macrotask, the engine runs **all** microtasks until the queue is empty, *including newly added ones*, before the next macrotask or a render.
- **Consequences**
  - A promise callback always runs **before** a `setTimeout(0)` callback scheduled in the same turn.
  - **Microtask starvation:** an endless chain of microtasks blocks rendering and timers.
  - **Long tasks (over 50ms)** block input and rendering. That is jank, and INP suffers.
- **`setTimeout(fn, 0)` isn't immediate:** it's the *minimum* delay. Browsers clamp nested timers to about 4ms after 5 levels, throttle background tabs, and the callback only runs when the stack is free. Timer drift is normal.
- **Rendering:** the browser may render between tasks (typically at display refresh rate). `requestAnimationFrame` callbacks run right before paint, so use them for visual updates.
- **Breaking up long work:** chunk with `setTimeout` or `scheduler.postTask`/`scheduler.yield()` (where supported), `requestIdleCallback` for low-priority work, Web Workers for CPU-heavy work, and virtualization to reduce DOM work.

**Node.js event loop (libuv) phases**
```
┌─▶ timers (setTimeout/setInterval callbacks)
│   pending callbacks (some system errors)
│   idle, prepare (internal)
│   poll (retrieve new I/O events; run I/O callbacks; may block waiting)
│   check (setImmediate callbacks)
└── close callbacks (socket.on('close'))
```
- Between each callback (Node 11+), Node drains **`process.nextTick` queue first, then promise microtasks**.
- **`setImmediate` vs `setTimeout(0)`:** from the main module the order is non-deterministic (depends on process performance). *Inside an I/O callback*, `setImmediate` always runs first.
- **`process.nextTick` vs `Promise.then`:** in CommonJS, nextTick wins. In **ES modules** the top-level code itself runs inside a promise job, so promise callbacks run *before* nextTick.
- **Blocking the loop:** a sync `for` over millions of items, `JSON.parse` of a huge payload, sync crypto, or a catastrophic regex stalls *all* requests. Fix with `worker_threads`, streaming and chunking, a job queue, or another service.
- **libuv thread pool** (default 4 threads) handles file system, DNS lookup (`dns.lookup`), crypto (`pbkdf2`, `scrypt`), and zlib. Network I/O uses OS async primitives (epoll/kqueue/IOCP), not the pool.

```js

setTimeout(() => console.log('7 timeout'), 0);
Promise.resolve().then(() => console.log('4 promise 1'))
                 .then(() => console.log('6 promise 2'));
queueMicrotask(() => console.log('5 microtask'));

console.log('3 script end');
```

# 3.3.7 Promises
🟡 Intermediate · **Must-know**

**Definition:** An object representing the eventual completion (fulfilled) or failure (rejected) of an async operation, and its resulting value.

**Key concepts**
- **States:** *pending → fulfilled* or *pending → rejected*. A settled promise **never changes** state or value (immutable once settled).
- **`.then(onFulfilled, onRejected)`** returns a **new promise**. The returned value resolves it, a returned *promise/thenable* is adopted (flattened), and a thrown error rejects it. **Callbacks always run asynchronously (as microtasks)**, even on already-resolved promises.
- **`.catch(fn)`** = `.then(undefined, fn)`. **`.finally(fn)`** runs on either outcome, gets no argument, and passes through the original value or error (unless `finally` throws).
- **Chaining and error propagation:** a rejection skips `.then` fulfillment handlers until a rejection handler is found. After `.catch` returns normally, the chain *recovers*.
- **`.then(a, b)` vs `.then(a).catch(b)`:** in the first, `b` won't catch errors thrown in `a`. In the second, it will.
- **Constructor:** `new Promise((resolve, reject) => {...})` runs the executor **synchronously**. Throwing inside it rejects. Only the first `resolve`/`reject` counts.
- **Static helpers**

| Method | Resolves when | Rejects when | Use for |
|---|---|---|---|
| `Promise.all([…])` | All fulfill (results array in input order) | **First** rejection (fail-fast) | Independent tasks that must all succeed |
| `Promise.allSettled` | All settle (`{status, value\|reason}`) | Never | Batch where partial failure is OK |
| `Promise.race` | **First to settle** | First to settle if it rejects | Timeouts |
| `Promise.any` | **First fulfillment** | All reject (`AggregateError`) | Fastest-mirror / fallback |
| `Promise.resolve(v)` / `reject(e)` | Wrap a value or error | | Normalize |
| `Promise.withResolvers()` (ES2024) | Returns `{promise, resolve, reject}` | | Externally controlled promises |

- **Unhandled rejections:** browsers fire `unhandledrejection`, and **Node (v15+) crashes the process by default**. Always handle or `catch`, and log with context.
- **Thenables:** any object with a `.then` method is adopted by `resolve`, which is how libraries interoperate.
- **Anti-patterns**
  - **Explicit construction:** wrapping an existing promise in `new Promise` (`new Promise(res => fetch().then(res))`). Just return the promise.
  - **Forgetting to `return` inside `.then`:** the chain doesn't wait.
  - **Nesting `.then` pyramids** instead of flat chains.
  - **`async` inside `forEach`:** `forEach` ignores returned promises (see 3.3.8).
  - **Swallowing:** `.catch(() => {})` hides bugs.
- **Promisify callbacks:**
```js
const promisify = fn => (...args) =>
  new Promise((resolve, reject) => fn(...args, (err, val) => (err ? reject(err) : resolve(val))));
// Node: util.promisify, fs/promises
```
- **Cancellation:** promises can't be cancelled. Use `AbortController` (supported by `fetch`, many Node APIs, and your own functions) to cancel the underlying work.
```js
const ac = new AbortController();
fetch(url, { signal: ac.signal }).catch(e => { if (e.name !== 'AbortError') throw e; });
ac.abort();
fetch(url, { signal: AbortSignal.timeout(5000) });   // built-in timeout signal
```

```js
Promise.resolve(1)
  .then(v => { throw new Error('boom'); })
  .then(v => console.log('skipped'))
  .catch(e => { console.log('caught', e.message); return 'recovered'; })
  .then(v => console.log(v))          // 'recovered'
  .finally(() => console.log('cleanup'));
```

# 3.3.8 async/await and Concurrency Patterns
🟡 Intermediate · **Must-know**

**Definition:** Syntax over promises. An `async` function always returns a promise, and `await` pauses that function until a promise settles, without blocking the thread.

**Key concepts**
- **Mechanics:** `await x` ≈ `Promise.resolve(x).then(continueFunction)`. Code before the first `await` runs **synchronously**. The continuation is a microtask. A thrown error becomes a rejection, and `return v` resolves with `v`.
- **Error handling:** `try/catch/finally` around `await`. `await` on a rejected promise throws.
- **`return await` inside try/catch:** `return promise` (without await) bypasses the local `catch`, because the function returns before the promise rejects.
```js
async function a() { try { return failing(); }       catch { return 'handled'; } } // NOT handled
async function b() { try { return await failing(); } catch { return 'handled'; } } // handled
```
- **Sequential vs parallel**
```js
// Sequential: ~ t1 + t2 (use when B depends on A)
const user = await getUser(id);
const orders = await getOrders(user.id);

// Parallel: ~ max(t1, t2) (independent work)
const [profile, settings] = await Promise.all([getProfile(id), getSettings(id)]);

// Start early, await later
const pA = getA(); const pB = getB();
const a = await pA; const b = await pB;
```
- **Loops:** `for...of` with `await` is sequential. **`arr.forEach(async x => await …)` does NOT wait**, because `forEach` ignores returned promises, so errors become unhandled rejections and the code after continues early. Use `for...of`, or `await Promise.all(arr.map(async …))` for parallel.
- **Unbounded parallelism is dangerous:** `Promise.all(10000 requests)` can overwhelm APIs, DBs, and sockets. Use a **concurrency limiter** (3.3.17 `mapLimit`, or `p-limit`).
- **Top-level `await`:** allowed in ES modules. It blocks the module's dependents, so avoid it in widely imported modules.
- **Race conditions in async UI code:** a slow earlier request resolving after a later one overwrites newer state (typeahead). Fix by ignoring stale responses (a request id or flag), aborting with `AbortController`, or using TanStack Query (Phase 4).
- **Error aggregation:** `Promise.allSettled` plus filtering rejections.
- **Async iteration:** `for await (const chunk of stream)` for streams and paginated APIs (3.3.12).
- **Event emitters and callbacks in async code:** `events.once(emitter, 'x')` returns a promise.
- **Debugging:** async stack traces are supported in modern DevTools and Node. Name your async functions.

**Questions**

# 3.3.9 Types, Coercion, and Equality
🟡 Intermediate · **Must-know**

**Key concepts**
- **Types:** 7 primitives (`string`, `number`, `bigint`, `boolean`, `undefined`, `null`, `symbol`) and objects. `typeof` returns `'string' | 'number' | 'bigint' | 'boolean' | 'undefined' | 'symbol' | 'function' | 'object'`. Note `typeof null === 'object'` (a historical bug) and arrays are `'object'` (use `Array.isArray`).
- **Primitive wrappers:** `'abc'.length` works because the engine temporarily boxes the primitive. `new String('a')` is an object, and you should avoid it.
- **Implicit coercion rules (the useful subset)**
  - **`+`:** if either operand (after `ToPrimitive`) is a string, concatenate. Otherwise add numerically.
  - **`-`, `*`, `/`, `%`, unary `+`:** convert to number.
  - **ToPrimitive on objects:** `Symbol.toPrimitive` → `valueOf` → `toString` (order flips for string hint). `[] → ''`, `{} → '[object Object]'`, and `Date` prefers string with `+`.
  - **ToNumber:** `''→0`, `' 12 '→12`, `'12px'→NaN`, `null→0`, `undefined→NaN`, `true→1`, `[]→0`, `[5]→5`, `[1,2]→NaN`.
  - **Truthiness:** falsy are `false, 0, -0, 0n, '', null, undefined, NaN`. Everything else is truthy, including `'0'`, `'false'`, `[]`, `{}`, and `new Boolean(false)`.
- **`==` (loose equality), simplified**
  1. Same type: behaves like `===`.
  2. `null == undefined` is true, and they equal *nothing else* (`null == 0` is false).
  3. number vs string: convert the string to a number.
  4. boolean: convert it to a number first (`[] == false` → `[] == 0` → `'' == 0` → `0 == 0` true).
  5. object vs primitive: `ToPrimitive(object)`, then compare.
- **`===`:** no coercion, but `NaN !== NaN`, and `+0 === -0`. **`Object.is`:** `NaN` equals `NaN`, and `+0` differs from `-0`. Use `Number.isNaN`, not global `isNaN` (which coerces).
- **Relational operators:** `null >= 0` is true (null → 0), but `null == 0` is false. Strings compare lexicographically (`'10' < '9'` is true).
- **Parsing:** `Number('12px')` → NaN, `parseInt('12px')` → 12, `parseInt('08')` → 8, `parseFloat('3.14abc')` → 3.14, and `['1','2','3'].map(parseInt)` → `[1, NaN, NaN]` (map passes the index as the radix).
- **Practical guidance:** use `===`, convert explicitly (`Number(x)`, `String(x)`, `Boolean(x)`), use `x == null` only for the "null or undefined" check, and in TypeScript lean on the type system.
- **Sorting:** `[10, 9, 1].sort()` sorts as strings → `[1, 10, 9]`. Always pass a comparator: `.sort((a, b) => a - b)`.
- **Numbers:** `0.1 + 0.2 !== 0.3` (2.6.1), `Number.MAX_SAFE_INTEGER`, `BigInt` doesn't mix with numbers (`1n + 1` throws), `toFixed` returns a string, and `Math.round(-0.5)` is `-0`.

# 3.3.11 Modules: ESM vs CommonJS
🟡 Intermediate · **Must-know**

| | **ES Modules (ESM)** | **CommonJS (CJS)** |
|---|---|---|
| Syntax | `import x from './x.js'`, `export` | `require('./x')`, `module.exports` |
| Loading | **Static** (analyzable at parse time), asynchronous | **Dynamic**, synchronous |
| Bindings | **Live read-only bindings** | **Copies** of exported values (at require time) |
| Tree shaking | Yes (static structure) | Hard |
| Top-level `await` | Yes | No |
| Strict mode | Always | Optional |
| `this` at top level | `undefined` | `module.exports` |
| `__dirname` / `__filename` | Not available (`import.meta.url`, `import.meta.dirname` in newer Node) | Available |
| File extensions | **Required** in Node ESM (`./x.js`) | Optional |
| Conditional/lazy load | `await import('./x.js')` | `require` anywhere |
| Enable in Node | `"type": "module"` in `package.json`, or `.mjs` | Default, or `.cjs` |

**Key concepts**
- **Exports:** named (`export const a`), default (`export default`), re-exports (`export * from`), and namespace imports (`import * as ns`). Prefer **named exports**: they're refactor-friendly, grep-friendly, and tree-shake better.
- **Module singleton:** a module is evaluated **once** and cached, and every importer sees the same instance. That's why a module-level object works as a singleton.
- **Live bindings:** an importer sees updates to an exported `let` (`export let count`). CJS exports copy the value.
- **Circular dependencies:** ESM hoists import bindings, so you may touch an uninitialized binding (TDZ error). CJS returns a *partial* `exports` object. The fix is to restructure (extract shared code), use lazy access inside functions, or use dependency injection.
- **Dynamic `import()`:** returns a promise, and is the basis for **code splitting** (`React.lazy`) and conditional loading.
- **Interop:** ESM can import CJS (default = `module.exports`). CJS cannot `require()` ESM synchronously (newer Node versions are relaxing this, so check yours), and must use `await import()`.
- **`package.json`:** `"exports"` field (the public entry points, conditional for `import`/`require`), `"main"`, `"module"`, `"type"`, and `"sideEffects": false` (helps bundlers tree-shake).
- **Barrel files** (`index.js` that re-exports everything) can hurt tree-shaking and dev startup in large codebases.
- **Browser:** `<script type="module">` is deferred, strict, CORS-fetched, and runs once per URL. Import maps map bare specifiers.

```js
// math.js
export const add = (a, b) => a + b;
export default function multiply(a, b) { return a * b; }
// app.js
import multiply, { add } from './math.js';
const { heavy } = await import('./heavy.js');   // lazy
```

# 3.3.12 Iterators and Generators
🔴 Advanced · **Good-to-know** (asked at mid and senior levels, and it explains async/await and Redux-Saga)

**Key concepts**
- **Iterator protocol:** an object with `next()` returning `{ value, done }`. **Iterable protocol:** an object with `[Symbol.iterator]()` returning an iterator. `for...of`, spread, destructuring, `Array.from`, `Map`, `Set`, and `Promise.all` consume iterables.
- **Generators** (`function*`) are functions that can pause at `yield` and resume. Calling one returns an iterator. They're lazy (values are produced on demand) and can model infinite sequences.
- `yield` can also *receive* values: `const x = yield 1;` (the value passed to `next(v)`). `return()` and `throw()` allow cancellation and error injection. `yield*` delegates to another iterable.
- **Async iterators and generators** (`async function*`, `Symbol.asyncIterator`, `for await...of`): consume streams, paginated APIs, and event sequences.
- **Relation to `async/await`:** `async/await` is essentially a generator-driven coroutine runner over promises (the old `co` library).
- **Use cases:** lazy pipelines, pagination, ID generators, tree traversal, state machines, custom iteration over data structures, and Redux-Saga effects.

```js
class Range {
  constructor(start, end) { this.start = start; this.end = end; }
  *[Symbol.iterator]() { for (let i = this.start; i < this.end; i++) yield i; }
}
[...new Range(0, 5)];   // [0,1,2,3,4]

function* fibonacci() { let [a, b] = [0, 1]; for (;;) { yield a; [a, b] = [b, a + b]; } }
function* take(n, it) { let i = 0; for (const v of it) { if (i++ >= n) return; yield v; } }
[...take(8, fibonacci())];   // [0,1,1,2,3,5,8,13]

async function* paginate(url) {                  // async generator over pages
  let next = url;
  while (next) {
    const res = await fetch(next);
    const { items, nextUrl } = await res.json();
    yield* items;
    next = nextUrl;
  }
}
for await (const item of paginate('/api/items')) { /* process lazily */ }

function* inOrder(node) {                        // tree traversal
  if (!node) return;
  yield* inOrder(node.left); yield node.value; yield* inOrder(node.right);
}
```

# 3.3.13 Proxy, Reflect, Symbols, and Weak Collections
🔴 Advanced · **Good-to-know**

**Proxy and Reflect**
- `new Proxy(target, handler)` intercepts operations: `get`, `set`, `has`, `deleteProperty`, `ownKeys`, `apply`, `construct`, `defineProperty`, and `getPrototypeOf`. **Reflect** has matching methods that perform the default behavior and keep `this` and receiver semantics correct. Forward with `Reflect.get(...arguments)`.
- **Uses:** reactivity (**Vue 3** uses Proxies, whereas Vue 2 used `Object.defineProperty`), validation, default values, logging and tracing, negative array indexes, access control, API clients (`api.users.get()`), and mocking.
- **Limits:** a performance overhead, invariants that can't be violated (e.g., non-configurable properties), identity (`proxy !== target`), private fields don't work through proxies (`#x` throws on a proxy receiver), and internal slots on `Map`/`Date` need bound methods.
```js
const validated = (target) => new Proxy(target, {
  set(obj, prop, value, receiver) {
    if (prop === 'age' && !Number.isInteger(value)) throw new TypeError('age must be an integer');
    return Reflect.set(obj, prop, value, receiver);
  },
  get: (obj, prop, receiver) => (prop in obj ? Reflect.get(obj, prop, receiver) : `no_${String(prop)}`)
});

const negArray = arr => new Proxy(arr, {
  get: (t, p, r) => Reflect.get(t, typeof p === 'string' && /^-\d+$/.test(p) ? t.length + +p : p, r)
});
```

**Symbols**
- Unique, immutable primitives, used as collision-free property keys (`Symbol('id')`). They're skipped by `for...in`, `Object.keys`, and `JSON.stringify` (`Object.getOwnPropertySymbols` reveals them). `Symbol.for('key')` uses a global registry.
- **Well-known symbols** customize language behavior: `Symbol.iterator`, `Symbol.asyncIterator`, `Symbol.toPrimitive`, `Symbol.hasInstance`, `Symbol.toStringTag`.
- Not truly private (reflectable). Use `#private` fields for real privacy.

**WeakMap, WeakSet, WeakRef, FinalizationRegistry**
- **`WeakMap`:** keys must be objects, held **weakly**: if nothing else references the key, the entry can be garbage collected. Not iterable, with no `size`. **Uses:** private data per object, caching computed values keyed by objects (e.g., DOM nodes) without leaks, and metadata.
- **`WeakSet`:** membership tracking of objects (e.g., "already visited" in circular deep-clone).
- **`WeakRef`/`FinalizationRegistry`:** rare, non-deterministic, with no guaranteed timing. Avoid relying on them for logic.
```js
const meta = new WeakMap();
function track(el) { meta.set(el, { clicks: 0 }); }   // entry vanishes when `el` is GC'd
```

# 3.3.14 Copying, Immutability, and Property Descriptors
🟡 Intermediate · **Must-know** (React and Redux depend on it)

**Copying**

| Technique | Depth | Preserves | Notes |
|---|---|---|---|
| `b = a` | None | Same reference | Aliasing |
| `{...a}`, `[...a]`, `Object.assign({}, a)`, `arr.slice()` | **Shallow** | Own enumerable props | Nested objects still shared |
| `structuredClone(a)` | **Deep** | Dates, Maps, Sets, RegExp, typed arrays, circular refs | Throws on functions and DOM nodes, drops prototypes and class identity, ignores getters/setters |
| `JSON.parse(JSON.stringify(a))` | Deep (lossy) | JSON types only | Drops `undefined`/functions/symbols, `NaN`→`null`, Date→string, throws on circular and BigInt |
| Hand-written `deepClone` / lodash `cloneDeep` | Deep | Customizable | See 3.3.17 |

**Immutability**
- **Why:** predictable state, cheap change detection by reference (`prev !== next`), time-travel debugging, and fewer bugs from shared mutation.
- **Immutable update patterns:**
```js
const next = { ...state, user: { ...state.user, name: 'Ada' } };           // nested object
const added = [...list, item];  const removed = list.filter(x => x.id !== id);
const updated = list.map(x => (x.id === id ? { ...x, done: true } : x));
const sorted = list.toSorted(cmp);                                          // non-mutating
```
- **Immer** lets you write "mutating" code on a draft and produces an immutable result with structural sharing (used inside Redux Toolkit).
- **Structural sharing:** unchanged branches are reused by reference, so updates stay cheap.
- **`Object.freeze`** is shallow, and in sloppy mode writes fail silently (in strict mode they throw). `Object.seal` blocks adding and removing, but allows editing. `Object.preventExtensions` blocks adding only. `Object.isFrozen` tests. `as const` in TypeScript is compile-time only.

**Property descriptors**
```js
Object.defineProperty(obj, 'id', { value: 1, writable: false, enumerable: false, configurable: false });
Object.getOwnPropertyDescriptor(obj, 'id');
```
- **Data property:** `value`, `writable`, `enumerable`, `configurable`. **Accessor property:** `get`, `set`, `enumerable`, `configurable`.
- Plain assignment creates properties as writable, enumerable, and configurable. `defineProperty` defaults them to `false`.
- **Getters/setters** enable computed and validated properties without changing the call syntax.

# 3.3.15 Date, Intl, and Regex
🟡 Intermediate · **Good-to-know**

**Date pitfalls**
- Months are **0-indexed** (`new Date(2025, 0, 31)` is January), and `getDay()` is the weekday while `getDate()` is the day of month.
- **Parsing:** `new Date('2025-01-31')` (date-only ISO) is parsed as **UTC**, but `new Date('2025-01-31T00:00:00')` (no offset) is parsed as **local time**. Non-ISO strings are implementation-dependent, so avoid them.
- A `Date` is a UTC timestamp (ms since epoch). **Time zones only matter on display and in calendar math.** `setMonth` overflow rolls over (`Jan 31` + 1 month → `Mar 3`).
- **Best practice:** store and transmit **UTC ISO 8601** (`toISOString()`) or epoch ms, convert at the edge for display, store the user's IANA time zone (`America/New_York`) for scheduling rather than offsets (DST), and never do date math by adding `86400000` across DST.
- **Libraries:** `date-fns`, `Luxon`, `Day.js` (avoid Moment, which is legacy). **`Temporal`** is the modern replacement API (check support and polyfills).
- **Intl** (built in, with no libraries needed):
```js
new Intl.DateTimeFormat('en-GB', { dateStyle: 'medium', timeZone: 'Asia/Kolkata' }).format(date);
new Intl.NumberFormat('de-DE', { style: 'currency', currency: 'EUR' }).format(1234.5);  // "1.234,50 €"
new Intl.RelativeTimeFormat('en', { numeric: 'auto' }).format(-1, 'day');               // "yesterday"
new Intl.PluralRules('en').select(1);                                                   // 'one'
new Intl.ListFormat('en').format(['a', 'b', 'c']);                                      // "a, b, and c"
```
Also `Intl.Collator` for locale-aware sorting (`['ä','z','a'].sort(new Intl.Collator('de').compare)`).

**Regex essentials**
- **Syntax:** character classes `\d \w \s [a-z]`, quantifiers `* + ? {n,m}` (**greedy** by default, lazy with `?`), anchors `^ $ \b`, groups `( )`, **named groups** `(?<year>\d{4})`, non-capturing `(?:…)`, alternation `|`, **lookahead** `(?=…)` `(?!…)`, **lookbehind** `(?<=…)` `(?<!…)`, and backreferences `\1`.
- **Flags:** `g` (global), `i`, `m`, `s` (dot matches newline), `u` (Unicode), `y` (sticky), `d` (indices), and `v` (set notation).
- **API:** `str.match(re)`, `str.matchAll(re)` (iterator with groups, needs `g`), `re.test(str)`, `re.exec(str)`, `str.replace(re, fn|string)`, `replaceAll`, and `split(re)`.
- **Gotcha: a regex with `g` or `y` is stateful** (`lastIndex`). Calling `re.test()` repeatedly on a shared `/x/g` alternates true/false. Avoid `g` with `test`, or reset `lastIndex`.
- **ReDoS:** nested quantifiers like `(a+)+$` or `(.*)*` backtrack exponentially on crafted input, so one request can block the event loop. Avoid ambiguous nested repetition, cap input length, use atomic-style patterns where possible, and use linear-time engines (RE2) for untrusted patterns.
- **Don't parse HTML or validate emails with regex.** Use a parser (or `type=email` plus verification).

```js
const m = '2025-01-31'.match(/(?<y>\d{4})-(?<m>\d{2})-(?<d>\d{2})/);
m.groups.y;                                        // '2025'
'a-b_c'.replace(/[-_](\w)/g, (_, c) => c.toUpperCase());   // 'aBC' (camelCase)
const re = /\d/g; re.test('1'); re.test('1');      // true, false!
```

# 3.3.16 Memory and Garbage Collection (JS view)
🔴 Advanced · **Good-to-know** (cross-ref 2.6.2)

- **Reachability:** a value is retained if it's reachable from a root (globals, the current stack, active closures, timers, event listeners). V8 uses generational, incremental, and concurrent mark-and-sweep GC.
- **Typical JS leaks and fixes**

| Leak | Fix |
|---|---|
| Event listeners never removed | `removeEventListener`, `AbortController` signal, cleanup in effects |
| `setInterval` never cleared | `clearInterval` on teardown |
| Closures capturing big objects | Narrow captured scope, null references |
| Unbounded caches and globals | LRU with a max size, TTL, `WeakMap` |
| Detached DOM nodes held in JS | Drop references on removal |
| Node: per-request data in module-level arrays, unbounded queues, uncleared listeners (`MaxListenersExceededWarning`) | Bounded structures, backpressure, cleanup |
- **Tooling:** DevTools Memory (heap snapshot diff, allocation timeline), Performance monitor, Node `--inspect` plus heap snapshots, `process.memoryUsage()`, `--heap-prof`, and `clinic heapprofiler`.
- **GC pauses:** allocate less in hot paths, reuse objects and buffers, and avoid creating closures per frame in animation loops.

# 3.3.17 MUST-IMPLEMENT-FROM-SCRATCH (22 Problems)

**How to practice:** write each from memory, then test it against edge cases. In an interview, state assumptions, handle the main edge cases, and mention what you left out.

### 1. `call`, `apply`, `bind`
```js
Function.prototype.myCall = function (ctx, ...args) {
  ctx = ctx == null ? globalThis : Object(ctx);
  const key = Symbol('fn');
  ctx[key] = this;
  try { return ctx[key](...args); } finally { delete ctx[key]; }
};
Function.prototype.myApply = function (ctx, args = []) { return this.myCall(ctx, ...args); };

Function.prototype.myBind = function (ctx, ...preset) {
  const fn = this;
  if (typeof fn !== 'function') throw new TypeError('Bind must be called on a function');
  function bound(...args) {
    // when used with `new`, `this` is the new instance and ctx is ignored
    return fn.apply(new.target ? this : ctx, [...preset, ...args]);
  }
  if (fn.prototype) bound.prototype = Object.create(fn.prototype);
  return bound;
};
```
*Edge cases:* primitives as `this` (boxed), `new` on bound functions, preset args, a Symbol key to avoid collisions.

### 3. Minimal Promise (A+-style core)
```js
class MyPromise {
  #state = 'pending'; #value; #callbacks = [];

  constructor(executor) {
    let called = false;
    const resolve = v => { if (called) return; called = true; this.#resolve(v); };
    const reject  = e => { if (called) return; called = true; this.#settle('rejected', e); };
    try { executor(resolve, reject); } catch (e) { reject(e); }
  }

  #resolve(x) {
    if (x === this) return this.#settle('rejected', new TypeError('Chaining cycle detected'));
    if (x !== null && (typeof x === 'object' || typeof x === 'function')) {
      let then;
      try { then = x.then; } catch (e) { return this.#settle('rejected', e); }
      if (typeof then === 'function') {            // adopt thenables
        let done = false;
        try {
          then.call(x,
            y => { if (!done) { done = true; this.#resolve(y); } },
            r => { if (!done) { done = true; this.#settle('rejected', r); } });
        } catch (e) { if (!done) { done = true; this.#settle('rejected', e); } }
        return;
      }
    }
    this.#settle('fulfilled', x);
  }

  #settle(state, value) {
    if (this.#state !== 'pending') return;
    this.#state = state; this.#value = value;
    for (const cb of this.#callbacks) queueMicrotask(cb);
    this.#callbacks = [];
  }

  then(onFulfilled, onRejected) {
    return new MyPromise((resolve, reject) => {
      const run = () => {
        const ok = this.#state === 'fulfilled';
        const handler = ok ? onFulfilled : onRejected;
        if (typeof handler !== 'function') return ok ? resolve(this.#value) : reject(this.#value);
        try { resolve(handler(this.#value)); } catch (e) { reject(e); }
      };
      if (this.#state === 'pending') this.#callbacks.push(run);
      else queueMicrotask(run);
    });
  }
  catch(onRejected) { return this.then(undefined, onRejected); }
  finally(fn) {
    return this.then(
      v => MyPromise.resolve(fn()).then(() => v),
      e => MyPromise.resolve(fn()).then(() => { throw e; }));
  }
  static resolve(v) { return v instanceof MyPromise ? v : new MyPromise(r => r(v)); }
  static reject(e) { return new MyPromise((_, rej) => rej(e)); }
}
```
*Talking points:* state immutability, async callbacks via microtasks, chaining returns a new promise, thenable adoption, and the "resolve once" guard.

### 4. `Promise.all`, `allSettled`, `race`, `any`
```js
const all = iterable => new Promise((resolve, reject) => {
  const items = [...iterable];
  if (!items.length) return resolve([]);
  const out = new Array(items.length); let left = items.length;
  items.forEach((p, i) => Promise.resolve(p).then(v => { out[i] = v; if (--left === 0) resolve(out); }, reject));
});

const allSettled = iterable => all([...iterable].map(p =>
  Promise.resolve(p).then(value => ({ status: 'fulfilled', value }),
                          reason => ({ status: 'rejected', reason }))));

const race = iterable => new Promise((resolve, reject) =>
  [...iterable].forEach(p => Promise.resolve(p).then(resolve, reject)));

const any = iterable => new Promise((resolve, reject) => {
  const items = [...iterable]; const errors = new Array(items.length); let left = items.length;
  if (!left) return reject(new AggregateError([], 'All promises were rejected'));
  items.forEach((p, i) => Promise.resolve(p).then(resolve, e => {
    errors[i] = e;
    if (--left === 0) reject(new AggregateError(errors, 'All promises were rejected'));
  }));

```
*Edge cases:* empty input, non-promise values, preserving result order (index, not completion order).

### 5. `debounce` (leading/trailing, cancel)
```js
function debounce(fn, wait = 0, { leading = false, trailing = true } = {}) {
  let timer, lastArgs, lastThis, result;
  const invoke = () => { const a = lastArgs, t = lastThis; lastArgs = lastThis = undefined; result = fn.apply(t, a); return result; };
  function debounced(...args) {
    lastArgs = args; lastThis = this;
    const callNow = leading && !timer;
    clearTimeout(timer);
    timer = setTimeout(() => { timer = undefined; if (trailing && lastArgs) invoke(); }, wait);
    if (callNow) invoke();
    return result;
  }
  debounced.cancel = () => { clearTimeout(timer); timer = undefined; lastArgs = lastThis = undefined; };
  debounced.flush = () => { if (timer) { clearTimeout(timer); timer = undefined; if (lastArgs) return invoke(); } return result; };
  return debounced;
}
```
*Use:* search-as-you-type, resize, autosave (wait for a pause). In React, keep the debounced function stable with `useRef`/`useMemo`, and cancel on unmount.

### 6. `throttle` (leading and trailing)
```js
function throttle(fn, wait) {
  let last = 0, timer = null, lastArgs, lastThis;
  const run = () => { last = Date.now(); timer = null; const a = lastArgs, t = lastThis; lastArgs = lastThis = undefined; fn.apply(t, a); };
  function throttled(...args) {
    lastArgs = args; lastThis = this;
    const remaining = wait - (Date.now() - last);
    if (remaining <= 0) { clearTimeout(timer); timer = null; run(); }
    else if (!timer) timer = setTimeout(run, remaining);
  }
  throttled.cancel = () => { clearTimeout(timer); timer = null; last = 0; lastArgs = lastThis = undefined; };
  return throttled;
}
```
*Debounce vs throttle:* debounce fires after activity *stops*, and throttle fires at most once per interval *during* activity (scroll position, mousemove, rate-limited API calls).

### 8. `memoize`

```js
function memoize(fn, resolver = (...a) => JSON.stringify(a)) {
```

### 9. `deepClone` (circular-safe)
```js
function deepClone(value, seen = new WeakMap()) {
  if (value === null || typeof value !== 'object') return value;      // primitives and functions by reference
  if (seen.has(value)) return seen.get(value);                        // circular references
  if (value instanceof Date) return new Date(value);
  if (value instanceof RegExp) return new RegExp(value.source, value.flags);
  if (value instanceof Map) {
    const m = new Map(); seen.set(value, m);
    value.forEach((v, k) => m.set(deepClone(k, seen), deepClone(v, seen))); return m;
  }
  if (value instanceof Set) {
    const s = new Set(); seen.set(value, s);
    value.forEach(v => s.add(deepClone(v, seen))); return s;
  }
  const out = Array.isArray(value) ? [] : Object.create(Object.getPrototypeOf(value));
  seen.set(value, out);
  for (const key of Reflect.ownKeys(value)) out[key] = deepClone(value[key], seen);   // includes symbols
  return out;
}
```
*Mention:* `structuredClone` covers most cases. This version ignores property descriptors and non-enumerable properties.

### 10. Event emitter
```js
class EventEmitter {
  #events = new Map();
  on(event, fn) { (this.#events.get(event) ?? this.#events.set(event, []).get(event)).push(fn); return this; }
  off(event, fn) {
    const list = this.#events.get(event); if (!list) return this;
    const i = list.findIndex(l => l === fn || l.original === fn);
    if (i > -1) list.splice(i, 1);
    return this;
  }
  once(event, fn) {
    const wrapper = (...a) => { this.off(event, wrapper); fn.apply(this, a); };
    wrapper.original = fn;
    return this.on(event, wrapper);
  }
  emit(event, ...args) {
    const list = this.#events.get(event);
    if (!list?.length) return false;
    for (const l of [...list]) l.apply(this, args);     // copy: listeners may unsubscribe during emit
    return true;
  }
}
```

```js
Array.prototype.myReduce = function (cb, ...init) {
  let i = 0, acc;
  if (init.length) acc = init[0];
  else {
    while (i < this.length && !(i in this)) i++;                 // find first present element (sparse arrays)
    if (i >= this.length) throw new TypeError('Reduce of empty array with no initial value');
    acc = this[i++];
  }
  for (; i < this.length; i++) if (i in this) acc = cb(acc, this[i], i, this);
  return acc;
};
```

### 15. `retry` with exponential backoff and full jitter
```js
async function retry(fn, { retries = 3, baseMs = 200, factor = 2, shouldRetry = () => true } = {}) {

    try { return await fn(attempt); }
    catch (err) {
```

### 17. LRU cache (O(1) with `Map` insertion order)
```js
class LRUCache {
  #cap; #map = new Map();
  constructor(cap) { this.#cap = cap; }
  get(k) {
    if (!this.#map.has(k)) return undefined;
    const v = this.#map.get(k); this.#map.delete(k); this.#map.set(k, v);   // mark most recent
    return v;
  }
  set(k, v) {
    if (this.#map.has(k)) this.#map.delete(k);
    else if (this.#map.size >= this.#cap) this.#map.delete(this.#map.keys().next().value);  // evict oldest
    this.#map.set(k, v);
  }
}
```

### 19. `deepEqual`
```js
function deepEqual(a, b, seen = new WeakMap()) {
  if (a === b || (a !== a && b !== b)) return true;                  // equal, or both NaN
  if (typeof a !== 'object' || typeof b !== 'object' || !a || !b) return false;
  if (Object.getPrototypeOf(a) !== Object.getPrototypeOf(b)) return false;
  if (a instanceof Date) return a.getTime() === b.getTime();
  if (a instanceof RegExp) return String(a) === String(b);
  if (seen.get(a) === b) return true;                                 // circular
  seen.set(a, b);
  if (a instanceof Map || a instanceof Set) {                         // compare as arrays (order-sensitive simplification)
    return a.size === b.size && deepEqual([...a], [...b], seen);
  }
  const ka = Reflect.ownKeys(a), kb = Reflect.ownKeys(b);
  return ka.length === kb.length && ka.every(k => Object.hasOwn(b, k) && deepEqual(a[k], b[k], seen));
}
```

```js
  add(task) {
```

# 3.4 TYPESCRIPT

## 3.4.1 The Mental Model: What TypeScript Is
🟡 Intermediate · **Must-know** · Prerequisites: JS Core (3.3)

**Definition:** A statically typed superset of JavaScript. A type checker analyzes your code at build time, then the types are **erased**, and plain JavaScript is what runs.

**Why interviewers ask:** Most full stack teams are TypeScript-first. Questions separate people who *annotate* from people who *design with types*.

**Key concepts**
- **Types are erased.** There's no runtime type information. Data from the network, `localStorage`, `JSON.parse`, or env vars is untyped at runtime, so validate it (Zod, Valibot) at boundaries.
- **Structural typing ("duck typing"):** compatibility depends on *shape*, not declared name. Two unrelated types with the same members are interchangeable. Contrast with Java's nominal typing. Use **branded types** when you need nominal behavior.
- **Type checking vs transpiling:** `tsc` does both. esbuild, SWC, Babel, and Vite only *strip* types and never check. So run `tsc --noEmit` separately in CI. Check with `isolatedModules`/`verbatimModuleSyntax` so every file can be transpiled alone.
- **Type inference:** let the compiler infer locals, and annotate **function boundaries** (parameters, public return types, exported APIs). Over-annotating adds noise, and under-annotating exports leaks accidental types.
- **Soundness:** TS is intentionally *not fully sound* (casts, `any`, array covariance, index access without `noUncheckedIndexedAccess`). It trades perfect safety for usability.
- **Erasable syntax:** recent Node versions (22.18+ / 23.6+) can run `.ts` files by stripping types. Features that emit code (`enum`, `namespace`, constructor parameter properties) aren't supported in strip-only mode. TS 5.8's `erasableSyntaxOnly` flags them.
- **Where the compiler helps most:** refactoring, autocompletion, catching `undefined` access, exhaustive `switch`, and API contracts between frontend and backend (shared types, tRPC, OpenAPI codegen).

**Questions**
1. TypeScript vs JavaScript: what do you gain and lose?
2. Do types exist at runtime? How do you validate API responses? *(No. Use runtime schemas such as Zod and infer types from them.)*
3. What is structural typing? When is it a problem?
4. Why doesn't Vite or esbuild report type errors? 
5. When should you annotate and when should you infer?

**Model answer, Q2:** "No, TypeScript types are erased at compile time, so a `User` type can't protect me from a malformed API response. At trust boundaries (HTTP responses, request bodies, env vars, `JSON.parse`, storage) I validate with a runtime schema like Zod and derive the static type from it with `z.infer`. That gives one source of truth, and inside the boundary I can trust the types."

## 3.4.3 Core Types and Everyday Features
🟢 → 🟡 · **Must-know**

- **`any` vs `unknown` vs `never` vs `void`**
  - `any` switches off checking (and infects whatever it touches). **`unknown`** is the type-safe top type: you must narrow before use. **`never`** is the bottom type: no value (functions that always throw, impossible branches, exhaustiveness checks). **`void`** means "return value is ignored".
  - Use `unknown` for `catch (e)`, `JSON.parse` results, and generic inputs.
- **Literals and `as const`:** `'GET' | 'POST'`; `as const` makes an object deeply `readonly` with literal types, so you derive types from values: `const ROLES = ['admin','user'] as const; type Role = typeof ROLES[number];`
- **`satisfies` (4.9):** validates a value against a type *without widening* it. It keeps precise inference and still catches typos in keys.
```ts
const routes = { home: '/', user: '/u/:id' } satisfies Record<string, string>;
routes.home;      // type is the literal-ish string, and routes.nope is an error
```
- **Tuples:** `[string, number]`, optional and rest elements, named: `[id: number, label?: string]`.
- **Enums vs union of literals:** numeric enums are loosely typed (any number is assignable in older versions), emit runtime code, and don't work in strip-only mode. Prefer **string literal unions** or `as const` objects. `const enum` has bundler and `isolatedModules` pitfalls.
- **`type` vs `interface`**

| | `interface` | `type` |
|---|---|---|
| Object shapes | Yes | Yes |
| Unions, tuples, primitives, mapped/conditional | No | **Yes** |
| Extending | `extends` (clearer errors, cached, slightly faster) | intersection `&` |
| Declaration merging | **Yes** (useful for augmenting libraries) | No |
| Guideline | Public object contracts, class shapes, augmentation | Everything else. **Be consistent per codebase** |
- **Function types:** overloads (several call signatures, implementation signature hidden), optional and default params, `this` parameters, rest args, generic functions.
- **Classes:** `public/private/protected/readonly`, `#private` (true runtime privacy) vs TS `private` (compile-time only), `abstract`, `implements`, parameter properties (`constructor(private db: Db) {}`).
- **Object-type gotchas:** excess property checks apply only to fresh object literals. `{}` means "any non-nullish value" (avoid it). `object` means non-primitive. `Function` is too loose (use a call signature). `Object.keys(o)` returns `string[]` because objects can have extra keys, so cast deliberately or use a typed helper. Index signatures (`Record<string, T>`) make every key "exist" (hence `noUncheckedIndexedAccess`).
- **Non-null assertion `!` and casts `as T`:** assertions *override* the compiler and don't check anything. Prefer narrowing, type guards, or schemas. Treat each `as`/`!` as a code smell that needs justification.
- **Declaration files:** `.d.ts` describe untyped JS. `@types/*` packages (DefinitelyTyped), `declare module 'x'`, `declare global { interface Window { analytics: … } }`, and module augmentation for third-party types.
- **`import type`** is erased entirely and avoids accidental runtime imports and cycles.

## 3.4.4 Narrowing, Discriminated Unions, Type Guards
🟡 → 🔴 · **Must-know**

**Narrowing mechanisms:** `typeof`, `instanceof`, `in`, equality, truthiness, `Array.isArray`, optional-chaining checks, assignment, control flow analysis (early return), and user-defined guards.

```ts
// Discriminated union: a shared literal "tag" lets the compiler narrow
type Result<T> = { ok: true; value: T } | { ok: false; error: Error };

function unwrap<T>(r: Result<T>): T {
  if (r.ok) return r.value;     // narrowed to { ok: true }
  throw r.error;                // narrowed to { ok: false }
}

// Exhaustiveness: adding a new variant makes this a compile error
type Action = { type: 'add'; item: string } | { type: 'remove'; index: number } | { type: 'clear' };
const assertNever = (x: never): never => { throw new Error(`Unhandled: ${JSON.stringify(x)}`); };

function reducer(state: string[], a: Action): string[] {
  switch (a.type) {
    case 'add':    return [...state, a.item];
    case 'remove': return state.filter((_, i) => i !== a.index);
    case 'clear':  return [];
    default:       return assertNever(a);
  }
}

// User-defined type guard (the predicate is *trusted*, so a wrong guard is a lie)
const isString = (x: unknown): x is string => typeof x === 'string';

// Assertion function
function assertDefined<T>(x: T | null | undefined, msg = 'Expected value'): asserts x is T {
  if (x == null) throw new Error(msg);
}

// `in` narrowing
type Cat = { meow(): void }; type Dog = { bark(): void };
const speak = (p: Cat | Dog) => ('meow' in p ? p.meow() : p.bark());
```
- **Why model state as discriminated unions:** it makes illegal states unrepresentable.
```ts
// ❌ allows { loading: true, error: Error, data: User }
type BadState = { loading: boolean; data?: User; error?: Error };
// ✅
type State = { status: 'idle' } | { status: 'loading' } | { status: 'success'; data: User } | { status: 'error'; error: Error };
```
- **Narrowing caveats:** narrowing is lost across callbacks and after mutation. `filter(Boolean)` doesn't narrow (use `.filter((x): x is T => x != null)`, and TS 5.5 infers some predicates automatically). Narrowing by property works on `const`/readonly references more reliably.

## 3.4.5 Generics
🟡 → 🔴 · **Must-know**

**Definition:** Type-level parameters that let one function, class, or type work over many types while preserving the relationship between inputs and outputs.

```ts
function first<T>(xs: readonly T[]): T | undefined { return xs[0]; }

// Constraint: K must be a key of T, so the return type is tied to the exact key
function pluck<T, K extends keyof T>(items: T[], key: K): T[K][] { return items.map(i => i[key]); }
pluck([{ id: 1, name: 'a' }], 'name');     // string[]

// Generic with default, and a constraint on shape
interface ApiResponse<T = unknown> { data: T; status: number }

// Generic React-like list component, inference from props
function groupBy<T, K extends PropertyKey>(arr: T[], fn: (x: T) => K): Record<K, T[]> {
  return arr.reduce((acc, x) => { (acc[fn(x)] ??= []).push(x); return acc; }, {} as Record<K, T[]>);
}

// Generic class
class Repository<T extends { id: string }> {
  #items = new Map<string, T>();
  save(item: T) { this.#items.set(item.id, item); }
  find(id: string): T | undefined { return this.#items.get(id); }
}
```
- **Inference:** the compiler infers `T` from arguments, and explicit type args are rarely needed. If a type parameter appears only once in a signature, it's usually pointless (`function f<T>(x: T): void`).
- **`keyof`, `typeof`, indexed access `T[K]`, `T[number]`** are the vocabulary for relating types.
- **Constraints (`extends`)** limit what's acceptable and unlock member access.
- **`const` type parameters (5.0)** infer literals: `function f<const T>(x: T)`.
- **`NoInfer<T>` (5.4)** blocks inference from a position.
- **Variance:** function parameters are checked contravariantly under `strictFunctionTypes` (for function-typed properties, not method syntax, which stays bivariant).
- **Overloads vs generics vs unions:** prefer a generic or union parameter over many overloads when you can.

## 3.4.6 Utility, Mapped, Conditional, and Template Literal Types
🔴 Advanced · **Must-know (utilities)** / **Good-to-know (building your own)**

**Built-in utilities**

| Utility | Result |
|---|---|
| `Partial<T>` / `Required<T>` | All optional / all required |
| `Readonly<T>` | All `readonly` (shallow) |
| `Pick<T, K>` / `Omit<T, K>` | Keep / drop keys |
| `Record<K, V>` | Object with keys K and values V |
| `Exclude<U, X>` / `Extract<U, X>` | Remove from / keep in a union |
| `NonNullable<T>` | Remove `null`/`undefined` |
| `ReturnType<F>` / `Parameters<F>` | Function's return / param tuple |
| `Awaited<T>` | Unwrap promises (recursive) |
| `InstanceType<C>`, `ConstructorParameters<C>` | Class helpers |

**Mapped types:** `{ [K in keyof T]: … }` with modifiers (`readonly`, `?`, and `-readonly`/`-?` to remove) and key remapping with `as`.

**Conditional types:** `T extends U ? X : Y`, with `infer` to capture parts. They're **distributive** over naked union type parameters (`T extends U` applies to each member). Wrap in `[T]` to prevent that.

**Template literal types:** `` `get${Capitalize<K>}` ``, which build string unions.

```ts
type MyPick<T, K extends keyof T> = { [P in K]: T[P] };
type MyOmit<T, K extends PropertyKey> = { [P in keyof T as P extends K ? never : P]: T[P] };
type MyReadonly<T> = { readonly [P in keyof T]: T[P] };
type DeepReadonly<T> =
  T extends (...a: any[]) => any ? T :
  T extends object ? { readonly [K in keyof T]: DeepReadonly<T[K]> } : T;
type MyReturnType<F> = F extends (...a: any[]) => infer R ? R : never;
type MyAwaited<T> = T extends PromiseLike<infer U> ? MyAwaited<U> : T;
type TupleToUnion<T extends readonly unknown[]> = T[number];
type Getters<T> = { [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K] };
type UnionToIntersection<U> =
  (U extends unknown ? (x: U) => void : never) extends (x: infer I) => void ? I : never;
type PathsOf<T> = T extends object
  ? { [K in keyof T & string]: T[K] extends object ? K | `${K}.${PathsOf<T[K]>}` : K }[keyof T & string]
  : never;
// Make some keys optional
type PartialBy<T, K extends keyof T> = Omit<T, K> & Partial<Pick<T, K>>;
// Distributive vs non-distributive
type ToArray<T> = T extends unknown ? T[] : never;        // string | number → string[] | number[]
type ToArrayND<T> = [T] extends [unknown] ? T[] : never;  // (string | number)[]
```

**Practical patterns:** deriving types from schemas and constants (`z.infer`, `typeof CONFIG`, `keyof typeof`), typed event maps (`on<K extends keyof Events>(e: K, cb: (p: Events[K]) => void)`), typed route params, API client types from OpenAPI, and `Pick` for DTOs and view models.

## 3.5.1 Browser Architecture and the Rendering Pipeline
🔴 Advanced · **Must-know** (strongly tested for frontend-leaning roles)

**Architecture:** modern browsers are multi-process: a **browser** process (UI, navigation), **renderer** processes (one per site or tab, via **site isolation**, running Blink/WebKit + the JS engine), a **GPU** process, and a **network** service. In a renderer, the **main thread** runs JS, style, layout, and paint recording. The **compositor thread** and raster workers handle scrolling and `transform`/`opacity` animations independently of the main thread, which is why those stay smooth while JS is busy.

**The pipeline (every frame that changes visuals)**
```
JS ─▶ Style (match CSS, compute styles) ─▶ Layout/Reflow (geometry)
   ─▶ Paint (record draw ops per layer) ─▶ Raster ─▶ Composite (GPU assembles layers)
```
1. **Parse HTML → DOM** (incremental, streaming). The **preload scanner** looks ahead for resources (scripts, CSS, images) while the main parser is blocked.
2. **Parse CSS → CSSOM.** CSS is render-blocking, and scripts wait for pending CSS (they may query styles).
3. **Style calculation:** match selectors, compute final values. DOM + CSSOM yield the **render tree** (excludes `display:none`, includes pseudo-elements).
4. **Layout:** compute size and position (the cascade of geometry, expensive because changes can ripple).
5. **Paint:** produce draw instructions (text, colors, borders, shadows) per layer.
6. **Composite:** layers (for `transform`/`opacity`/`will-change`/video/canvas, fixed elements) are rastered and combined on the GPU.

**What triggers what**
- **Reflow (layout):** changing geometry (`width`, `height`, `top/left`, `margin`, `padding`, `font-size`, adding/removing DOM nodes, window resize, content change). Always followed by paint.
- **Repaint:** changing appearance without geometry (`color`, `background`, `visibility`, `box-shadow`, `outline`).
- **Composite only:** `transform`, `opacity`.
- **Forced synchronous layout ("layout thrashing")** happens when JS *reads* a layout-dependent value (`offsetHeight`, `getBoundingClientRect()`, `scrollTop`, `getComputedStyle().height`) after *writing* styles, so the browser must layout immediately. In a loop it repeats per iteration.
```js
// ❌ thrashing: read/write interleaved → N forced layouts
for (const el of items) el.style.width = (container.offsetWidth / 2) + 'px';
// ✅ batch reads, then writes
const w = container.offsetWidth / 2;
for (const el of items) el.style.width = w + 'px';
```
- **Fixes:** batch reads and writes, use `requestAnimationFrame` for writes, prefer `transform`, use `DocumentFragment` or build off-DOM, toggle classes instead of many inline styles, use `contain`/`content-visibility`, and virtualize long lists.
- **Parser-blocking and render-blocking:** `<script>` without `defer`/`async`, CSS `<link>`, and `@import`. **Critical rendering path** optimization means minimizing the bytes, round trips, and blocking resources before first paint.
- **Frame budget:** about 16.7ms at 60Hz. Long tasks (over 50ms) block input.
- **`DOMContentLoaded` vs `load`** (3.1.1), and the **`readyState`** progression (`loading` → `interactive` → `complete`).

## 3.5.2 JavaScript Engine (V8) in Practice
🔴 Advanced · **Good-to-know**

- **Pipeline:** parse → AST → **Ignition** (bytecode interpreter) → hot functions optimized by **TurboFan** (JIT, machine code) with **speculative optimization** based on observed types. If an assumption breaks (a function that always got ints suddenly gets a string), it **deoptimizes**. A cheaper baseline tier (Sparkplug, Maglev) sits between them.
- **Hidden classes (shapes) and inline caches:** objects with the same property insertion order share a shape, so property access becomes a fast offset lookup. **Writing practices that keep code fast:** initialize all properties in the constructor in the same order, don't `delete` properties (set to `undefined`/`null`), keep arrays homogeneous and dense (no holes), and don't mix types in hot functions (monomorphic > polymorphic > megamorphic).
- **GC:** generational (young "scavenger", old "mark-compact"), incremental and concurrent (Orinoco), so GC pauses are short, but allocation pressure still costs.
- **Don't micro-optimize prematurely.** Profile first, because most slowness is network, bundle size, DOM work, or algorithms.
- **Startup cost:** parse and compile time scales with JS bytes, which is why **shipping less JS** beats clever code. Code caching helps repeat visits.

## 3.5.3 Events: Propagation, Delegation, and Listener Behavior
🟡 Intermediate · **Must-know**

**Three phases:** **capture** (window → target) → **target** → **bubble** (target → window). `addEventListener(type, fn, { capture, once, passive, signal })`. Handlers default to the bubble phase.

- **`target` vs `currentTarget`:** the element that fired the event vs the element the listener is attached to. `this` in a regular-function listener is `currentTarget`.
- **`stopPropagation()`** stops further propagation. **`stopImmediatePropagation()`** also stops other listeners on the same element. **`preventDefault()`** cancels the default action (link navigation, form submit) but not propagation.
- **Delegation:** attach **one** listener to a common ancestor and inspect `event.target` (`closest('[data-action]')`). Benefits: fewer listeners, dynamic children work automatically, and less memory.
```js
list.addEventListener('click', (e) => {
  const btn = e.target.closest('button[data-id]');
  if (!btn || !list.contains(btn)) return;
  remove(btn.dataset.id);
});
```
- **Events that don't bubble:** `focus`/`blur` (use `focusin`/`focusout`), `mouseenter`/`mouseleave` (use `mouseover`/`out`), `load`, `scroll` on elements. Capture works for them.
- **Passive listeners:** `{ passive: true }` promises you won't call `preventDefault()`, so the browser can scroll without waiting for your handler (touch and wheel listeners on `window`/`document`/`body` are passive by default in Chrome).
- **Cleanup:** remove listeners (`removeEventListener` needs the same function reference and capture flag), or pass an `AbortSignal` to remove many at once.
```js
const ac = new AbortController();
window.addEventListener('resize', onResize, { signal: ac.signal });
window.addEventListener('keydown', onKey,   { signal: ac.signal });
ac.abort();   // removes both
```
- **Custom events:** `new CustomEvent('cart:add', { detail, bubbles: true, composed: true })` and `dispatchEvent`.
- **Pointer Events** (`pointerdown/move/up`) unify mouse, touch, and pen. Use `setPointerCapture` for drags, `touch-action` CSS to control gestures.
- **Keyboard:** `event.key` (not deprecated `keyCode`), `event.code` for physical keys, `isComposing` for IME input, and `keydown` vs `keyup` vs `input`.
- **`click` fires on Enter/Space for native buttons**, which is one more reason to avoid `div` buttons.
- **React's synthetic events** are delegated at the root container (not `document`) since React 17. `e.stopPropagation()` in React stops React propagation, and native listeners attached to `document` can still fire.
- **Unload:** don't use `unload`/`beforeunload` for analytics (they break bfcache and are unreliable on mobile). Use `visibilitychange`/`pagehide` with `navigator.sendBeacon()` or `fetch(..., { keepalive: true })`.

## 3.5.4 Same-Origin Policy, CORS, and Cross-Origin Controls
🔴 Advanced · **Must-know** (full stack classic)

**Origin** = scheme + host + port. `https://a.com` ≠ `http://a.com` ≠ `https://a.com:8443` ≠ `https://api.a.com`. **Same-site** (eTLD+1, i.e. `a.com`) is a looser concept used for cookies.

**Same-Origin Policy (SOP):** scripts from one origin can't *read* responses from another (embedding is mostly allowed: images, scripts, CSS, iframes, and form posts can be *sent* cross-origin but not read). SOP protects users' data on other sites. It is enforced **by browsers**, not servers.

**CORS** is a controlled *relaxation* of SOP via response headers.
- **Simple requests** (GET/HEAD/POST with safelisted headers and content types `text/plain`, `application/x-www-form-urlencoded`, `multipart/form-data`) go straight out, and the browser checks `Access-Control-Allow-Origin` on the response.
- **Preflighted requests:** anything else (methods like PUT/PATCH/DELETE, `Content-Type: application/json`, `Authorization` or custom headers) triggers an `OPTIONS` request first:
```http
OPTIONS /api/items HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type, authorization

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, PUT, DELETE
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 600        ← cache the preflight
Vary: Origin
```
- **Credentials:** the request needs `credentials: 'include'` (fetch) and the server must send `Access-Control-Allow-Credentials: true` with a **specific** origin, since `*` is not allowed with credentials. Cookies must also satisfy their `SameSite` rules.
- **Reflecting `Origin` blindly** (echo whatever is sent) while allowing credentials is a vulnerability. Use an allowlist, and add `Vary: Origin` so caches don't mix responses.
- **`Access-Control-Expose-Headers`** lets JS read non-safelisted response headers.
- **What CORS is NOT:** it's not server-side access control. `curl` and attackers' servers ignore it. It doesn't stop CSRF for simple requests (the request is still *sent*). It doesn't hide an unauthenticated API.
- **Common errors:** "No 'Access-Control-Allow-Origin' header" (the server didn't send it, or an error response such as a 500/redirect lacks CORS headers), "wildcard with credentials", "preflight doesn't pass" (the `OPTIONS` route is missing or behind auth), "header not allowed".
- **Solutions:** configure CORS middleware with an allowlist on the API. In dev, use a **dev-server proxy** (`/api` → backend) so the browser sees one origin. In prod, serve the frontend and API under one origin through a reverse proxy, or use the API gateway/CDN to add headers.
```js
import cors from 'cors';
const allowed = new Set(['https://app.example.com']);
app.use(cors({
  origin: (origin, cb) => cb(null, !origin || allowed.has(origin)),   // no Origin = non-browser client
  credentials: true,
  maxAge: 600,
}));
```
- **Related controls:** **CORP** (`Cross-Origin-Resource-Policy`), **COOP/COEP** (**cross-origin isolation**, required for `SharedArrayBuffer` and high-res timers), `postMessage` (always check `event.origin` and target origin), `<iframe sandbox>`, `Referrer-Policy`, `SameSite` cookies, and CSP `frame-ancestors`/`connect-src` (Phase 7).

## 3.5.5 Browser Storage
🟡 Intermediate · **Must-know**

| | Cookies | `localStorage` | `sessionStorage` | IndexedDB | Cache API / OPFS |
|---|---|---|---|---|---|
| Capacity | ~4KB per cookie | ~5MB per origin | ~5MB per origin | Large (a share of disk, quota-managed) | Large |
| Sent to server | **Every matching request** | No | No | No | No |
| Lifetime | Session or `Expires`/`Max-Age` | Until cleared | Per tab (cleared on tab close) | Until cleared or evicted | Until cleared or evicted |
| API | `document.cookie` / `Set-Cookie` | Sync, strings only | Sync, strings only | **Async**, structured data, indexes, transactions | Async, request/response pairs, files |
| Accessible by JS | Unless `HttpOnly` | Yes | Yes | Yes | Yes (workers too) |
| Typical use | Sessions, auth, preferences needing the server | Small UI prefs (theme) | Wizard state per tab | Offline data, large caches | Offline assets, large files |

**Cookie attributes (security-critical)**
- `HttpOnly`: JS can't read it (mitigates token theft via XSS). `Secure`: HTTPS only. `SameSite=Lax|Strict|None` controls cross-site sending (`None` requires `Secure`). `Lax` is the modern browser default. `Domain`/`Path` scope. `Max-Age`/`Expires`. Prefixes `__Host-` (Secure, no Domain, Path=/) and `__Secure-`.
- **Third-party cookies** are being restricted or blocked in browsers, so don't build core flows on them.
```http
Set-Cookie: __Host-sid=abc123; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=86400
```

**`localStorage` details**
- **Synchronous and blocking** on the main thread. Don't store large or frequently written data. Strings only (`JSON.stringify`). Shared across tabs of the same origin (the `storage` event notifies *other* tabs). It can throw `QuotaExceededError` or be unavailable in private modes, so wrap it in `try/catch`. It's not available in workers or SSR.
- **Never store secrets or auth tokens in `localStorage`** if XSS is a concern, since any injected script can read them. Prefer `HttpOnly` cookies (Phase 7 discusses the trade-offs, including CSRF).
- **Storage partitioning** and Safari's Intelligent Tracking Prevention can cap script-writable storage lifetime (about 7 days of inactivity in some conditions), so don't treat browser storage as durable. Request persistence with `navigator.storage.persist()` for important offline data.

**IndexedDB:** transactional object-store database. The raw API is verbose, so use `idb`, Dexie, or localForage. **Use for:** offline-first apps, drafts, caching API results.

**Choosing:** server-relevant and sensitive → `HttpOnly` cookie; small non-sensitive prefs → `localStorage`; per-tab ephemeral → `sessionStorage`; large/structured/offline → IndexedDB; assets → Cache API.

## 3.5.6 HTTP Caching (Browser and CDN)
🔴 Advanced · **Must-know**

**The model:** a cached response is **fresh** (use without asking) or **stale** (revalidate with the server using validators).

**Headers**
- **`Cache-Control` (response):**
  - `max-age=N` fresh for N seconds (browser). `s-maxage=N` for shared caches (CDN).
  - **`no-cache`**: may store, but **must revalidate** before every use. (Not "don't cache".)
  - **`no-store`**: don't store at all (sensitive data).
  - `public` / `private` (private: browser only, not shared caches). `must-revalidate`. **`immutable`**: it'll never change while fresh, so skip revalidation on reload.
  - `stale-while-revalidate=N`: serve stale for N seconds while refreshing in the background. `stale-if-error=N`.
- **Validators:** `ETag` (content fingerprint) → client sends `If-None-Match`; `Last-Modified` → `If-Modified-Since`. The server answers **`304 Not Modified`** (no body) if unchanged.
- **`Vary`:** which request headers the cached response depends on (`Accept-Encoding`, `Origin`, `Accept-Language`). Mis-set `Vary` causes cache poisoning or fragmentation.
- Without explicit freshness, browsers apply **heuristic freshness** (often a fraction of the time since `Last-Modified`), so set headers deliberately.
- **Reload behavior:** normal navigation uses the cache, a regular reload revalidates, and a hard reload bypasses it.

**The standard strategy**

| Resource | Header | Why |
|---|---|---|
| Fingerprinted assets (`app.3f9a1c.js`, hashed CSS/images/fonts) | `public, max-age=31536000, immutable` | Content hash in filename = safe to cache forever. A new deploy = new filename |
| HTML documents | `no-cache` (or short `max-age` + `stale-while-revalidate`) | Must point to the latest hashed assets |
| Public API data that can be slightly stale | `public, max-age=60, stale-while-revalidate=300` | Fast and cheap |
| Per-user API responses | `private, no-cache` or `no-store` | Never in shared caches |
| Sensitive data | `no-store` | Don't persist |

- **Cache busting:** content hashes (best), versioned URLs (`?v=2` is weaker, since some proxies ignore the query string), and CDN purge for non-hashed assets.
- **Layers:** memory cache → disk cache → service worker cache → CDN edge → origin. Each can serve independently.
- **bfcache (back/forward cache):** whole-page snapshots that make back/forward navigation instant. Pages are blocked by `unload` handlers, open connections, and sometimes `Cache-Control: no-store`, so use `pagehide`/`visibilitychange` instead.
- **Common bug:** deploying a new `index.html` that references assets not yet uploaded, or caching `index.html` for a year so users are stuck on old code. Upload assets first, then HTML, and keep old assets available for a while for open tabs.

## 3.5.7 Web Workers and Off-Main-Thread Work
🔴 Advanced · **Good-to-know**

- **Dedicated Worker:** `new Worker(new URL('./w.js', import.meta.url), { type: 'module' })` has its own thread and event loop, with no DOM access. Communicate with `postMessage` (data copied via the **structured clone algorithm**, which can't clone functions or DOM nodes).
- **Transferables** (`ArrayBuffer`, `MessagePort`, `OffscreenCanvas`, `ImageBitmap`) are moved without copying: `postMessage(buf, [buf])`. The sender loses access.
- **`SharedArrayBuffer` + `Atomics`:** true shared memory, requires cross-origin isolation (COOP + COEP).
- **SharedWorker:** one worker shared by tabs of the same origin. **Service Worker:** network proxy (3.9). **Worklets:** audio/paint.
- **Use for:** parsing big JSON/CSV, image/video processing, crypto, search indexing, diffing, compression, WASM, heavy charting, and anything over about 50ms that blocks input.
- **Costs:** startup time, serialization overhead for large messages, and no DOM. Comlink gives an RPC-style API over `postMessage`.
```js
// main.js
const worker = new Worker(new URL('./parse.worker.js', import.meta.url), { type: 'module' });
worker.onmessage = ({ data }) => render(data);
worker.onerror = console.error;
worker.postMessage({ csv: bigString });

// parse.worker.js
self.onmessage = ({ data }) => {
  const rows = data.csv.split('\n').map(l => l.split(','));   // heavy work off the main thread
  self.postMessage(rows);
};
```
- **Node's equivalent:** `worker_threads` (Phase 5).

## 3.5.8 Observers and DOM APIs
🟡 Intermediate · **Must-know**

| Observer | Watches | Typical use |
|---|---|---|
| **IntersectionObserver** | Visibility relative to a root/viewport | Lazy loading, infinite scroll, scroll-spy, viewability analytics, pause off-screen video |
| **ResizeObserver** | Element size changes | Responsive components, charts, auto-grow textareas |
| **MutationObserver** | DOM tree/attribute changes (fires as a microtask batch) | Reacting to third-party DOM changes, extensions |
| **PerformanceObserver** | Performance entries (LCP, long tasks, layout shift, resources) | RUM and web-vitals |

```js
// Infinite scroll without scroll listeners
const io = new IntersectionObserver(async ([entry]) => {
  if (!entry.isIntersecting || loading) return;
  loading = true;
  try { await loadNextPage(); } finally { loading = false; }
}, { rootMargin: '400px' });          // start loading before it's visible
io.observe(document.querySelector('#sentinel'));

// Lazy image swap
const imgIO = new IntersectionObserver((entries, obs) => {
  for (const e of entries) if (e.isIntersecting) { e.target.src = e.target.dataset.src; obs.unobserve(e.target); }
});
document.querySelectorAll('img[data-src]').forEach(img => imgIO.observe(img));

// Long tasks (RUM)
new PerformanceObserver(list => list.getEntries().forEach(e => report('long-task', e.duration)))
  .observe({ type: 'longtask', buffered: true });
```
- **Prefer observers over `scroll`/`resize` handlers:** they're asynchronous, batched, and off the hot path.
- **ResizeObserver loop errors** ("ResizeObserver loop completed with undelivered notifications") happen if a callback changes sizes that trigger more observations. It's usually benign, but avoid layout feedback loops.
- **Always `disconnect()`/`unobserve()`** on cleanup (React effect return).

**DOM API essentials**
- **Selection:** `querySelector(All)` returns a **static** NodeList. `getElementsByClassName` returns a **live** HTMLCollection. `closest()`, `matches()`, `contains()`.
- **Manipulation:** `textContent` (safe, no parsing) vs **`innerHTML`** (parses HTML, an XSS sink, so sanitize with DOMPurify or avoid). `createElement`, `append`, `replaceChildren`, `insertAdjacentHTML`, `DocumentFragment` and `<template>` for batching, `classList`, `dataset`, `toggleAttribute`.
- **Timing APIs:** `requestAnimationFrame` (visual updates before paint), `requestIdleCallback` (low-priority work, not in Safari, so feature-detect), `queueMicrotask`, `scheduler.postTask`/`yield` where supported.
- **Trusted Types** (a CSP feature) forces dangerous sinks to receive sanitized typed values.

## 3.6.1 Core Web Vitals and Measurement
🔴 Advanced · **Must-know**

**Definition:** Google's user-centric metrics for loading, interactivity, and visual stability. They're ranking signals and the shared vocabulary for performance work.

| Metric | Measures | Good | Poor |
|---|---|---|---|
| **LCP** (Largest Contentful Paint) | When the main content (largest image/text block) renders | ≤ 2.5 s | > 4 s |
| **INP** (Interaction to Next Paint) | Responsiveness: the (near-)worst interaction latency across the visit. **Replaced FID in March 2024** | ≤ 200 ms | > 500 ms |
| **CLS** (Cumulative Layout Shift) | Unexpected layout movement | ≤ 0.1 | > 0.25 |

Evaluated at the **75th percentile** of real users, separately for mobile and desktop. Supporting metrics: **TTFB** (≤ ~800 ms good), **FCP**, **TBT** (lab proxy for INP), **Speed Index**.

**Lab vs field data**
- **Lab** (Lighthouse, WebPageTest, DevTools): controlled, reproducible, good for debugging, but it's a single simulated device and network, and can't measure INP without scripted interactions (TBT stands in).
- **Field/RUM** (CrUX, PageSpeed Insights field section, your own beacon using the `web-vitals` library): what real users experience, and what Google ranks on. **Use lab to diagnose and field to prioritize and verify.**
```js
import { onLCP, onINP, onCLS } from 'web-vitals/attribution';
const send = ({ name, value, id, attribution }) =>
  navigator.sendBeacon('/rum', JSON.stringify({ name, value, id, page: location.pathname, attribution }));
onLCP(send); onINP(send); onCLS(send);
```
- **Performance budgets:** set limits (JS ≤ N KB, LCP ≤ 2.5s) and enforce them in CI (Lighthouse CI, bundlesize/size-limit) so regressions fail PRs.
- **Business link:** conversion and retention correlate with speed, so tie metrics to outcomes when making the case to stakeholders.

## 3.6.2 Optimizing LCP
🔴 Advanced · **Must-know**

**LCP = four phases:** **TTFB** → **resource load delay** (discovering the LCP resource late) → **resource load duration** → **element render delay** (blocked by CSS/JS or client rendering).

**Fixes by phase**
- **TTFB:** CDN and edge caching, server/DB speed, avoid redirect chains, HTTP/2 or 3, streaming SSR, cache HTML where possible, `103 Early Hints`.
- **Load delay:** make the LCP element **discoverable in the initial HTML** (don't inject via JS, don't `loading="lazy"` it, avoid CSS `background-image` for hero content, and CSR-only apps delay everything). Use `<link rel="preload" as="image" fetchpriority="high">` and `fetchpriority="high"` on the `<img>`.
- **Load duration:** right-size and compress images (AVIF/WebP, `srcset`), serve from a CDN, preconnect to the image origin, and avoid giant hero videos.
- **Render delay:** inline critical CSS, remove render-blocking CSS and JS, don't block on web fonts for LCP text (`font-display: swap`/`optional`), and prefer SSR/SSG so content exists before JS hydrates.

**Questions:** What element counts as LCP? Your LCP is 4.5s. What do you check first? *(Break it into the four phases, using the Performance panel's insights or `web-vitals` attribution, then fix the largest phase.)* Why is lazy-loading the hero image harmful? How does CSR affect LCP?

## 3.6.3 Optimizing INP and Main-Thread Work
🔴 Advanced · **Must-know**

**INP phases:** **input delay** (main thread busy when the user taps) → **processing time** (your handlers) → **presentation delay** (rendering the result).

**Fixes**
- **Break up long tasks** (over 50ms) and yield to the main thread so input can be handled in between:
```js
const yieldToMain = () =>
  globalThis.scheduler?.yield ? scheduler.yield() : new Promise(r => setTimeout(r, 0));

async function processAll(items) {
  let deadline = performance.now() + 40;
  for (const item of items) {
    work(item);
    if (performance.now() > deadline) { await yieldToMain(); deadline = performance.now() + 40; }
  }
}
```
- **Do less in event handlers:** show visual feedback immediately, then defer non-urgent work (analytics, logging, state fan-out).
- **React specifics:** `useTransition`/`useDeferredValue` to mark non-urgent updates, `memo`/`useMemo` where profiling justifies them, virtualize long lists, split state so fewer components re-render, avoid expensive work in render, and reduce **hydration cost** (RSC, islands, selective hydration).
- **Reduce main-thread work overall:** ship less JS, defer third-party scripts, avoid layout thrashing, use `content-visibility: auto`, move computation to Web Workers, and reduce DOM size (large DOMs of thousands of nodes make every style/layout expensive).
- **Debounce/throttle** high-frequency handlers (scroll, input), and use passive listeners.

**Questions:** What is INP? How is it different from FID? A button click takes 600ms to update the UI. How do you investigate? *(Performance panel, find the long task and its call tree, check handler work, forced layouts, re-render scope, then fix by deferring, splitting, memoizing, or workers.)* What is a long task? How does hydration hurt INP? How does `useTransition` help?

## 3.6.4 Optimizing CLS
🟡 Intermediate · **Must-know**

**Causes → fixes**
- Images/video/iframes without dimensions → set `width`/`height` or `aspect-ratio`.
- Ads, embeds, banners injected late → reserve space with `min-height`/placeholder, and avoid inserting content *above* existing content.
- Web fonts swapping and changing metrics → `font-display`, preload key fonts, and fallback fonts with matched metrics (`size-adjust`, `ascent-override`, or Next's `next/font`).
- Late-loading CSS → inline critical CSS.
- Animations that move layout → use `transform` instead of `top/margin/height`.
- Client-rendered content replacing a skeleton of a different size → size skeletons to match.
- Layout shifts within 500ms of user input are excluded (expected shifts). Debug with the DevTools "Layout Shifts" track and the Rendering panel's shift regions.

## 3.6.5 JavaScript, Bundles, and Loading Strategy
🔴 Advanced · **Must-know**

**Why JS is the costliest byte:** it must be downloaded, **parsed, compiled, and executed** on the main thread, and slow phones pay far more than your laptop. 200KB of JS costs more than 200KB of images.

**Tactics**
- **Measure first:** bundle analyzers (`vite-bundle-visualizer`, `webpack-bundle-analyzer`, `source-map-explorer`, `next build` output), Chrome DevTools **Coverage** tab (unused bytes), and Lighthouse "Reduce unused JavaScript".
- **Code splitting:** route-level (`React.lazy` + dynamic `import()`, Next.js automatic per-route), component-level for heavy, rarely used widgets (editors, charts, maps, modals), and vendor chunking for cache stability.
- **Tree shaking:** ESM imports, `sideEffects: false`, avoid barrel-file re-exports of huge libraries, import specifically (`import debounce from 'lodash-es/debounce'`).
- **Replace heavy dependencies:** `moment` → `date-fns`/`dayjs`/Temporal, full `lodash` → native or `lodash-es`, icon packs → per-icon imports, and check **bundlephobia**-style size before adding a dependency.
- **Modern output:** target modern browsers with `browserslist` to avoid shipping legacy transforms and polyfills to everyone.
- **Third-party scripts:** a top cause of poor INP and LCP. Load with `async`/`defer`, after interaction or idle, use facades (click-to-load YouTube embeds), self-host critical ones, move to a worker (Partytown), and audit tag-manager sprawl.
- **Preload/prefetch strategy:** preload critical, prefetch likely next routes (`<Link prefetch>` on hover or viewport), and don't over-preload.
- **Rendering strategy choice:** SSG/ISR for mostly static pages, SSR with streaming for dynamic personalised ones, RSC to keep heavy libraries on the server, islands (Astro) for mostly static pages with small interactive pieces, and CSR only where SEO and first paint matter less.
- **Avoid request waterfalls:** fetch in parallel, hoist data fetching to the route level (loaders, RSC), `preconnect` to API/CDN origins, and avoid fetch-on-render chains (component A renders, then fetches, then renders child B, which fetches).
- **Compression and protocol:** Brotli for text (gzip fallback), HTTP/2 or 3 multiplexing (so don't over-bundle, but also don't create hundreds of tiny files), and long-lived caching with hashed filenames (3.5.6).
- **Lists and DOM size:** virtualization (TanStack Virtual, react-window) for thousands of rows, pagination or infinite scroll with windowing, and `content-visibility: auto` for long documents.
- **Service worker / client caching, SWR/TanStack Query** for data reuse.

## 3.6.6 Images, Fonts, and CSS Performance
🟡 Intermediate · **Must-know**

- **Images (usually the heaviest bytes):** AVIF/WebP with fallbacks, `srcset`/`sizes`, correct dimensions (don't ship 4000px for a 400px slot), quality 60-80, lazy-load below the fold, eager + `fetchpriority="high"` for LCP, an image CDN or framework component (`next/image`) with automatic resize and format negotiation, and `decoding="async"`. ## 3.6.7 The "Page Is Slow" Playbook
🔴 Advanced · **Must-know** (a classic scenario)

# 3.7 ACCESSIBILITY IN DEPTH

*(Builds on 3.1.5.)*

## 3.7.1 The Accessibility Tree, Names, Roles, and Values
🟡 → 🔴 · **Must-know**

- The browser derives an **accessibility tree** from the DOM (plus ARIA and CSS effects). Assistive tech reads *that*. Each node exposes **role** (what it is), **name** (what it's called), **state/properties** (checked, expanded, disabled, required, invalid), and **value**.
- **Accessible name computation (simplified order):** `aria-labelledby` → `aria-label` → native source (`<label>`, `alt`, `<legend>`, `<caption>`, button/link text content) → `title` (last resort) → placeholder (weak fallback, don't rely on it).
- **Test names and roles with Testing Library:** `getByRole('button', { name: /save/i })` simultaneously encourages accessible markup (Phase 9).
- **What removes content from the tree:** `display: none`, `visibility: hidden`, the `hidden` attribute, `aria-hidden="true"` (not for focusable elements, which creates "ghost" focus), and `inert`.
- **Never put `aria-hidden` on focusable content**, and never use `role="presentation"` on elements that need semantics.
- **Common naming bugs:** icon-only buttons with no label, links that say "click here"/"read more" (give context), repeated identical link names that go to different places, images with filename alt text, inputs labelled only by placeholder, and `aria-label` that doesn't include the visible text (breaks voice control, as WCAG 2.5.3 "Label in Name" requires the visible text be in the accessible name).

**Questions:** What's the accessibility tree? How is an element's accessible name computed? What's wrong with `<a>click here</a>`? When should you use `aria-labelledby` over `aria-label`? *(When visible text already exists, so it stays in sync and translated.)*

## 3.7.2 ARIA Patterns and Keyboard Interaction
🔴 Advanced · **Must-know**

- **ARIA Authoring Practices Guide (APG)** defines expected roles, states, and **keyboard behavior** for widgets (tabs, menu, combobox, listbox, dialog, accordion, tree, disclosure, tooltip). Users expect the standard keys, so follow APG precisely or use a headless library that already does (Radix, React Aria, Headless UI, Ark).
- **Focus-management techniques**
  - **Roving tabindex:** only the active item has `tabindex="0"`, the rest `-1`. Arrow keys move focus and update the tabindex (tabs, toolbars, radio-like groups). One Tab stop for the whole widget.
  - **`aria-activedescendant`:** focus stays on the container/input (e.g., a combobox input) and the attribute points to the "virtually focused" option.
- **Tabs (APG)**
```html
<div role="tablist" aria-label="Settings">
  <button role="tab" id="t1" aria-selected="true"  aria-controls="p1" tabindex="0">General</button>
  <button role="tab" id="t2" aria-selected="false" aria-controls="p2" tabindex="-1">Billing</button>
</div>
<div role="tabpanel" id="p1" aria-labelledby="t1" tabindex="0">…</div>
<div role="tabpanel" id="p2" aria-labelledby="t2" hidden>…</div>
```
```js
tablist.addEventListener('keydown', (e) => {
  const tabs = [...tablist.querySelectorAll('[role=tab]')];
  const i = tabs.indexOf(document.activeElement);
  const next = { ArrowRight: (i + 1) % tabs.length, ArrowLeft: (i - 1 + tabs.length) % tabs.length,
                 Home: 0, End: tabs.length - 1 }[e.key];
  if (next === undefined) return;
  e.preventDefault();
  tabs.forEach((t, j) => { t.tabIndex = j === next ? 0 : -1; t.setAttribute('aria-selected', String(j === next)); });
  tabs[next].focus();    // update panels' `hidden` too
});
```
- **Dialog/modal:** `role="dialog"` + `aria-modal="true"` + a name (`aria-labelledby`), move focus inside on open (first focusable or the dialog itself), trap Tab within, close on `Esc`, return focus to the trigger on close, make the background inert, and lock body scroll. Native `<dialog>.showModal()` handles most of this.
- **Disclosure/accordion:** a `<button aria-expanded aria-controls>` toggling a region. Use native `<details>` when possible.
- **Menu button:** `aria-haspopup`, `aria-expanded`, arrow-key navigation, `Esc`, typeahead. **Don't use `role="menu"` for site navigation** (a list of links in a `<nav>` with a disclosure button is correct). `role="menu"` is for application-style menus.
- **Combobox/autocomplete:** `role="combobox"`, `aria-expanded`, `aria-controls` the listbox, `aria-activedescendant`, `aria-autocomplete`, and announcing result counts via a live region. It's the hardest widget, so use a library.
- **Tooltip:** `role="tooltip"` + `aria-describedby`, shown on both hover **and** focus, dismissible with `Esc`, and hoverable (WCAG 1.4.13 Content on Hover or Focus).
- **Keyboard essentials:** all interactive elements reachable and operable, visible focus (WCAG 2.4.7; and 2.4.11 *Focus Not Obscured*, so sticky headers must not cover the focused element), logical order, no keyboard traps, and shortcuts that can be turned off or remapped (2.1.4).

**Questions**

4. Is `role="menu"` appropriate for a site's navigation dropdown? *(No)*

## 3.7.3 Focus Management in SPAs and Dynamic UIs
🔴 Advanced · **Must-know**

- **The SPA problem:** client-side route changes don't reload the page, so screen readers hear nothing and focus stays on the clicked link. **Fix:** on navigation, update `document.title`, move focus to the new page's `<h1>` (give it `tabindex="-1"`) or the main container, and/or announce the new page title in a live region. Frameworks (Next.js has a route announcer, React Router has options) help, but verify.
- **Modals/drawers:** move focus in, trap, restore on close.
- **Deleting an item:** move focus to a logical neighbor (next item, list heading, or "undo" message), never lose it to `<body>`.
- **Loading states:** `aria-busy="true"` on the updating region, announce completion via `role="status"`.
- **Inline validation errors:** on submit, focus the first invalid field or an error summary at the top (with links to fields).
- **Skip links** (`<a href="#main">Skip to content</a>`), and landmark regions for fast navigation.
- **`:focus-visible`** for keyboard-only focus rings, and never remove outlines without a clear replacement.
- **Don't autofocus aggressively**, since it disorients screen reader users and scrolls pages unexpectedly (except in modals and search dialogs, where it's expected).
- **Focus trapping edge cases:** shadow DOM, iframes, and portal-rendered content. Prefer the native `inert` attribute on the background to avoid fragile manual traps.

```js
// After client-side navigation
function onRouteChange(title) {
  document.title = title;
  const h1 = document.querySelector('h1');
  h1.setAttribute('tabindex', '-1');
  h1.focus({ preventScroll: false });
}
```

## 3.7.4 Live Regions and Dynamic Announcements
🟡 Intermediate · **Must-know**

- **Live regions** announce DOM changes without moving focus. `aria-live="polite"` (waits for a pause), `"assertive"` (interrupts, use sparingly), `role="status"` (implicit polite), `role="alert"` (implicit assertive), `aria-atomic` (read the whole region vs the change), `aria-relevant`.
- **Gotcha:** the live region container must **exist in the DOM before** its content changes. Injecting a new `role="status"` element that already has text often isn't announced. Render an empty container on load and update its text.
- **Use cases:** form errors and success messages, toasts ("Saved"), search result counts ("12 results"), cart updates, chat messages, and loading/complete states.
- **Anti-patterns:** announcing every keystroke or progress tick, using `assertive` for non-critical info, toasts that vanish before they can be read (WCAG 2.2.1 timing), and live regions inside `display:none`.
```html
<div id="live" role="status" aria-live="polite" class="sr-only"></div>
<script>
  function announce(msg) { live.textContent = ''; requestAnimationFrame(() => (live.textContent = msg)); }
</script>
```

**Questions:** How do you announce an async result to screen readers? `polite` vs `assertive`? Why might a live region not announce?

## 3.7.5 Visual Accessibility: Contrast, Zoom, Motion, and Preferences
🟡 Intermediate · **Must-know**

- **Contrast:** text 4.5:1 (3:1 for large text), **non-text UI** (input borders, icons, focus rings, chart elements) 3:1 (WCAG 1.4.11), and states (hover, disabled are exempt for disabled). Tools: DevTools color picker, axe, Stark, WebAIM contrast checker. Remember dark mode, gradients, and text over images.
- **Don't rely on color alone** (links need underline or another cue, errors need an icon and text, chart series need patterns or labels).
- **Reflow and zoom:** content must work at 400% zoom / 320 CSS px wide without two-dimensional scrolling (1.4.10), text resizes to 200% (1.4.4), and users can set text spacing (1.4.12), so don't use fixed heights that clip text. Use `rem`, flexible layouts, and avoid `user-scalable=no`.
- **Orientation:** don't lock to portrait or landscape unless essential (1.3.4).
- **Motion:** respect `prefers-reduced-motion`, avoid parallax and large auto-moving content, provide pause/stop for anything moving over 5s (2.2.2), and never flash more than 3 times per second (2.3.1).
- **Touch and pointer (2.2 additions):** targets at least 24×24 CSS px (2.5.8), alternatives to drag-only interactions (2.5.7, e.g. buttons to reorder), and pointer cancellation (don't fire on `down`).
- **User preferences:** `prefers-color-scheme`, `prefers-contrast`, `prefers-reduced-transparency`, and `forced-colors` (Windows High Contrast, where custom backgrounds and `box-shadow` focus rings may vanish, so use `outline`/`border`, and system colors like `CanvasText`).
- **Readable content:** plain language, `lang` attributes for foreign phrases (`<span lang="fr">`), consistent navigation and help (3.2.3, 3.2.6), no content that only works on hover.

🟡 Intermediate · **Good-to-know**

- **WCAG 2.2 AA additions:** 2.4.11 Focus Not Obscured (Minimum), 2.5.7 Dragging Movements, 2.5.8 Target Size (Minimum), 3.2.6 Consistent Help, 3.3.7 Redundant Entry (don't make users retype info), 3.3.8 Accessible Authentication (no cognitive-test-only login, so allow paste, password managers, and passkeys). 2.2 also removed the obsolete 4.1.1 Parsing criterion.

# 3.8 BUILD TOOLS AND MONOREPOS

## 3.8.1 What Build Tools Do and the Landscape
🟡 Intermediate · **Must-know**

**Responsibilities:** transpile (TS/JSX/new syntax → target JS), **bundle** (resolve the module graph into few files), minify, tree shake, code split, handle assets (CSS, images, fonts, SVG), inject env vars, produce source maps and content-hashed filenames, run a **dev server with HMR**, and generate the HTML shell/manifest.

| Tool | Notes |
|---|---|
| **Vite** | Dev server serves **native ES modules** on demand (no bundling in dev) with **esbuild** pre-bundling third-party deps, so cold start and HMR are fast. Production builds use Rollup (with Rolldown, a Rust port, rolling out). The de facto choice for SPAs and most frameworks |
| **Webpack** | The long-time standard: highly configurable (loaders, plugins, Module Federation), but slower and config-heavy. Huge legacy footprint (CRA is deprecated) |
| **Rspack** | Rust, mostly Webpack-compatible (a migration path from Webpack) |
| **esbuild** | Go, extremely fast bundler/transpiler/minifier. No type checking, limited plugin hooks, so it's used under other tools |
| **SWC** | Rust compiler (Babel replacement) used by Next.js, Vitest-adjacent tooling |
| **Babel** | Plugin-based JS transformer, still used for custom transforms (e.g., React Compiler plugin, some libraries). Slower |
| **Turbopack** | Rust bundler integrated into Next.js |
| **Rollup / tsup / tsdown / unbuild** | Library bundling (clean ESM/CJS output, `.d.ts` generation) |
| **Parcel, Bun** | Zero-config bundler / runtime with a built-in bundler |
| **tsc** | Type checker and (optionally) emitter. Use `--noEmit` with bundlers |

**Why Vite dev is fast:** it doesn't bundle your source. The browser requests modules over native ESM, and Vite transforms each file lazily on request. Dependencies are pre-bundled once (they're CommonJS-heavy and have many files). HMR invalidates only the changed module chain. Large apps can still suffer from many unbundled requests (mitigated by caching and by newer full-bundle dev modes).

**Why prod is still bundled:** fewer round trips, tree shaking, minification, optimized chunking, and legacy-browser targets.

4. How does HMR work? *(A dev-server websocket tells the client which modules changed. The runtime re-imports them and calls accept handlers. React Fast Refresh preserves component state when only components changed.)*

## 3.8.2 Configuration, Env Vars, Chunking, and Caching
🟡 → 🔴 · **Must-know**

```js
// vite.config.ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  resolve: { alias: { '@': '/src' } },
  server: { proxy: { '/api': { target: 'http://localhost:4000', changeOrigin: true } } },  // dev: no CORS needed
  build: {
    target: 'es2022',
    sourcemap: true,                       // upload to Sentry, don't serve publicly
    rollupOptions: { output: { manualChunks: { vendor: ['react', 'react-dom'] } } },
  },
});
```
- **Environment variables are inlined at build time.** In Vite, only `VITE_*` vars reach client code (`import.meta.env.VITE_API_URL`). In Next.js, `NEXT_PUBLIC_*`. **Anything in a client bundle is public**, so never put secrets there. Consequence: a client build is tied to its env values, so "build once, deploy many" needs runtime config (fetch `/config.json` at startup, or inject via a server-rendered script).
- **Content-hashed filenames** (`app.3f9a1c.js`) enable immutable caching. **Chunk strategy:** a stable vendor chunk survives app deploys, route chunks load on demand, and shared chunks avoid duplication. Watch for duplicate packages from mismatched versions (`npm ls`, `pnpm why`).
- **Source maps:** `hidden-source-map`/uploading to an error tracker gives readable stack traces without exposing source publicly.
- **Browserslist/targets:** controls transforms and polyfills (`core-js`). Modern targets mean smaller bundles.
- **Tree shaking requirements:** ESM, no side-effectful top-level code in the shaken module, and `"sideEffects": false` (or a list) in `package.json`. Marking CSS imports as side-effects matters.
- **Assets:** small assets inlined as data URIs (threshold), others hashed and emitted. CSS extracted and minified. SVG as components (SVGR) or URLs.
- **Common pitfalls:** huge barrel files, importing a whole library for one function, accidentally bundling server-only code (and secrets) in a client bundle, duplicate React copies (breaks hooks), "works in dev, breaks in prod" caused by CJS/ESM interop or dev-only behavior, and aliases configured for TS but not for the bundler.

## 3.8.3 Monorepos: Workspaces, Turborepo, Nx
🔴 Advanced · **Good-to-know** (increasingly common at full stack companies)

- **Why:** share types, schemas, UI components, and config between web, API, and mobile. Atomic cross-package changes, one CI config, consistent tooling. **Costs:** tooling complexity, CI time without caching, and permissions/ownership.
- **Layers**
  1. **Package manager workspaces** (pnpm, npm, yarn): link local packages (`"@acme/ui": "workspace:*"`). pnpm's strict `node_modules` avoids phantom dependencies.
  2. **Task orchestrators:** **Turborepo** and **Nx** understand the package graph, run tasks in dependency order and in parallel, **cache** outputs by input hash (locally and remotely, so CI and teammates skip repeated work), and run only **affected** packages on a PR. Nx adds generators, a project graph, and module boundary lint rules.
  3. **TypeScript project references** or path/`exports` mapping to share types and build incrementally.
  4. **Versioning and publishing:** Changesets or semantic-release for libraries, or a single version for apps.
- **Typical layout**
```
apps/web (Next.js)      apps/api (Node)      apps/admin
packages/ui (components) packages/schemas (Zod, shared types) packages/config (eslint, tsconfig)
```
- **Internal packages:** either **build** them (compile to `dist`, with `exports`) or consume **source directly** (the app's bundler transpiles them, which is faster to iterate on but requires the bundler config to transpile workspace packages).
- **Pitfalls:** circular package dependencies, hoisting issues and phantom deps, mismatched dependency versions (use `syncpack`/catalogs), cache misses from undeclared inputs (env vars, files not listed in the task config), and giant CI jobs when everything depends on a core package.
- **Polyrepo vs monorepo:** polyrepo gives hard isolation and independent release cadence, but cross-repo changes and shared code are painful. Choose based on team size, coupling, and tooling maturity.

# 3.9 PWAs AND WEB APIs

## 3.9.1 Progressive Web Apps and Service Workers
🔴 Advanced · **Must-know (concepts)** / **Good-to-know (implementation)**

**Definition:** Web apps enhanced with a manifest, service worker, and HTTPS so they're installable, resilient to bad networks, and can re-engage users.

**Web App Manifest:** JSON linked via `<link rel="manifest">` with `name`, `short_name`, `icons` (192 and 512, with maskable), `start_url`, `scope`, `display` (`standalone`), `theme_color`, `background_color`, and optionally `shortcuts`, `screenshots`. Installability criteria vary by browser (HTTPS and a valid manifest are the core). Safari/iOS has its own quirks and storage limits.

**Service worker (SW):** a script that runs in a separate thread, **intercepts network requests** for its scope, and works with the **Cache API**. It requires **HTTPS**, has no DOM access, is event-driven, and can be terminated when idle (don't keep state in globals).

**Lifecycle**
```
register → install (precache) → waiting (if an old SW controls pages) → activate (clean old caches) → controlling clients → fetch/message/push events
```
- A new SW installs in the background but **waits** until all tabs using the old one close (or `skipWaiting()` is called). `clients.claim()` takes control of open pages immediately. **Updates:** the browser byte-compares the SW script (checked on navigation and about every 24h) and bypasses HTTP caching for it (so don't cache `sw.js` aggressively).
- **`event.waitUntil(promise)`** keeps the SW alive for async work. `event.respondWith(promise)` answers a fetch.

**Caching strategies**

| Strategy | Behavior | Use for |
|---|---|---|
| **Cache-first** | Cache, falling back to network | Versioned/hashed static assets, fonts |
| **Network-first** | Network, falling back to cache | HTML, frequently changing API data |
| **Stale-while-revalidate** | Serve cache now, update in the background | Avatars, non-critical API data |
| **Network-only / cache-only** | Self-explanatory | Payments / precached shell |

```js
// sw.js
const CACHE = 'app-v3';
const PRECACHE = ['/', '/offline.html', '/app.css', '/app.js'];

self.addEventListener('install', e => {
  e.waitUntil(caches.open(CACHE).then(c => c.addAll(PRECACHE)));
});
self.addEventListener('activate', e => {
  e.waitUntil(
    caches.keys()
      .then(keys => Promise.all(keys.filter(k => k !== CACHE).map(k => caches.delete(k))))
      .then(() => self.clients.claim()));
});
self.addEventListener('fetch', e => {
  const { request } = e;
  if (request.method !== 'GET') return;                       // never cache mutations
  if (request.mode === 'navigate') {                          // network-first with offline fallback
    e.respondWith(fetch(request).catch(() => caches.match('/offline.html')));
    return;
  }
  e.respondWith(caches.match(request).then(cached => {        // stale-while-revalidate
    const network = fetch(request)
      .then(res => { if (res.ok) { const copy = res.clone(); caches.open(CACHE).then(c => c.put(request, copy)); } return res; })
      .catch(() => cached);
    e.waitUntil(network);
    return cached || network;
  }));
});
```
```js
// registration (in app code)
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js').then(reg => {
```

## 3.9.2 Fetch, Streaming, and Cancellation
🟡 Intermediate · **Must-know**

```js
async function api(path, { method = 'GET', body, signal } = {}) {
  const res = await fetch(`/api${path}`, {
    method,
    headers: body ? { 'Content-Type': 'application/json' } : undefined,
    body: body ? JSON.stringify(body) : undefined,
    credentials: 'same-origin',
    signal: signal ?? AbortSignal.timeout(10_000),
  });
  if (!res.ok) {
    const err = new Error(`HTTP ${res.status}`);
    err.status = res.status; err.body = await res.text().catch(() => '');
    throw err;                               // fetch only rejects on network failure
  }
  return res.status === 204 ? null : res.json();
}
```
- **`fetch` resolves for 404/500**, and rejects only on network errors, CORS blocks, or aborts. Always check `res.ok`.
- **Body is a single-use stream**: read once (`json()`, `text()`, `blob()`), or `clone()`.
- **Streaming responses:** `res.body.getReader()` for incremental reads, or `for await (const chunk of res.body)` where supported. This enables streaming LLM output (SSE or chunked), large downloads with progress, and NDJSON.
- **Upload progress:** `fetch` has no progress events (request streaming has limited support), so use XHR `upload.onprogress` or chunked uploads with presigned URLs (Phase 5).
- **Cancellation and races:** `AbortController` per request, abort on unmount/new query, and ignore `AbortError`.
- **Headers/credentials:** `credentials: 'include'` for cross-origin cookies (needs CORS support). **Retries:** only for idempotent requests or with idempotency keys.
- **Request deduping and caching** are best delegated to TanStack Query/SWR (Phase 4).
- **`keepalive: true`** and `sendBeacon` allow requests to survive page unload.

**Questions:** Why doesn't `fetch` reject on a 404? How do you timeout and cancel a fetch? How do you show download or upload progress? How do you consume a streaming response (e.g., from an LLM API)?

## 3.9.3 WebSockets, Server-Sent Events, and Alternatives
🔴 Advanced · **Must-know** (full stack real-time, depth in Phase 5)

| | **WebSocket** | **SSE (EventSource)** | **Long polling** | **Short polling** |
|---|---|---|---|---|
| Direction | Full duplex | Server → client only | Simulated push | Client pulls |
| Transport | Upgraded TCP (`ws://`/`wss://`) | Plain HTTP stream (`text/event-stream`) | HTTP | HTTP |
| Reconnect | Manual | **Automatic** (with `Last-Event-ID` resume) | Manual | N/A |
| Proxies/firewalls | Occasionally problematic | Works anywhere HTTP does | Works | Works |
| Binary | Yes | Text only | Any | Any |
| Use for | Chat, collaboration, games, trading | Notifications, live feeds, dashboards, LLM token streaming | Legacy fallback | Low-frequency updates |

- SSE over HTTP/1.1 has a **per-domain connection limit** (about 6 across tabs), whereas HTTP/2 multiplexes many streams.
- **Production concerns:** reconnect with exponential backoff and jitter, **application-level heartbeats** (browser WebSocket API can't send protocol pings), authentication (cookies on the upgrade request, or a short-lived ticket, since custom headers aren't supported by the browser API), message ordering and **idempotent** handlers, resync after reconnect (fetch missed state), backpressure (`bufferedAmount`), scaling across servers (sticky sessions or a pub/sub backplane like Redis), and cleanup on unmount.
```js
function connect(url, onMessage) {
  let ws, attempt = 0, closedByUser = false, hb;
  const open = () => {
    ws = new WebSocket(url);
    ws.onopen = () => { attempt = 0; hb = setInterval(() => ws.readyState === 1 && ws.send('{"type":"ping"}'), 25_000); };
    ws.onmessage = (e) => onMessage(JSON.parse(e.data));
    ws.onclose = () => {
      clearInterval(hb);
      if (closedByUser) return;
      const delay = Math.min(30_000, 500 * 2 ** attempt++) * (0.5 + Math.random() / 2);   // backoff + jitter
      setTimeout(open, delay);
    };
  };
  open();
  return {
    send: (d) => ws.readyState === 1 && ws.send(JSON.stringify(d)),
    close: () => { closedByUser = true; ws.close(); },
  };
}
```

```js
// SSE
const es = new EventSource('/events');
es.addEventListener('order', (e) => update(JSON.parse(e.data)));
es.onerror = () => { /* browser auto-reconnects; show a "reconnecting" indicator */ };
```

## 3.9.4 Files, Drag-and-Drop, and Binary Data
🟡 Intermediate · **Good-to-know**

- **Objects:** `File` extends `Blob`. `FileReader` (async, callback-based) or modern `blob.text()`/`arrayBuffer()`/`stream()`. `URL.createObjectURL(blob)` for previews (**call `URL.revokeObjectURL` to avoid leaks**). `blob.slice()` for chunking. `canvas.toBlob` for image export. `<a download>` or `showSaveFilePicker` (File System Access, Chromium) for saving.
- **Drag and drop:** to make a drop zone, you **must `preventDefault()` on `dragover`** (and `drop`), or the browser opens the file. Read `e.dataTransfer.files`. For keyboard and accessibility, always offer a normal `<input type="file">` too (WCAG 2.5.7 requires non-drag alternatives).
```js
zone.addEventListener('dragover', e => e.preventDefault());
zone.addEventListener('drop', e => { e.preventDefault(); handleFiles([...e.dataTransfer.files]); });
```
- **Upload architecture:** small files via `multipart/form-data`. Large files via **presigned URLs direct to object storage** (the app server issues a signed URL, the browser uploads straight to S3, then confirms), **chunked/resumable uploads** (tus, S3 multipart), progress through XHR, concurrency limits, client-side validation (type, size) for UX **plus** server-side validation, antivirus scanning, and never trusting `file.type` or filename.
- **Images client-side:** resize/compress before upload with canvas or `createImageBitmap` (in a worker), strip EXIF for privacy, and preview via object URLs.
- **Binary APIs:** `ArrayBuffer`, typed arrays, `DataView`, `TextEncoder/Decoder`, `btoa/atob` (Latin-1 only, so encode UTF-8 first), `Blob` ↔ base64 data URLs (33% bigger, avoid for large data).

**Questions:** How do you build a drag-and-drop uploader? Why does the browser open the file if you don't call `preventDefault`? How do you upload a 2GB file reliably? Why use presigned URLs? How do you avoid leaking memory with object URLs?

## 3.9.6 Internationalization (i18n) and Localization (l10n)
🟡 Intermediate · **Good-to-know** (**Must** for global products)

- **i18n** is designing so a product *can* support many locales. **l10n** is adapting it for a specific one (translations, formats, imagery).
- **Locale-aware formatting** with `Intl` (3.3.15): dates, numbers, currency, plurals, lists, relative time, collation.
- **Plurals and grammar:** English has two plural forms, but other languages have up to six (Arabic) and gender/case. **Never concatenate strings** (`"You have " + n + " items"`), since word order differs. Use **ICU MessageFormat**: `"{count, plural, one {# item} other {# items}}"`. Libraries: `react-i18next`, **FormatJS/react-intl**, `next-intl`, Lingui.
- **Keys and workflow:** stable semantic keys, extract and manage translations with a TMS (Crowdin, Lokalise), provide context for translators, **pseudo-localization** (accented, longer strings) to catch hardcoded text and layout breakage, and CI checks for missing keys.
- **Layout:** text expands (German and Finnish about 30%+ longer), so don't hardcode widths. Support **RTL** (Arabic, Hebrew) with `dir="rtl"` and CSS logical properties (3.2.7), mirror directional icons (not logos or media controls), and set `lang` per document and per fragment.
- **Locale detection:** user preference (stored) > URL (`/fr/`) > `Accept-Language` header > default. Don't rely on IP geolocation alone. Make switching easy.
- **Routing and SEO:** locale-prefixed paths or domains, `hreflang` alternates, localized metadata, canonical per locale.
- **Dates and time zones:** store UTC, display per user zone (3.3.15). **Currency:** store minor units plus the currency code, format with `Intl.NumberFormat`.
- **Performance:** lazy-load locale bundles per route/locale, and keep translation JSON out of the main bundle.
- **Other pitfalls:** text in images, sorting that assumes ASCII, names (no first/last assumption), address and phone formats, calendars, and number input with decimal commas.

**Questions**
1. How would you add i18n to an existing React app? 
2. Why can't you build translated sentences by concatenation? What do you use for plurals?
3. How do you support RTL? 
4. How do you choose a user's locale?
5. How would you test that nothing is hardcoded in English? *(pseudo-localization, lint rules, and missing-key CI checks)*
