# PHASE 1: Interview Preparation Foundations

## How a full stack interview pipeline works

```
Application → Recruiter screen → Online assessment OR take-home
           → Technical phone screen (coding)
           → Onsite/virtual loop (3-6 rounds)
                 ├─ Coding (1-2)
                 ├─ Frontend/Backend domain round (1)
                 ├─ System design (1, mid-level and above)
                 ├─ Behavioral / culture (1)
                 └─ Hiring manager (1)
           → Debrief → Offer → Negotiation
```

Every company varies. Startups may do only a take-home plus a pair session. Big tech runs a long, structured loop. Know which pipeline you're entering before you start preparing.

## 1.1 FULL STACK INTERVIEW (planning group)

### 1.1.1 Timeline Planning
🟢 Beginner · **Must-know**

**Definition:** Working backward from your target interview date to schedule what you learn, practice, and apply, with buffers.

**Why it matters:** Most failed preparation comes from poor allocation, such as 200 LeetCode problems and no system design, or months of tutorials and no mocks.

**Key concepts**
- **Backward planning:** fix the date, subtract a 1-week buffer, then divide the remainder into phases.
- **Diagnostic first:** rate yourself 0-3 on each area below. Time goes to your weakest high-weight areas, not your favorite ones.
- **Interview sequencing:** schedule your *least-wanted* companies first as warm-up, and cluster real interviews into a 2-3 week window so offers overlap and you can negotiate.
- **Weekly rhythm:** learn new material → practice → review mistakes → mock.
- **Buffer:** plan for 80% of available hours. Life interferes.

**Diagnostic (rate yourself 0-3)**

| Area | Score |
|---|---|
| JavaScript core (closures, event loop, async) | |
| React or your framework | |
| HTML/CSS and layout | |
| Node/Express and REST design | |
| SQL and data modeling | |
| Auth and security basics | |
| DSA (easy/medium) | |
| System design | |
| Git, CLI, Docker, CI basics | |
| Testing | |
| Behavioral stories | |
| Communication under pressure | |

Anything scoring 0-1 on a heavily weighted area for your target role is a priority.

**Suggested time allocation (balanced mid-level full stack)**

| Area | % of study time |
|---|---|
| DSA and problem solving | 25-30% |
| JavaScript/TypeScript and framework depth | 20% |
| Backend, databases, APIs | 15-20% |
| System design | 10-15% |
| Mock interviews and review | 10% |
| Behavioral and storytelling | 5% |
| Resume, portfolio, applications | 5% |

Adjust by track: frontend-leaning shifts 10% from backend to browser/CSS/performance, and backend-leaning does the reverse. Senior candidates shift 10-15% from DSA to system design and architecture.

**Sample weekly rhythm (10 hrs/week)**

| Day | Activity | Time |
|---|---|---|
| Mon | New concept (1 topic) | 1.5h |
| Tue | DSA: 2 problems of one pattern | 1.5h |
| Wed | Build or practice exercise | 1.5h |
| Thu | DSA: 2 problems and review | 1.5h |
| Fri | System design (1 case study) | 1.5h |
| Sat | Mock interview + self-review | 2h |
| Sun | Weekly review, flashcards, plan next week | 0.5h |

**Common mistakes**
- Starting applications before you're ready, then burning through your best companies.
- Planning 40 hrs/week while working full-time, then quitting by week 3.
- No buffer, so one missed week collapses the plan.
- Studying only what feels comfortable.

**Mini task:** Fill in the diagnostic, pick your date, and write a week-by-week plan with the top 3 weak areas given the most hours. Keep it in a doc you revisit weekly.

**Self-check:** Can you state your target date, your top 3 weak areas, and this week's plan in under 60 seconds?

### 1.1.2 Resource Selection
🟢 Beginner · **Must-know**

**Definition:** Choosing a small, high-quality set of learning materials and sticking with them.

**Why it matters:** Resource hopping is the main cause of "tutorial hell." Depth with one good source beats shallow exposure to ten.

**Key concepts**
- **One primary resource per area**, plus one reference. Add a second only if the first fails you.
- **Official docs first** for tools and languages. They're current and authoritative.
- **Active over passive:** if a resource doesn't make you write code or answer questions, pair it with exercises.
- **Recency check:** frameworks change fast, so prefer material updated within the last 1-2 years (React, Next.js, and Node especially).
- **Free-first:** pay only for something that fills a verified gap (structured question banks, mock platforms).

**Recommended starter stack**

| Area | Primary | Supplement |
|---|---|---|
| HTML/CSS | MDN Web Docs | web.dev Learn courses |
| JavaScript | javascript.info | *You Don't Know JS Yet* (Kyle Simpson), MDN |
| TypeScript | Official TypeScript Handbook | Total TypeScript (Matt Pocock, free tutorials plus paid workshops) |
| React | react.dev | Dan Abramov and Kent C. Dodds' writing on hooks and rendering |
| Node.js | nodejs.org docs and guides | Node.js Design Patterns (book) |
| SQL | PostgreSQL docs, SQLBolt | *Use The Index, Luke* (free web book) |
| DSA | NeetCode roadmap and videos | *Cracking the Coding Interview* (Gayle McDowell) |
| System design | *Designing Data-Intensive Applications* (Kleppmann) | *System Design Interview* vols 1 and 2 (Alex Xu), ByteByteGo |
| Behavioral | Tech Interview Handbook (free) | Your own story bank |
| Mocks | Peers, Pramp, interviewing.io | Recording yourself |
| Compensation | Levels.fyi | Glassdoor, Blind (verify carefully) |

**Evaluating a resource (5 questions)**
1. Is it current (check publish and update dates)?
2. Does it include exercises or projects?
3. Does it explain *why*, not just *how*?
4. Do experienced engineers recommend it?
5. Does it match my target level?

**Common mistakes**
- Collecting 50 bookmarks and finishing none.
- Watching videos at 2x without taking notes or writing code.
- Using outdated React tutorials that teach class components as the default.

**Mini task:** Build a one-page "resource map" listing one primary resource per row in the table above, with a completion target date.

**Self-check:** Can you name your one primary resource for each of the 8 major areas?

### 1.1.3 Mock Interviews
🟡 Intermediate · **Must-know**

**Definition:** Simulated interviews under realistic conditions (time limit, another person, no looking things up) followed by structured feedback.

**Why it matters:** Interviewing is a separate skill from engineering. Candidates who solve problems easily alone often fail when someone is watching and the timer is running. Mocks are the only way to train that.

**Key concepts**
- **Types:** coding, system design, behavioral, frontend/domain, and pair programming.
- **Cadence:** begin mocks by roughly 25-30% into your timeline. Do 1 per week, rising to 2-3 per week in the final 2-3 weeks.
- **Sources:** friends and colleagues, peer platforms (Pramp, interviewing.io), paid experienced interviewers for system design, or solo with a timer and recorded screen and audio.
- **Realism:** same tools you'll use in the interview (CoderPad-style editor or a shared doc, no autocomplete if the real one has none), a strict 45 minutes, and talking out loud the whole time.
- **Feedback loop:** every mock ends with scoring and 2-3 specific action items.

**Scorecard (score each 1-4)**

| Dimension | 1 (weak) | 4 (strong) |
|---|---|---|
| Problem understanding | Jumped to code | Clarified, restated, listed edge cases |
| Approach | Stuck or brute-force only | Compared options, justified choice |
| Coding | Buggy, messy | Clean, correct, well-named |
| Testing | None | Dry-ran examples and edge cases |
| Complexity analysis | Missing or wrong | Correct and explained |
| Communication | Silent or rambling | Structured, thinking aloud |
| Handling hints | Defensive, ignored | Took them gracefully |

**Self-mock protocol (no partner)**
1. Pick a problem you haven't seen. Set a 45-minute timer.
2. Record screen and microphone.
3. Talk the entire time as if someone is listening.
4. Rewatch at 1.5x and score yourself. Note every filler word, silence over 15 seconds, and missed edge case.

**Common mistakes**
- Doing mocks only with friends who go easy on you.
- Skipping feedback, which turns a mock into practice with no learning.
- Never mocking system design, which is hard to self-assess.

**Mini task:** Book your first mock for this week and write down its score so you have a baseline.

**Self-check:** Do you have a scorecard and a scheduled mock for each of the next 3 weeks?

### 1.1.4 Resume Review
🟢 Beginner · **Must-know** (deep dive in Phase 15)

**Definition:** Structuring and refining your resume so it passes an ATS and a 10-second recruiter scan, and gives interviewers good questions to ask.

**Why it matters:** Your resume is also your interview agenda. Interviewers pick questions from it, so every line must be defensible.

**Key concepts**
- **One page** for under 10 years of experience. Reverse chronological. Single column, standard fonts, and no graphics or tables, so ATS can parse it.
- **Bullet formula:** *Action verb + what you did + how (tech) + measurable result.*
- **Skills section:** group by category (Languages, Frontend, Backend, Databases, Cloud/DevOps) and list only what you can discuss for 10 minutes.
- **Projects:** include 2-3 with links, a one-line problem statement, stack, and a metric if available.
- **Tailoring:** mirror keywords from the job description honestly.

**Before and after**

> ❌ Worked on backend APIs using Node and MongoDB.
>
> ✅ Designed and shipped 12 REST endpoints (Node/Express, MongoDB) powering checkout for 40k monthly users; cut p95 latency from 900ms to 280ms by adding compound indexes and Redis caching.

> ❌ Responsible for React frontend.
>
> ✅ Rebuilt the dashboard in React + TypeScript with code splitting and virtualized tables, reducing initial load from 4.2s to 1.8s and cutting support tickets about slowness by 35%.

**If you have no numbers:** use scale (users, requests, records), time saved, or scope (team size, number of services). Never invent figures, because interviewers will probe them.

**Checklist**
- [ ] One page, PDF, named `FirstName-LastName-Resume.pdf`
- [ ] Every bullet starts with a strong verb
- [ ] 60% or more of bullets contain a result
- [ ] No typos (read it aloud, and have someone else read it)
- [ ] Links work (GitHub, portfolio, LinkedIn)
- [ ] Nothing listed that you can't discuss

**Mini task:** Rewrite your 5 weakest bullets using the formula.

**Self-check:** Can you give a 2-minute story behind each bullet?

### 1.1.5 Portfolio Building
🟡 Intermediate · **Must-know**

**Definition:** A small set of deployed, well-documented projects that demonstrate real full stack skill.

**Why it matters:** For juniors and career-changers, projects substitute for work experience. For seniors, they show current skills.

**Key concepts**
- **Depth over breadth:** 2-3 substantial projects beat 10 tutorial clones.
- **What makes a project interview-worthy**
  - Solves a real problem (even a small one)
  - Has authentication, relational data, and non-trivial business logic
  - Deployed with a live URL
  - Has tests and CI
  - README with architecture diagram, setup steps, and trade-off decisions
- **Project ladder:** see the 8 projects in the cross-cutting section (later part).
- **Talking points sheet:** for each project, prepare answers to the questions below.

**Project talking-points template**

| Question | Your answer (write it) |
|---|---|
| What problem does it solve and for whom? | |
| Why this stack? What alternatives did you consider? | |
| Draw the architecture. | |
| What was the hardest bug? How did you find it? | |
| What would break at 100x scale? | |
| What did you cut or defer, and why? | |
| What would you do differently? | |
| How is it tested and deployed? | |
| Security considerations? | |

**README checklist**
- [ ] One-paragraph description plus screenshot or GIF
- [ ] Live demo link and test credentials
- [ ] Tech stack and architecture diagram
- [ ] Setup in under 5 commands
- [ ] Design decisions and known limitations
- [ ] How to run tests

**Common mistakes**
- Todo app with no auth, no tests, no deployment.
- Copy-pasting tutorial code you can't explain.
- Broken live links, which interviewers do click.
- Hiding limitations. Honest "known issues" sections read as maturity.

**Mini task:** Pick your strongest project and fill in the talking-points template. Practice the architecture walkthrough out loud in 3 minutes.

**Self-check:** Can you explain any file in your best project and justify its design?

### 1.1.6 Mental Readiness (including Handling Interview Anxiety)
🟡 Intermediate · **Must-know**

**Definition:** Managing stress, confidence, and energy so your performance reflects your ability.

**Why it matters:** Anxiety narrows working memory, which is exactly what problem solving needs. Managing it is a trainable skill.

**Key concepts**
- **Exposure:** the most effective remedy is repeated realistic practice. Mocks make the real thing feel familiar.
- **Reframing:** treat the interview as a collaborative problem-solving session, not an exam. The interviewer wants you to succeed, since hiring is expensive for them.
- **Physiological tools:** box breathing (4 in, 4 hold, 4 out, 4 hold), a short walk before the interview, and avoiding extra caffeine.
- **Pre-interview routine (60 minutes before):** eat, test your tech (camera, mic, editor, internet backup), skim your one-page cheat sheet, and review your first-two-minutes introduction. Don't learn anything new.
- **In-the-moment tools:** slow your speech, pause before answering ("Let me think about that for a moment"), and write things down.
- **Rejection hygiene:** a rejection is data about one loop on one day. Debrief, log what went wrong, then move on. Don't ruminate.
- **Sleep and sustainability:** cramming the night before hurts recall. Protect 7+ hours of sleep.

**If you blank mid-interview (script)**
> "Let me step back and make sure I'm approaching this correctly. Can I restate the problem and walk through a small example?"

Working an example by hand usually unlocks the pattern.

**Post-interview debrief (within 2 hours)**
- What went well? What went poorly?
- Which questions surprised me?
- Which topics should I add to my study list?
- Did I handle nerves effectively? What would I change?

**Common mistakes**
- Treating one rejection as proof you're not good enough.
- All-night cramming.
- Comparing yourself to others' highlight reels online.
- Not practicing talking while coding.

**Mini task:** Write your personal pre-interview checklist and use it in your next mock.

**Self-check:** Do you have a go-to technique for each of: nerves before, blanking during, and rejection after?

### 1.1.7 Tracking Progress
🟢 Beginner · **Good-to-know**

**Definition:** Measuring your preparation with data so you can see what's working.

**Why it matters:** It's easy to feel productive without improving. Tracking exposes blind spots.

**Key concepts**
- **Study tracker columns:** date, topic, activity, time spent, confidence (1-5), follow-up needed.
- **DSA log:** problem, pattern, difficulty, time to solve, solved unaided (Y/N), mistake type, revisit date.
- **Mock score history:** plot scorecard totals over time.
- **Weak-topic list:** updated weekly, with the top 3 driving the next week's plan.
- **Application funnel:** applications → recruiter screens → technical screens → onsites → offers, so you can see where the pipeline leaks. Low screen rate means fix the resume. Low technical pass rate means more practice.
- **Weekly review (20 minutes, every Sunday):** what I did, what I learned, what's still weak, next week's plan.

**Metrics worth tracking**
- Problems solved per pattern, and percentage solved without hints
- Average time-to-solution by difficulty
- Mock scores by dimension
- Flashcard retention rate
- Application conversion at each stage

**Common mistake:** tracking vanity numbers ("300 problems solved") instead of retention and unaided success rate.

**Mini task:** Set up a spreadsheet or Notion board with the DSA log and application funnel tabs.

**Self-check:** Can you name your three weakest topics from data, not feelings?

### 1.1.8 Job Description Analysis
🟢 Beginner · **Must-know**

**Definition:** Decomposing a job posting into what the company needs, so you prepare and tailor accordingly.

**Why it matters:** The job description is the closest thing to the interview syllabus.

**Key concepts**
- **Split requirements into:** hard skills (React, PostgreSQL), practices (CI/CD, code review), scope signals ("own features end to end"), and level signals ("mentor," "drive architecture").
- **Required vs nice-to-have:** apply even if you match 60-70% of the required items, but weight prep toward the required stack.
- **Keyword mapping:** list their top 8-10 technologies and map each to a resume bullet or project of yours. Any unmapped keyword is a prep gap.
- **Company stage signals:** "fast-paced, wear many hats" means startup generalist. "Cross-functional alignment, scalability at millions of users" means a larger company.
- **Red flags:** unrealistic stacks (10+ unrelated technologies as "required"), vague ownership, and "rockstar/ninja" language.

**Worked example**

> *"Full Stack Engineer: React, TypeScript, Node.js, PostgreSQL, AWS. Own features from design to deploy. Experience with CI/CD. Nice: GraphQL, Kubernetes."*

| Signal | Interpretation | Prep action |
|---|---|---|
| React + TS | Frontend depth tested | Hooks, rendering, typing |
| Node + PostgreSQL | Backend API and SQL round likely | REST design, joins, indexing |
| AWS | Basic cloud questions | S3, Lambda, IAM, RDS |
| "Own features end to end" | Mid/senior expectations, system design likely | Mini design of a feature |
| CI/CD | Pipeline questions | GitHub Actions, deployment strategies |
| Nice: GraphQL, K8s | Low priority | Overview only |

**Mini task:** Take 3 job descriptions for your target role and build a frequency table of the technologies. That's your priority list.

**Self-check:** For any job post, can you produce a prioritized prep list in 10 minutes?

### 1.1.9 Target Role Selection
🟢 Beginner · **Must-know**

**Definition:** Choosing which flavor of full stack you're interviewing for, because the emphasis differs.

| Track | Heavily tested | Lightly tested |
|---|---|---|
| **Frontend-leaning** | JS/TS depth, React internals, CSS/layout, browser performance, accessibility, frontend system design | DB internals, infra |
| **Backend-leaning** | APIs, databases, caching, queues, auth, system design, concurrency | CSS details, animations |
| **Balanced** | Both at working depth, end-to-end feature design, trade-offs across the stack | Extremes on either side |
| **Startup generalist** | Shipping speed, breadth, practical debugging, deployment, product sense | Deep theory, long DSA |

**How to choose:** look at what you enjoy debugging, where your projects are strongest, and what the market near you demands. Frontend-leaning roles are often titled "Software Engineer, Web" or "Frontend Engineer," and "Full Stack Engineer" may mean either lean, so read the description (see 1.1.8).

**Mini task:** Pick one track and write a one-sentence positioning statement: *"I'm a full stack engineer leaning backend, strongest in Node, PostgreSQL, and API design, comfortable shipping React UIs."* Use it in intros.

**Self-check:** Does your resume, portfolio, and intro all point to the same track?

### 1.1.10 Target Level
🟡 Intermediate · **Must-know**

**Definition:** Understanding what's expected at junior, mid, senior, and staff so you can aim for, and prepare for, the right level.

| Dimension | Junior | Mid | Senior | Staff |
|---|---|---|---|---|
| **Coding rounds** | Easy-medium DSA, clean code | Medium DSA, solid fundamentals | Medium-hard, optimal solutions, tests | Same bar plus quality of reasoning |
| **Domain depth** | Knows the tools | Knows why tools work | Knows trade-offs and failure modes | Chooses stacks and defines standards |
| **System design** | Rarely asked or simple | Basic feature/service design | Full design with scale and trade-offs | Cross-system, organizational constraints |
| **Scope** | Tasks | Features | Projects, multiple engineers | Multi-team, multi-quarter |
| **Behavioral** | Learning, teamwork | Ownership, collaboration | Mentoring, conflict, leading | Influence without authority, strategy |
| **Ambiguity** | Needs clear specs | Handles some | Defines the problem | Finds the right problem |

**Level calibration tips**
- Interviewing above your level gets you a down-level offer at worst, so it's usually safe to try.
- Titles vary by company ("Senior" at a startup may equal "Mid" at big tech). Ask about the leveling guide.
- Your year count matters less than demonstrated scope and impact.

**Mini task:** For your target level, write 3 stories that demonstrate its scope signals.

**Self-check:** Can you describe how the expectations differ between your current level and the next?

### 1.1.11 Spaced Repetition and Note System
🟡 Intermediate · **Good-to-know**

**Definition:** A review schedule and note structure designed so what you learn is still in your head on interview day.

**Why it matters:** Without review, retention drops sharply within days. Interview prep covers a huge surface area, so retention is the bottleneck.

**Key concepts**
- **Review intervals:** day 1, 3, 7, 14, 30. Tools like Anki automate this.
- **Good flashcards:** one fact per card, phrased as a question, answerable in about 10 seconds.
  - ✅ *"What are the phases of the Node.js event loop?"*
  - ✅ *"Difference between `Promise.all` and `Promise.allSettled`?"*
  - ❌ *"Explain everything about closures."* (too broad)
- **Card types to use**
  - Concept (definition and why)
  - Compare (X vs Y)
  - Code-output ("What does this log?")
  - Complexity ("Time complexity of heap insert?")
- **Error log:** every mistake in a mock or problem becomes a card or a note. Mistakes show your actual weak spots.
- **Teach-back (Feynman):** explain the topic out loud or in writing as if to a beginner. Gaps in the explanation reveal gaps in understanding.
- **Note structure:** one note per concept with sections *Definition / Why it matters / Example / Pitfalls / Interview questions*. Tools: Obsidian, Notion, or plain Markdown in a Git repo.
- **Daily cap:** 20-30 new cards a day at most, or reviews will pile up.

**Common mistakes**
- Making cards by copying paragraphs.
- Skipping reviews for a week, so the backlog snowballs.
- Taking notes that are never revisited.

**Mini task:** Create 20 flashcards from JS Core topics you got wrong. Review daily for a week.

**Self-check:** Do you have an error log, and does each entry produce a review item?

## 1.2 PREPARATION STRATEGY (interview formats)

### 1.2.1 Recruiter Screens
🟢 Beginner · **Must-know**

**Definition:** A 20-30 minute call (often non-technical) to check fit, motivations, logistics, and compensation range.

**Why it matters:** It's a real filter. Recruiters reject people who ramble, are vague about their experience, or have misaligned expectations.

**What they evaluate:** communication, relevance of experience, motivation, salary and location fit, timeline and visa.

**Common questions**
1. Tell me about yourself.
2. Why are you looking to leave your current role?
3. Why this company and this role?
4. What are your salary expectations?
5. What's your timeline and are you interviewing elsewhere?
6. What are you looking for in your next role?

**Model "Tell me about yourself" (present → past → future, 90 seconds)**
> "I'm a full stack engineer with about four years of experience, currently at X where I build and maintain the customer-facing React and Node platform serving around 50k users. Before that I worked at Y on internal tooling, where I got deep into PostgreSQL and API design. Recently I led the migration of our checkout flow to TypeScript, which cut production bugs noticeably. I'm now looking for a role where I can own features end to end on a product with real scale, and your focus on developer tooling really matches what I enjoy."

**Salary question: deflect politely first**
> "I'd like to learn more about the role and level before naming a number. Could you share the budgeted range for this position?"

If pressed, give a researched range based on market data with your target at the lower-middle, never below your real floor. (Some regions legally require ranges in postings.)

**Questions to ask the recruiter:** team structure, interview process and timeline, what success looks like in 6 months, why the role is open.

**Mistakes:** speaking negatively about your current employer, giving a number first with no research, being vague about your own contributions.

**Mini task:** Write and rehearse a 90-second intro and a 30-second "why this company" for your top three targets.

**Self-check:** Can you do your intro without notes, in under 90 seconds, with no filler?

### 1.2.2 Technical Assessments (Online Assessments)
🟡 Intermediate · **Must-know**

**Definition:** Timed, automated coding tests (HackerRank, CodeSignal, Codility, or a company's own platform), typically 60-120 minutes with 2-4 problems.

**Why it matters:** They're the first technical filter at many companies, and scoring is automated, so edge cases and efficiency matter.

**Strategy**
1. **Read all problems first** (2-3 minutes). Start with the easiest to bank points.
2. **Time-box:** if you're stuck for 15 minutes, move on and return.
3. **Partial credit:** a correct brute-force solution that passes some tests beats a half-written optimal one.
4. **Test your own edge cases:** empty input, single element, duplicates, negatives, maximum size.
5. **Use the platform's custom input** to run your tests before submitting.
6. **Mind constraints:** an input of 10⁵ needs O(n log n) or better. Constraints hint at the intended complexity.
7. **Know your language's I/O and standard library** (sorting with comparators, maps, heaps) before the test.
8. **Rules:** many tests are proctored (webcam, tab-switching detection). Follow the stated rules.

**Constraints cheat sheet**

| n | Likely complexity needed |
|---|---|
| ≤ 20 | O(2ⁿ) / backtracking |
| ≤ 500 | O(n³) |
| ≤ 5,000 | O(n²) |
| ≤ 10⁵-10⁶ | O(n log n) or O(n) |
| ≤ 10⁹ | O(log n) or O(1) |

**Mistakes:** spending 50 minutes on one problem, ignoring hidden-test edge cases, not practicing on the platform's format beforehand.

**Mini task:** Do two timed practice sets (90 minutes, 3 problems) on the platform your target company uses.

**Self-check:** Do you have a rule for when to abandon a problem and move on?

### 1.2.3 System Design Rounds (overview; full coverage in Phase 12)
🔴 Advanced · **Must-know for mid and above**

**Definition:** A 45-60 minute open-ended discussion where you design a system (e.g., a URL shortener or chat app) and justify trade-offs.

**What they evaluate:** structured thinking, requirement gathering, knowledge of building blocks, trade-off reasoning, and communication. There is no single right answer.

**Time-boxed framework (45 minutes)**

| Step | Time | Output |
|---|---|---|
| 1. Requirements (functional, non-functional) | 5-7 min | Scope list, scale assumptions |
| 2. Estimation | 3-5 min | QPS, storage, bandwidth |
| 3. API design | 5 min | Endpoints, payloads |
| 4. Data model | 5 min | Tables or collections, key indexes |
| 5. High-level architecture | 8-10 min | Diagram: clients, LB, services, DB, cache, queue |
| 6. Deep dive | 10-12 min | 1-2 components in detail (interviewer's choice) |
| 7. Bottlenecks and trade-offs | 5 min | Scaling, failures, alternatives |

**Mistakes:** diving into a database choice before clarifying requirements, drawing a giant diagram without explaining it, never mentioning trade-offs, ignoring the interviewer's hints.

**Mini task:** Design a URL shortener using the framework in 40 minutes, talking aloud.

**Self-check:** Can you recite the 7 steps from memory?

### 1.2.4 Behavioral Interviews (overview; full coverage in Phase 14)
🟡 Intermediate · **Must-know**

**Definition:** Questions about past behavior ("Tell me about a time...") used to predict future performance.

**Prepare:** a story bank of 8-10 stories mapped to themes (conflict, failure, leadership, ambiguity, tight deadline, mentoring, disagreement, impact), each in STAR format (Situation, Task, Action, Result), 2 minutes each, with measurable results and a reflection ("what I learned").

**Mistakes:** using "we" throughout so your contribution is unclear, stories with no result, blaming others, and answering hypothetically instead of from real experience.

**Mini task:** Write 3 stories this week and practice them aloud.

### 1.2.5 Pair Programming Rounds
🟡 Intermediate · **Must-know (especially at startups)**

**Definition:** You and an interviewer work together on a realistic task, such as adding a feature, fixing failing tests, or building a small component or API, often in your own editor or a shared environment.

**What they evaluate:** how you collaborate, not just whether the code works. They watch how you break down a task, use tools, debug, and respond to input.

**How to do well**
- **Restate and plan** before typing: "I'll build the endpoint first, then the UI, then handle errors."
- **Work in small steps** and run the code often.
- **Narrate your reasoning** and invite input: "Does that approach make sense to you?"
- **Read existing code** first. Follow the repo's conventions.
- **Use tools fluently:** shortcuts, debugger, test runner, and browser DevTools. Fluency signals real-world experience.
- **Handle stuck moments aloud:** "I'm not sure about this API. I'd normally check the docs. Is it okay if I look?" (Looking things up is usually allowed and realistic.)
- **Write at least a few tests** or manually verify behavior.

**Typical tasks:** build a paginated list with search, implement a debounced autocomplete, add an endpoint with validation, fix a bug in a failing test suite, refactor a messy function.

**Mistakes:** coding silently for 10 minutes, ignoring the interviewer's suggestions, over-engineering instead of getting something working, never running the code.

**Mini task:** Pair with a friend on building a searchable, paginated user list (React + mock API) in 60 minutes.

**Self-check:** Do you narrate while coding and run the code every few minutes?

### 1.2.6 Hiring Manager Chats
🟡 Intermediate · **Must-know**

**Definition:** A conversation with the future manager covering your experience, working style, motivation, and team fit. It's often semi-technical.

**What they evaluate:** ownership, communication, how you handle ambiguity and feedback, and whether you'd be productive and pleasant to work with.

**Common questions**
1. Walk me through your most impactful project.
2. How do you prioritize when everything is urgent?
3. How do you handle disagreement with a teammate or product manager?
4. What kind of environment helps you do your best work?
5. Where do you want to grow in the next 2 years?
6. What do you do when you disagree with a technical decision that's already been made?

**Questions you should ask (pick 4-5)**
- What does success look like in the first 90 days?
- How does the team decide what to build?
- How are code reviews and deployments handled?
- What's the biggest technical challenge the team is facing?
- How do you give feedback and handle growth conversations?
- What's the on-call situation?

**Mistakes:** asking only about perks or compensation, not asking any questions, giving generic answers without specifics.

**Mini task:** Prepare the "most impactful project" story with context, your role, trade-offs, results, and learnings.

### 1.2.7 Onsite Loops
🔴 Advanced · **Must-know**

**Definition:** A series of back-to-back interviews (virtual or in person), typically 3-6 rounds of 45-60 minutes, done in one day or spread across a few days.

**Typical composition**

| Company type | Loop |
|---|---|
| Big tech | 2 coding, 1 system design (mid and above), 1 behavioral, sometimes a domain round |
| Mid-size/scale-up | 1 coding, 1 domain (frontend or backend), 1 system design, 1 behavioral and team fit |
| Startup | Take-home or pair session, a founder/CTO chat, a culture conversation |
| Agency/consultancy | Practical build, client-communication scenario, a portfolio review |
| Enterprise | Technical Q&A, architecture discussion, a behavioral round, sometimes a panel |

**Managing the loop**
- **Energy:** eat well, hydrate, and use breaks to reset. Don't replay the last round in your head.
- **Each round is independent:** interviewers typically submit separate feedback, so a bad round doesn't doom you. Don't spiral.
- **Consistency:** the same candidate often meets multiple interviewers, so keep your technical decisions and story details consistent.
- **Thank-you notes:** a short, specific follow-up to the recruiter is fine.

**Mini task:** Run a full mock loop with 4 back-to-back 45-minute sessions (coding, domain, design, behavioral), with friends playing interviewers if possible.

**Self-check:** Do you have a plan for energy, breaks, and recovering after a bad round?

### 1.2.8 Take-Home Assignments
🟡 Intermediate · **Must-know (common at startups)**

**Definition:** A small project you complete on your own time, often with a stated 2-4 hour expectation, then discuss in a follow-up interview.

**What they evaluate:** code quality, structure, testing, communication, product judgment, and whether you can finish and ship.

**Strategy**
1. **Clarify scope and time expectation.** Ask what to prioritize.
2. **Time-box strictly.** Don't spend 20 hours on a "3-hour" task. If you need to cut features, say so explicitly.
3. **Deliver a working, runnable solution** with clear setup instructions. A working small solution beats a broken ambitious one.
4. **README essentials:** how to run, how to test, what you built, what you skipped and why, how you'd extend it, and the assumptions you made.
5. **Include tests** for the core logic, with a few meaningful tests rather than a coverage chase.
6. **Commit history:** small, logical commits with clear messages.
7. **Be ready to discuss** every decision in the follow-up, and to extend it live.

**Grader's checklist**
- [ ] Runs on first try with the given instructions
- [ ] Clear structure (separation of concerns)
- [ ] Input validation and error handling
- [ ] Meaningful tests
- [ ] Sensible naming, no dead code
- [ ] Honest trade-off notes

**Mistakes:** gold-plating the UI while core logic is untested, skipping the README, over-engineering with unneeded patterns, using libraries you can't explain.

**Mini task:** Do a practice take-home (e.g., "build a URL shortener API with tests") in a strict 3 hours, then write the README.

### 1.2.9 Live Debugging Rounds
🟡 Intermediate · **Good-to-know**

**Definition:** You're given broken code (a failing test suite, a buggy endpoint, a misbehaving component) and asked to find and fix the issues.

**Systematic approach**
1. **Reproduce** the failure and read the error message and stack trace fully.
2. **Form a hypothesis** about the cause, and state it aloud.
3. **Isolate:** narrow with `console.log`, the debugger, or bisecting (comment out half).
4. **Verify the hypothesis** before changing code. Change one thing at a time.
5. **Fix, then re-run** the failing case plus related cases.
6. **Explain the root cause** and how to prevent recurrence (a test, validation, a type).

**Commonly planted bugs:** off-by-one errors, async race conditions (missing `await`), mutating state directly in React, stale closures in `useEffect`, wrong SQL join, unhandled promise rejection, incorrect `this`, wrong HTTP status handling, and missing null checks.

**Mistakes:** randomly changing code hoping it works, not reading the error message, fixing the symptom instead of the cause.

**Mini task:** Debug a deliberately broken Express and React app that a friend prepares, narrating aloud.

### 1.2.10 Code Review Rounds
🟡 Intermediate · **Good-to-know (common at mid and senior)**

**Definition:** You're shown a pull request or code snippet and asked to review it as you would on the job.

**What to look for (in priority order)**
1. **Correctness:** does it do what's intended? Edge cases?
2. **Security:** injection, auth checks, secrets, unsafe input.
3. **Performance:** N+1 queries, unnecessary re-renders, blocking operations.
4. **Design:** separation of concerns, naming, duplication.
5. **Tests:** are the important paths covered?
6. **Readability and style.**

**Practice snippet. How many issues can you find?**

```js
app.get('/user/:id', async (req, res) => {
  const user = await db.query(`SELECT * FROM users WHERE id = ${req.params.id}`);
  const posts = [];
  for (const p of user.postIds) {
    posts.push(await db.query(`SELECT * FROM posts WHERE id = ${p}`));
  }
  res.json({ ...user, posts, password: user.password });
});
```

**Issues**
- SQL injection (string interpolation), so use parameterized queries
- Leaks `password`, so return only needed fields
- N+1 queries and sequential awaits, so use one `WHERE id = ANY($1)` query or a join
- `SELECT *` over-fetches
- No try/catch, so errors become unhandled rejections
- No check for a missing user (`user` could be undefined, giving a 500 instead of 404)
- No authorization check (any user can fetch any other's data, an IDOR)
- No input validation on `id`

**How to give feedback:** be specific, explain the *why*, suggest a fix, and separate blocking issues from nits ("Nit:", "Suggestion:", "Blocking:"). Be kind. Critique the code, not the person.

**Mini task:** Review 3 open-source PRs on GitHub and write your comments as practice.

### 1.2.11 Bar-Raiser and Culture Rounds
🟡 Intermediate · **Good-to-know**

**Definition:** A round (often with an interviewer from outside the hiring team) that evaluates long-term potential, values alignment, and whether you raise or lower the team's bar.

**What they evaluate:** ownership, learning ability, handling of ambiguity and failure, integrity, and collaboration. Values are often public (e.g., Amazon's Leadership Principles), so research and map your stories.

**Prepare:** read the company's stated values or principles, map two stories to each, prepare a "biggest failure and what I changed" story, and prepare "how do you handle disagreement" with a real example.

**Mistakes:** memorized, generic answers with no specifics, treating the round as a formality.

### 1.2.12 Company-Type Differences

| Dimension | Startup | Scale-up | Big Tech | Agency | Enterprise |
|---|---|---|---|---|---|
| **Process** | Fast, 2-3 steps | 4-5 steps | Long, structured, 5-8 steps | Practical, portfolio-led | Panel, formal |
| **Coding** | Practical, build-something | Mixed | Heavy DSA | Practical | Light to moderate |

### 1.2.13 Remote Interview Etiquette and Setup
🟢 Beginner · **Must-know**

**Checklist**
- [ ] **Tech check 30 minutes early:** camera, mic, headphones, screen share, the specific meeting tool, a stable connection, and a phone hotspot as a backup
- [ ] **Environment:** quiet, front-facing light, neutral background, notifications off, other apps closed
- [ ] **Editor ready:** font size large enough to read when shared, a clean desktop, and no sensitive tabs open
- [ ] **Materials:** water, pen and paper (for diagrams), a short cheat sheet only if allowed, and your resume visible
- [ ] **Camera discipline:** look at the camera when speaking, and nod and respond visibly since remote cues are weaker
- [ ] **Narrate more than in person:** silence on a call feels longer
- [ ] **If tech fails:** message the recruiter immediately and stay calm. This is common and understood
- [ ] **No outside help:** don't use AI assistants or notes unless explicitly permitted. Interviewers can often tell, and it ends candidacies

## 1.3 INTERVIEW COMMUNICATION

### 1.3.1 Thinking Out Loud
**Why:** the interviewer can't see your mind. A silent correct answer yields less signal than a spoken, structured process.

**Structure for coding problems**
1. **Restate:** "So I need to return the indices of two numbers that add to the target."
2. **Examples:** "For `[2,7,11,15]` and target 9, the answer is `[0,1]`."
3. **Brute force:** "Check every pair, O(n²). Works but slow."
4. **Optimize:** "A hash map of seen values gives O(n)."
5. **Confirm before coding:** "Does that approach sound good?"
6. **Code while narrating**, then **test** with an example and an edge case.
7. **State complexity:** "Time O(n), space O(n)."

**Avoid:** narrating every keystroke, or going silent for more than 30-60 seconds.

### 1.3.2 Clarifying Questions

| Category | Examples |
|---|---|
| **Input** | Can the array be empty? Are values sorted? Duplicates? Negative numbers? Max size? |
| **Output** | Return indices or values? What if there's no answer? |
| **Scale** | How many users? Read-heavy or write-heavy? |
| **Constraints** | Memory limits? Latency target? Can I use library functions? |
| **Behavior** | Case-sensitive? Mutate in place or return a copy? |
| **System design** | Core features vs nice-to-have? Mobile and web? Global users? Consistency vs availability priority? |

Asking good questions is a positive signal. Asking none is a red flag.

### 1.3.3 Handling Hints
- Hints are not failures. Interviewers give them to see how you collaborate.
- **Acknowledge, then integrate:** "That's helpful. If I sort first, I can use two pointers..."
- Don't argue defensively or ignore the hint. If you disagree, say why politely and with reasoning.
- If you needed a hint, show you could solve the *variant* afterward. That recovers the signal.

### 1.3.4 Recovering from Blanking
1. Pause and breathe. Say: "Give me a moment to think."
2. Work a small example by hand on paper.
3. Restate what you *do* know and the constraint you're stuck on.
4. Try the brute force. A working slow solution is a platform to optimize from.
5. Ask a clarifying question to buy thinking time and information.
6. If still stuck: "Here's where I'm stuck: [specific]. Could you nudge me on [specific area]?" Specific beats "I don't know."

### 1.3.5 Explaining Trade-offs

**Template**
> "I see two options. **A** is [approach], which gives [benefit] but costs [drawback]. **B** is [approach], which gives [benefit] but costs [drawback]. Given [requirement or constraint], I'd choose **A**. I'd revisit if [condition changes]."

**Example**
> "For sessions, I could use JWTs, which are stateless and scale easily but are hard to revoke, or server-side sessions in Redis, which are easy to revoke but need shared storage. Since we need immediate logout and have Redis already, I'd use sessions. If we later go multi-region and want to reduce lookups, I'd revisit short-lived JWTs with a refresh flow."

Always tie the decision to a *stated requirement*, and always say when you'd change it.

### 1.3.6 Whiteboard and Shared-Editor Habits
- **Whiteboard/diagram:** write large, in boxes and arrows left to right, label data flows, and number the steps of a request. Leave room for additions.
- **Shared editor:** use meaningful names, write helper function signatures first, and keep code compact but readable. Comment your plan as `// TODO` outlines first.
- **Structure first:** outline function names, then fill them in. This shows you can plan.
- **Test on the page:** walk an example through your code line by line, tracking variable values.

### 1.3.7 Asking Good Questions at the End

**Good questions**
- What's the most interesting technical challenge the team has tackled recently?
- How does the team handle technical debt and refactoring?
- What does the code review and release process look like?
- What do successful engineers here do differently?
- What are the biggest priorities for the team in the next 6 months?
- What would you change about working here?

**Avoid:** questions answerable from the careers page, only asking about compensation or perks with engineers, and "no questions."
